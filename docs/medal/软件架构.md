# OpenMS 勋章系统软件架构

> 对照《OpenMS 勋章系统设计方案》v0.14（2026-10-20）。本文只规定实现落点，不复述档位表。  
> 档位数字以该方案为准，写入成就定义的 `thresholds`，不写进业务分支。定义不按规则分版本。  
> 本文不生成迁移、不改生产代码。迁移由 Django 根据模型生成，禁止手改迁移脚本。

当前自动评估覆盖原始股东、新手、个人最佳和三阶复合勋章，并提供人工授予、撤销及录像补传时间校正。本文其他赛事、历练和隐藏规则仍是设计目标；第 8、9 节区分当前行为与后续优化。后端回归位于 `back_end/saolei/medal/test*.py`，前端回归位于对应服务的 `.test.ts` 和组件的 `.cy.ts`。

## 1. 目标与总原则

勋章系统消费网站已经收下的录像、用户和赛事结果，在服务端判定、落库、再供展示读取。客户端可以展示，不能申报 BV、数字格、thrp、名次或「我已达成」。

各类勋章的判定、进度是否只升不降、解锁是否永久、规则改档时怎么重算、证据失效时怎么回滚，都不相同。不要做成一张「带阶段的成就表」再靠配置区分。能力四项是个人最佳；新手和历练里既有一次性事实，也有累计；赛事只抄已经颁奖的官方名次；隐藏成就对未解锁者不可见；纪念勋章多数由运营写入。

没有人工覆盖时，规则改档和证据失效走同一条写库路径：用当前规则重算，够哪档写哪档，一档不够就撤销，不另发中间档。证据失效指录像冻结、删除、成绩作废或排名被官方改写。管理员可对指定玩家的指定授予身份锁定档位或禁止发放，优先于自动重算，直到明确恢复自动。人工纪念没有自动判定器，解除其人工发放后不会自行重新获得。

TOP5 榜、锚点、NT20.5、定阶小数表都不是解锁条件。网站可以继续维护这些榜，勋章不读它们来发奖。

不做梁山分，也不做现任、历史最高，或任何「某日全站排第几」。网站录像现在不全，以后导入历史录像也补不出当时的座次。比赛结束后才上传、却要算进该届的录像，不能用来回放结束当天的排名。

个人门槛（破限、神速、全能、效率、三阶、新手、历练、隐藏）只聚合该玩家自己已经在库里的合格录像。历史录像导入之后重算这一枚的阶段。这不需要其他玩家的数据，也不把 `stage_log` 当成可对外的历史排名。

赛事名次只在 `state = AWARDED` 且官方名次行已经写下之后复制那一行。不读录像的 `upload_time` 来决定它属于哪一届。赛后补传本身不改勋章；赛事把该届官方名次正式改写之后，勋章跟着新行改写这一枚。没有官方名次行的历史比赛不补发。

## 2. 与现有数据的边界

### 2.1 录像：读什么

权威行是 `videomanager.VideoModel`。点击和比率里，下面这些是**已落库的生成列**（`GeneratedField`，`db_persist=True`），勋章直接读库，不在接口里重算，也不采用前端 `VideoAbstract` 的同名 getter：

| 用途 | 字段 | 含义 |
| --- | --- | --- |
| 总点击、有效点击 | `cl`、`ce` | `cl = left + right + double`，`ce = left_ce + right_ce + double_ce` |
| 时间 | `timems` | 毫秒。展示秒数是 `timems / 1000` |
| 3BV | `bv` | |
| 3BV/s | `bvs` | `bv / timems * 1000`。`timems = 0` 时为 0 |
| STNB 的底 | `iqg` | `bv / (timems/1000) ^ 1.7`。`timems = 0` 时为 0 |
| IOE、效率、Corr | `ioe`、`thrp`、`corr` | `ioe = bv/cl`，`thrp = bv/ce`，`corr = ce/cl` |
| 数字格 | `cell0` … `cell8` | 方案里的数字收藏只读这些计数 |

`stnb` **不是列**。它是 `VideoModel.stnb`：`STNB_COEFFICIENTS[level] * iqg`。系数在 `videomanager.models`：初级 36、中级 162、高级 435。同一难度内比 `iqg` 与比 STNB 顺序相同；跨难度必须乘上该难度的系数后再和整数档比较。

前端 `front_end/src/utils/ms_const.ts` 的 `STNB_const`（本地存储默认 47.299 / 153.73 / 435.001）只影响页面颜色和客户端展示，**不能**作为授予或补发的公式。勋章 API 返回服务端按 36 / 162 / 435 算出的值，前端不得再用本地系数重判是否过档。

模型里没有 `completion`。方案公式中的 \(\sqrt{\mathrm{completion}}\) 在现网上没有字段。已通过审核的整局，架构按网站现公式处理：\(\mathrm{STNB} = K \times \mathrm{iqg}\)，即把完成度视为 1。不要为勋章加一列让客户端填完成度。若以后确认未完成局也会进入 `OFFICIAL`，改公式后重算，而不是现在猜一个系数。

NF / FL 只看 `right_ce`，不看 `flag`，也不看模式。`right_ce = 0` 为 NF，`right_ce > 0` 为 FL，`right_ce` 为空则两边都不进。这与 `videomanager/test_nf.py` 的约定一致：模式和标雷标志都不能代替 `right_ce`。

`thrp`、`ioe` 的生成式没有除零保护。`ce` 为空或 0 的录像不进入效率；`cl` 为空或 0 的不读 IOE（本来也不发 IOE 勋章）。NF 的 thrp 只接受 `ce >= bv`（即 thrp ≤ 1）。`right_ce = 0` 但 thrp > 1 的行视为坏数据：不授予 NF 的 1 档，也不改道进入 FL。

### 2.2 能力类录像的共同资格

破限、神速、全能、效率，以及效率下的 NF 破限 / NF 神速 / NF 全能，只统计同时满足下面条件的行：

- `state = OFFICIAL`（`'c'`，已通过审核）。`PLAIN`、`FROZEN`、`IDENTIFIER`、`EXTERNAL` 都不算。
- `mode = STD`（`'00'`）。
- `level` 为 `b` / `i` / `e`。自定义级别（`c8_8_40` 等）不进入这些系列。
- `ongoing_tournament = False`。进行中的赛事录像在 `tournament.services` 里会先标上这个标记，结束时清掉。清掉之后才会进入生涯最佳，与 `speedranking` 的入榜条件一致。

破限、神速、全能、效率，以及 NF 破限、NF 神速、NF 全能、NF/FL 效率，都不设 BV 下限。`bv_min` 对这些定义留空。

低 BV 不会拉低 STNB。`STNB = K × bv / t^1.7`，时间随盘面一起变，不能把 BV 单独当成扣分项，也不要用这个理由滤掉录像。

下面这些 BV 门槛属于别的榜或赛事，不要套到能力勋章上：

- `speedranking.saolei` 的 3BV/s 是初级 `bv >= 4`、中级 `>= 30`、高级 `>= 100`（`bb` / `ib` / `eb`）。
- `speedranking.top` 的 `MINIMUM_BV` 初级是 **10**。那是前五均值榜。
- `speedranking.saolei` 的初级时间门槛是 `bv >= 2`（`bt`）。
- 金羊杯是 `GSC_Defaults.B_BV_MIN = 10`、中级 30、高级 100。只用于金羊杯算分。

现有 Redis 榜不是勋章的事实来源：

- `speedranking.pb` 是「每个 BV 一条最快时间」，不是生涯时间 / 3BV/s / STNB / thrp 最佳。
- `speedranking.saolei` 只有时间与 3BV/s 的单条纪录，没有 STNB、thrp，且初级时间门槛与破限不一致。NF 录像在这里会同时进入普通榜和 NF 榜。
- `speedranking.top` 保存各指标前五及 20 人锚点。勋章不读「是否在前五」或锚点。

能力勋章从合格 `VideoModel` 判定最高可达档位，只把自然档位写入进度行，不保存最佳成绩或最佳录像。不读排行榜 Redis。`medal:display:v4:{user_id}` 保存勋章状态，能力勋章的 `value` 为空；展示榜继续使用自己的纪录缓存。

同一条录像可以同时成为「破限」和「NF 破限」的证据，因为那是两个定义，各自保留最早达标证据。它不能同时进入 NF thrp 和 FL thrp。累计类（局数、BV 种数、参赛次数）另有贡献表，一条 `VideoModel.id` 在同一个累计指标里只出现一次。

### 2.3 用户、实名、模式、平台

- 玩家是 `userprofile.UserProfile`。实名沿用 `has_realname()`：`realname != '匿名'`。默认值就是 `'匿名'`。没有单独的实名审核列；名字在 `userprofile` 的更新流程里过滤。勋章不再发明一个审核状态。
- `msuser.UserMS` 上的 `video_num_beg`、`video_num_std`、`video_num_nf` 等在**创建录像时**就加，不要求已过审，也不能表达「全模式」。`video_num_ng` 只加了竞速无猜。这些计数器不能当作新手或历练进度。
- 模式以 `config.text_choices.MS_TextChoices.Mode` 为准，共 10 个：`00` 标准、`01` upk、`04` win7、`05` 竞速无猜、`06` 强无猜、`07` 弱无猜、`08` 准无猜、`09` 强可猜、`10` 弱可猜、`11` 标准递归。前端 `MS_Mode` 少了 upk、win7、弱无猜、准无猜、强可猜，不能当作「全模式」名单。
- 每个 `accountlink.models.Platform` 一枚一次性勋章：Bilibili、Authoritative Minesweeper、Mineracer、腾讯QQ、扫雷网、Minesweeper.Online。完成是该平台 `AccountLinkQueue.verified = True`。未验证的队列行不算。各平台各发各的，不设「全部平台都绑定」。解除或改为未验证，只收回这一枚。以后 `Platform` 新增取值，是新的 `code`，不要求已有玩家补绑。
- 「导入扫雷网录像」看 `accountlink.VideoSaolei.import_video` 指向的 `VideoModel` 是否已是 `OFFICIAL`。不看 `AccountSaolei` 上的远端局数，也不看客户端回执。和「连上扫雷网」是两枚。

`ExpandVideoModel.identifier` 是录像文件里的玩家标识，不是对局指纹。网站目前没有内容哈希，识别不了「同一局传了两次」。累计类以 `VideoModel.id` 去重。在服务端指纹出现之前，两行过审录像会算两局。不要增加客户端去重参数来补这个缺口。

### 2.4 赛事与金羊杯

赛事主体在 `tournament`，不在 `ranking`。`ranking.Match` 与 `UserMSScoreRank` 是未完成的草稿，勋章不读。

金羊杯：

- 一届是 `GSCTournament`，`order` 为届数，中文名由 `order` 生成。
- 选手是 `GSCParticipant`。最好、边缘、合计已经是列：初级 `bt1st`、`bt20th`、`bt20sum`；中级 `it1st`、`it12th`、`it12sum`；高级 `et1st`、`et5th`、`et5sum`。单位是毫秒，越小越好。
- `t37` 是三组合计的生成列。父表 `TournamentParticipant.rank` 由 `refresh_tournament_ranks` 按 `t37` 从小到大写成 1、2、3…，未完赛的选手也在里面。勋章不直接使用这个 `rank`。
- 占位默认值是 `GSC_Defaults`（初级 10000、中级 60000、高级 240000 毫秒）。有效时间必须严格快于对应默认值。完赛指三个边缘列都不是占位：`bt20th != 10000` 且 `it12th != 60000` 且 `et5th != 240000`，也就是初级 20 局、中级 12 局、高级 5 局都已填满。任一边缘仍是占位，就是未完赛。
- 未完赛不进入该届任何金羊杯统计，也不产生金羊杯参赛贡献。名次只在完赛选手之间，按已经写下的成绩列排序。勋章不扫录像，也不读 `TournamentUser.gsc_best`。

现在正在运行的非金羊杯赛事只有每周打卡赛：`WeeklyTournament` / `WeeklyParticipant`，名次按 `classic_score`，越小越好。一场的中文名是 `{year}年第{week}周打卡赛`。占位分是 780000，等于两局高级 240000 毫秒加五局中级 60000 毫秒都还没交。`classic_score` 仍等于 780000 的报名不计入有效人数，也不发名次勋章。当前一场的有效人数最多到过 6，以后可能变多，名次档按当届人数开，不按固定的八强。

`GeneralTournament` 没有参与现有的名次刷新。历史外部比赛在没有官方名次行之前，不自动发赛事勋章。

## 3. 模块落点

勋章是新的顶层业务，代码放在新建 app `back_end/saolei/medal`。仓库分层里，`config`、`utils` 是底层，`videomanager`、`userprofile` 是基础 app，`common` 是已有的宽业务 app，`saolei` 是根 app。勋章不写进这四层。

不放进 `videomanager` 或 `userprofile`：二者是基础 app，不应反向依赖勋章。不放进 `speedranking`：那里是 Redis 榜，放进去会把「前五」和永久解锁写在一起。不放进 `tournament`：生涯 PB 和隐藏成就不属于赛事。不放进 `common`：`common` 是跨域杂项，勋章有自己的模型和任务。

依赖方向只有勋章指向录像、用户、账号关联和赛事。反向禁止 import。`videomanager` 不知道勋章的存在。

### 3.1 现有文件只做挂接

业务判断不写进这些文件，只在这里登记新 app：

| 现有文件 | 改动 |
| --- | --- |
| `back_end/saolei/saolei/settings.py` 的 `INSTALLED_APPS` | 增加 `'medal'`。放在 `'common'` 之后、`django_cleanup` 之前，清理 app 仍保持最后 |
| `back_end/saolei/saolei/api.py` | `from medal.api import router as medal_router`，再 `api.add_router('/medal/', medal_router)`。对外路径是 `/api/medal/`，因为 `saolei/urls.py` 已经把 Ninja 挂在 `api/` |
| `back_end/saolei/saolei/urls.py` | 不新增 path。勋章走上面的 router |
| `vitepress_doc/guide/development/signals.md` | 实现信号接收器时补一条说明，与现有信号文档放在一起 |

表结构用 `makemigrations` 生成，迁移文件落在 `back_end/saolei/medal/migrations/`。测试放在 `back_end/saolei/medal/tests.py`（或同目录下的 `tests/`）。不把勋章断言写进 `videomanager/tests.py`。

运营写入走 `medal/api.py` 里用 `userprofile.decorators.staff_required` 包住的路由。不另开 Django Admin 来发勋章。

### 3.2 新 app 里的文件

app 内引用顺序遵守仓库约定：`utils -> models -> services -> api`。

| 文件 | 职责 |
| --- | --- |
| `medal/utils.py` | 刻度、比较、模式的默认开放名单。不 import 本 app 其他模块 |
| `medal/models.py` | 第 4 节的表 |
| `medal/services.py` | 按勋章类型分函数的判定、授予、撤销、重算。不要一个 `advance_stage()` 走全部类型 |
| `medal/schema.py` | 给前端的输出结构。能用 `create_schema` 的模型输出就用它 |
| `medal/api.py` | Ninja 路由。限流用 `django_ratelimit`，经 `decorate_view` 挂上，并写进 docstring 开头的无序列表 |
| `medal/cache.py` | 图鉴定义，以及每名玩家的 `medal:display:v4:{user_id}`。状态键只给名字悬停，内容是佩戴中的短记录，不参与资格比较，也不代替玩家主页详情 |
| `medal/tasks.py` | `django.tasks.task`，后端是 `django_tasks_db`。一名玩家的成就刷新、历史补发在这里入队。刷新任务记下这次碰到的录像 id。标识绑定和解绑仍由 `identifier.services` 批量更新录像和排行，提交后入队全量刷新 |
| `medal/signals.py` | 监听 `MedalDefinition` 的保存和删除以清图鉴缓存；监听 `VideoModel` 的保存和删除，事务提交后入队。不在信号里查录像 |
| `medal/apps.py` | `ready()` 里 `import medal.signals`。接法与 `speedranking/apps.py` 相同 |

BV 全收集的冻结名单、开放模式名单，都是规则数据，放 `medal/utils.py` 或随定义一起迁移进去的初始数据。不要写在 Vue 里。平台勋章的名单跟 `Platform`，不另做「全部连上」的集合，也不放梁山名册。

`MedalDefinition` 的保存和删除清掉图鉴缓存。`VideoModel` 的保存和删除在事务提交后入队 `task_refresh_player_medals`。标识绑定、解绑和比赛录像公开使用批量 `update()`，不会产生模型保存信号，因此由这些业务入口在提交后显式入队。同一名玩家已经有一条状态为 `READY` 的同类任务时，不再插入第二条；那一条跑的时候读最新录像。新插入的刷新任务 3 秒后才可被取走，这 3 秒内的后续变动并进同一条，不把开始时间再往后推。

已经有 `MedalScan` 的玩家单条录像变更直接走数据库增量，不依赖展示键。标识批量绑定、解绑，以及还没有 `MedalScan` 的玩家走完整的 `evaluate_player`。未扫描玩家打开详情时只入队历史补发；同一玩家的 READY 任务继续合并。

判定和迭代都在 `medal/services.py`。下表是每个函数允许读取的现有代码，以及谁把它叫起来。

| 隐藏成就 | `evaluate_hidden` | `VideoModel.timems`、`bv`、`level` | 录像保存。与 PB 分开函数，避免隐藏条件混进生涯最佳 |
| 纪念 | `grant_manual` | 不读成绩表。理由、操作者由 staff 路由传入 | `POST /api/medal/staff/grants` |
| 原始股东 | `evaluate_min_video_id` | `VideoModel` 的 `id`、`player_id`、`upload_time`。不看 `state`、`mode`、`level` | `VideoModel` 保存、删除，以及归属玩家变化。任务里按 id 取最小的一条 |

迭代本身是这些函数共用的写库步骤，放在 `services.py` 的 `write_stage`：按 §4.6 改写同一枚的 `stage`，或在第一次入档时插入。类型函数只负责算出新的阶段和证据，不各自复制一套插入逻辑。

## 4. 核心实体

定义、进度、解锁，三样分开存。

### 4.1 成就定义 `MedalDefinition`

一条定义描述「怎样算达成」，不含某个玩家的进度。

| 字段 | 作用 |
| --- | --- |
| `code` | 稳定主键，如 `ability.time.b`、`ability.thrp.nf`、`practice.bv_kinds.e` |
| `series` / `subseries` | 图鉴分组。`series` 存 `Medal_TextChoices.Series` 的 1～2 字符短码，如 `b`（破境）、`l`（扫雷新秀）。中文和英文名称都在前端 `medal.series`。`subseries` 可空，不再设梁山子系列 |
| `kind` | 见 4.5。评估函数按 `kind` 分发 |
| `metric` | `timems`、`bvs`、`stnb`、`thrp`、`count`、`bv_set`、`cell_mask`、`rank`、`manual` 等 |
| `direction` | `asc` 越大越好；`desc` 越小越好。时间、金羊杯用时、名次是 `desc` |
| `level` | `b` / `i` / `e` / 空。空表示跨难度或与难度无关 |
| `style` | `any` / `nf` / `fl`。只对需要分 NF、FL 的指标有意义 |
| `thresholds` | 有序阈值，刻度见第 5 节。一次性成就是长度为 1 的列表 |
| `bv_min` | 能力勋章留空。金羊杯的 BV 下限写在赛事规则里，不放这个字段 |
| `scope` | 模式集合、平台集合、赛事类别白名单、冻结 BV 名单。具体名单不塞进判断代码 |
| `hidden` | 隐藏成就为真 |
| `score_by_stage` | 各阶段分值。隐藏成就全 0，且不进入总分。分值表未定之前为空。改分值只改这里，总分按这张表重算 |
| `active` | 是否参与发放。未核实的定义保持关闭。每个 `code` 只有这一行，没有旧版本可引用 |

复合成就（三阶）另有 `depends_on`：三个子定义的 `code`，以及要求的子阶段。它自己的 `thresholds` 不解释成「再收集几条录像」。

同一 `code` 只有一行。改档是改这行的 `thresholds` 或 `scope`，然后按新规则重算已有授予。

### 4.2 玩家进度 `PlayerProgress`

每个玩家、每个 `code` 至多一行。类型不同，这一行的含义不同，但**不**把 PB 和累计塞进同一行。

| 字段 | 作用 |
| --- | --- |
| `user` | `UserProfile` |
| `definition` | 指向该 `code` 的定义。`code` 冗余一份，授予和进度都按 `code` 找 |
| `current_stage` | 按当前规则和当前进度值算出的阶段，0 表示未入档 |
| `current_value` | 非 PB 的标量进度，如累计次数、最小录像 ID；能力勋章为 `null`，不保存当前最佳成绩 |
| `extra` | 仅集合类使用：已覆盖的 BV 列表或数字格位图 |
| `best_video` | 非 PB 评估器使用的录像引用；能力勋章为 `null`，证据只保存在授予及阶段日志中 |

`current_stage` 是根据真实数据计算的自动阶段；0 表示自动判定不应授予。不存在人工覆盖时，它与授予上的 `stage` 一致。人工锁定可以令展示阶段与真实进度不同，但不伪造进度，也不连带满足其他复合勋章的条件。主页只展示未撤销授予。

### 4.3 授予记录 `MedalGrant`

一条阶梯一枚。进步、退步和规则改档都改写这枚的 `stage`，不按档再插一行。一档不够就填 `revoked_at`。

| 字段 | 作用 |
| --- | --- |
| `user`、`definition_code`、`stage` | 哪一条阶梯，以及它现在停在哪一档 |
| `scope_key` | 生涯 PB、一次性、累计：空字符串。金羊杯和单届赛事：届次或 `tournament_id`。同一条阶梯在不同届各有一枚 |
| `stage_log` | 已记录档位的最早达成节点：阶段、达成时间、证据 id；集合与三阶节点另存完整 `video_ids`。补传和改时会校正节点，同档去重并按达成时间排序。只给时间轴用，不能佩戴，也不计成第二枚勋章 |
| `video` | 可空。首次跨过该档的录像。复合成就见 `evidence` |
| `participant` | 可空。`TournamentParticipant` |
| `evidence` | 复合成就的三枚录像 id；数字格并集的覆盖快照；人工授予的说明 id |
| `granted_at` | 首次达成时间。补发时用达标录像的 `upload_time` 或赛事 `end_time`，不用任务跑完的时间 |
| `revoked_at`、`revoke_reason` | 空表示有效。撤销只填这两列。对外总分按当前 `score_by_stage`，对每枚未撤销勋章只计当前阶段一次 |

唯一约束：`(user, definition_code, scope_key)`。`stage` 不在键里。重复任务不会把同一条阶梯插成两枚。

能力勋章只保留授予及阶段日志中的证据，不维护 `PlayerProgress.best_video`。授予证据选择第一次跨进**当前阶段**的那条，补传和改时后重新核验；同档后来更佳的成绩不替换证据。跨进更高阶段时，证据改到第一次达到新阶段的那条。

### 4.4 累计贡献 `MedalContribution`

只服务局数、BV 种数、数字格并集、参赛次数、冠军次数。PB 不写这张表。

唯一约束按指标选择：

- 局数、时长、累计 3BV：`(user, code, video_id)`
- BV 种数、概率全收集：`(user, code, level, bv)`，录像 id 只是当前证据，同一 BV 再传不增加种数
- 数字格并集：`(user, code, video_id)`，一行可点亮多个 `cellN`
- 参赛、冠军：`(user, code, tournament_id)`

MySQL 不支持带条件的唯一索引，多条 `NULL` 也不互斥。贡献行因此用必填的 `source_key`，唯一约束是 `(user, code, source_key)`。录像、赛事、级别、BV 仍是可读列：局数和时长的 `source_key` 用来源录像，BV 种数用来源难度和 BV，参赛用来源赛事。

一条录像只有一个 `level`，不可能在三个难度各记一次。

### 4.5 `kind` 与类型的对应

| `kind` | 用于 |
| --- | --- |
| `pb` | 破限、神速、全能、效率（含 NF 破限 / NF 神速 / NF 全能） |
| `composite` | 三阶 NF/FL thrp。全能没有复合定义 |
| `once` | 新手一次性、收藏里的单局存在性、隐藏成就 |
| `count` | 分难度局数、BV 种数、累计 3BV、有效时长、参赛次数、冠军次数、缺陷、PR |
| `bv_set` | 概率 BV 全收集 |
| `cell_mask` | 高级数字 0–7、0–8 的跨录像并集 |
| `event_place` | 单届名次 |
| `gsc_stat` | 金羊杯最好 / 边缘 / 合计的时间档 |
| `gsc_place` | 金羊杯三组合计、单局、有效最佳的 1–20 名牌子 |
| `manual` | 纪念、活动 |
| `min_video_id` | 原始股东。阈值从易到难是 100000、10000、1000，录像 id 必须严格小于阈值 |

### 4.6 迭代还是另发一枚

同一条阶梯上，成绩变好是改写这一枚勋章的阶段，不是再插入一枚、把低档留着。初级破限从 Sub20 到 Sub15，玩家仍只有一枚初级破限，称号和徽章改成 Sub15。

**哪些用迭代**

一枚的身份是 `(user, definition_code, scope_key)`。

| 勋章 | 一枚的范围 | 阶段怎么变 |
| --- | --- | --- |
| 破限、神速、全能 | 每个难度一枚 | 生涯最佳跨入更高档时改写 |
| NF 破限、NF 神速、NF 全能 | 每个难度一枚，与不限风格的那枚分开 | 同上，只看 NF |
| NF 效率、FL 效率 | 每个难度、每种风格一枚 | thrp 跨入更高档时改写 |
| 三阶 NF 效率、三阶 FL 效率 | 各一条 | 三个难度共同达到的最高档改写这一条，不替代三个单级。全能不在此列 |
| 分难度局数、累计冠军、累计前三、跨难度冠军、缺陷数、PR 数 | 每个 `code` 一枚 | 次数跨入更高档时改写。首次冠军到十冠是同一枚的阶段 |
| 金羊杯参赛、打卡赛参赛 | 各一个 `code` 一枚 | 次数跨入更高色档时改写牌子。超过该 `code` 的最高色档后，`stage` 停在这一档，`current_value` 继续增加，展示加环并写次数 |
| 概率 BV 全收集 | 每个难度一枚 | 后一档名单包含前一档。收齐更稀的一档时改写 |
| 高级数字覆盖 | 一枚 | 先到 0–7，再到 0–8 时改写 |
| 打卡赛单届名次 | 每一周打卡赛一枚 | 这一周的名次写在这一枚上。发哪一档看当届有效人数，见 §6.4 |
| 金羊杯名次 | 每一届、每一种名次一枚 | 三组合计是一枚。单局和有效最佳按级别、指标再各一枚。金属和名次写在这一枚上 |
| 金羊杯用时 | 每一届、每一个指标一枚 | 档位定下来之后，多档也写在这一枚上 |
| 原始股东 | 每个玩家一枚 | 最小录像 id 决定档位和进度；当前档证据取合格录像中最早上传的一条，补传和改时会校正 |

**哪些另发，或没有下一档**

- 不同难度、不同系列、NF 与 FL、三阶与对应单级，各是一枚。初级破限的迭代不会吃掉中级破限，也不会吃掉初级 NF 破限。
- 新手一次性：实名、录像过审、全级别、全级别 NF、全模式、每个已验证平台、导入扫雷网。达到即一枚，没有更高档。每个平台单独一枚，没有「全部平台都绑定」。
- 收藏里互相独立的一次性：中级薄盘、高级薄盘、各难度的数字 7 和数字 8、中级时亚速。
- 新的一届赛事、新的一届金羊杯：新的 `scope_key`，新的一枚。只在已颁奖的官方名次行上发，不从赛后补传回放。
- 隐藏成就：一枚，没有阶段阶梯。
- 纪念里按次人工授予的活动、早期建设、赛事组织：一次荣誉一枚。
- BV 种数、累计完成 3BV、有效时长：还没有阶段，不发档。以后若分档，按迭代，不按每档一枚。

**迭代方法**

1. 重算进度，得到 `current_stage`。0 表示未入任何档。
2. 还没有未撤销授予，且 `current_stage > 0`：插入一行。`stage` 就是当前阶段。`granted_at` 和证据取第一次达到这个阶段的时间与录像或赛事，不取任务跑完的时间。`stage_log` 写下这一档。
3. 已有授予，且新阶段更高：改写同一行的 `stage`、证据。往 `stage_log` 追加这一档。不插入第二行。佩戴存的是授予 id，阶段变了佩戴不用改，展示名跟着新阶段变。
4. 已有授予，阶段没变，只是同档里出现了更好的录像：不改能力勋章的进度、证据、日期和日志，也不另存最佳成绩或录像。授予证据取当前阶段最早达标的录像；补传更早的达标录像或修改上传时间时，即使成绩没有改善，也要校正证据和时间。
5. 证据失效后仍够某一较低档：同一行的 `stage` 降到剩余证据仍满足的最高档，证据改成该档最早的有效记录。不把旧高档留成另一枚。
6. 证据失效后一档都不够：给这一行填 `revoked_at`。以后再次达到，清掉撤销标记并改写阶段，不另插一行。
7. 规则改档：改定义行上的阈值或名单，再按第 1 步重算。仍达到某一档，就把 `stage` 改成新刻度下的最高档。新刻度下完全不够，按第 6 步撤销。不补中间每一档，也不留旧档。
8. 计分只按这一枚的当前 `stage` 算一次，不把已经跨过的低档分数加进去。
9. 图鉴定义仍列出全部阈值，用来显示下一档。玩家拥有的列表里，这一条阶梯只出现当前阶段。时间轴读 `stage_log`。

### 4.7 佩戴

每个玩家一行 `MedalPins`。`grant_ids` 是有序的授予 id，最多 6 个。没有座次表。接口只读写这个列表。已撤销或不属于该玩家的 id 不能写入；读的时候跳过已经撤销的 id。

### 4.8 首次扫描 `MedalScan`

每个玩家至多一行。`user` 是主键。`scanned_at` 是这一名玩家第一次历史扫描完成的时间。

没有这一行，表示勋章还没有看过这名玩家已经在库里的录像、实名和绑定。摘要接口只把 `task_backfill_player_medals` 入队，不在这次请求里聚合。`evaluate_player` 跑完才写这一行。一枚都没有也要写，否则每次打开页面都会再入队。

首次扫描检查该玩家已有合格录像、实名和绑定，完成后写下 `MedalScan`，展示变化时提交后发布 `medal:display:v4:{user_id}`。展示键 TTL 300 秒；缺键仅表示展示缓存缺失，不能据此重新扫描历史。

已经扫描的玩家，录像更新按主键批量读取本次涉及的录像，一次读取有效定义及该用户的进度、授予、人工覆盖并共享。股东最小录像 ID 和未完成的新手 levels / modes 从数据库进度取得；凑齐集合后按需查证据。同档更快不改授予，补传和改时仍校正历史。退审、成绩变差、换玩家、删除录像只对受影响难度聚合；人工覆盖仍优先。

### 4.9 玩家摘要 `PlayerMedalSummary`

每个玩家至多一行，`user` 是主键，JSON只保存当前有效授予的公开事实、自然进度数值、佩戴顺序和首次扫描状态。`MedalGrant`、`PlayerProgress`、`MedalPins`、`MedalScan`仍是业务原始记录。摘要不保存人工理由、审计记录或定义副本。

`evaluate_player`、单项授予、人工决定和保存佩戴均持有同一玩家锁，在业务事务内更新摘要；内容相同则不写。佩戴列表或其中公开短记录、扫描状态改变时注册提交后发布，内部进度变化不重写名字缓存。发布及缺键回填重新取得玩家锁，读取最新摘要并在持锁期间写缓存，防止旧结果覆盖新结果。回滚不发布；摘要删除提交后删键，不改变初始化状态。

常用读取通过一次按玩家主键的查询连接玩家表与摘要表，定义、隐藏条件和分数仍按当前图鉴计算。图鉴缓存命中且摘要已建立时，`player_summary()`只有1次业务SQL。旧玩家首次读取时在玩家锁内从现有勋章表补齐摘要，不聚合录像；首次补齐和图鉴缓存未命中不属于1次查询的条件，也不计认证、会话或中间件开销。

录像或比赛参加记录删除前，勋章信号按外键找到关联玩家，取得同一玩家锁，在删除事务内移除这些摘要。下次读取从已经完成`SET_NULL`的授予补齐，避免保留已删除证据的链接；删除回滚也恢复摘要。自然进度和授予资格仍沿用现有后台评估流程。直接维护勋章原始表的脚本必须使用服务入口，或在相同玩家锁和事务内删除摘要后再由读取补齐。

### 管理员人工覆盖

`MedalOverride` 的唯一身份是 `(user, definition_code, scope_key)`。普通勋章的 `scope_key` 为空；按比赛届次区分的授予只影响所选届次。`grant` 锁定指定档位和授予日期，`revoke` 持续禁止自动授予。还没有授予记录也能先禁止发放。真实进度继续由评估器维护，人工档位不作为其他复合勋章的达成依据。

管理员必须填写原因，每次实际变更追加 `MedalOverrideLog`，保存操作、档位、授予日期、操作者和时间。恢复自动只删除覆盖记录，不删除历史；已有人工结果先撤下，提交后入队重新评估。对没有覆盖的自然授予点击恢复自动，不得将其撤销。操作与自动评估锁定同一玩家行，防止重算覆盖人工决定。

管理页面是 `/staff/medals`，只向管理员加载完整目录和操作历史。普通勋章只允许空范围，按次人工纪念和赛事类型才允许新建非空范围。全局停用仍控制公开可见性；停用或删除定义后，管理员仍能解除既有覆盖。规则变化不自动改写锁定档位，恢复自动后才按新规则升降。人工覆盖不固定计分表：总分仍使用当前定义，旧档位不在当前阈值中时没有对应分数。

操作方法、迁移和测试见 [管理员勋章决定](../../vitepress_doc/zh/guide/development/medal-overrides.md)。

## 5. 刻度与比较

阈值以整数刻度放进 `thresholds`，比较在服务端完成。

| 指标 | 刻度 | 过档 |
| --- | --- | --- |
| 时间 | 毫秒。Sub20 存 20000 | `timems < 阈值`（严格小于） |
| 3BV/s | 与 `speedranking.saolei` 的 `BVS_SCALE` 一致，×10000 | 刻度值 `>= 阈值` |
| STNB | 整数档（10、15、20…） | 该难度 `K * iqg >= 阈值` |
| thrp | ×100000。0.95 存 95000，1 存 100000 | 刻度值 `>= 阈值`。NF 比较前先要求刻度 `<= 100000` |
| 名次、次数 | 整数 | 名次是 `<=`（第 1 名优于第 2 名）；次数是 `>=` |
| 金羊杯用时 | 毫秒 | 小于阈值，且该列不是 `GSC_Defaults` 占位 |

能力勋章不维护「当前最佳」。每档的证据从所有满足该档的合格录像中按 `upload_time, id` 取第一条；同档后来更快的录像不替换证据。

隐藏成就的时间匹配也用 `timems`，不用展示字符串：

- 42.42：`42420 <= timems < 42430`
- `*8.99`：`floor(timems / 10) % 1000 == 899`（8.99 是 `[8990, 9000)`，18.99 是 `[18990, 19000)`）

## 6. 分类型设计

每一类都回答：判定输入、进度是否单调、解锁后是否永久、改档如何重算、撤销如何回滚。

### 6.1 能力勋章（破限、神速、全能、效率）

**输入。** 第 2.2 节的资格过滤之后，按玩家、难度、指标判定能够达到的最高档。全量扫描时聚合最优指标，聚合结果仅用于本次计算，不持久化最佳成绩或录像。

- 破限：最小 `timems`。不限 `right_ce`，无 BV 下限。
- 神速：最大 `bvs`。不限 `right_ce`，无 BV 下限。
- 全能：最大 `K * iqg`。不限 `right_ce`，无 BV 下限。低 BV 不会拉低 STNB，不要据此滤录像。三个难度各发各的，不要求同时达标。
- 效率 thrp：最大 `thrp`，NF 与 FL 分定义。NF 还要求 `ce >= bv`。无 BV 下限。
- NF 破限、NF 全能：档位数字与破限 / 全能相同，资格额外加上 `right_ce = 0`，无 BV 下限。NF 神速同样要求 `right_ce = 0`、无 BV 下限，末档按不标雷上限截断：初级停在 9（上限 9.09），中级停在 7（上限 7.02），高级停在 5（上限 5.38）。不把普通神速的 10、12、8、6 抄进 NF。称号也用这三套系列名，不另叫「NF 时间」。

**进度。** 每个 `code` 至多一行能力勋章进度，只保存自然档位 `current_stage`，`current_value` 和 `best_video` 均为空。尚未达到第一档时无需创建进度行。同档由 48 秒提高到 46 秒，不产生勋章业务写入；达到 Sub40 才升级。同档补传更早的达标录像或修改上传时间时，单独校正授予证据、日期和阶段日志。

**解锁与进阶。** 按 §4.6 迭代。每个难度、每种风格只有一枚。第一次入档时插入这一枚；之后只改写 `stage`。证据仍有效时这一枚保留。

**改档。** 从合格录像重新聚合并对新阈值计算自然档位，按 §4.6 改写或撤销这一枚。不按新跨过的每一档各发一枚。

**撤销。** 录像离开 `OFFICIAL`、被删、`ongoing_tournament` 重新变为真、玩家被改到别人名下、或 BV / 时间 / `right_ce` / `ce` 被改到不再合格：

1. 对录像变化涉及的难度重新聚合剩余合格录像，不依赖最佳录像指针。
2. 进度改成剩余录像能够达到的最高档（允许降档）。
3. 剩余录像仍够某一档：按 §4.6 第 5 步把这一枚降到仍满足的最高档。
4. 一档都不够：这一枚 `revoked_at` 写下原因。不物理删除，也不拆成低档的另一枚。

一条 NF 录像作废，会同时核验「不限风格」的破限/神速/全能和 NF 系列。它本来就不在 FL 进度里，不用去滚 FL。

### 6.2 新手成就

**输入。** 行为是否发生，不比成绩。

| 成就 | 输入 | 备注 |
| --- | --- | --- |
| 实名 | `UserProfile.has_realname()` | 改回「匿名」则失去 |
| 录像过审 | 存在 `state=OFFICIAL` 的录像 | 自定义级别算；不看快慢 |
| 全级别 | `b`、`i`、`e` 各至少一条过审 | 不含自定义 |
| 全级别 NF | 同上且 `right_ce=0` | |
| 全模式 | 当前开放的每个 `Mode` 各一条过审 | 名单在规则的 `scope` 里 |
| 关联某一平台 | 该 `Platform` 有 `verified=True` | 每个平台一个 `code`。未验证不算。不要求其他平台 |
| 导入扫雷网 | 至少一条 `VideoSaolei.import_video` 已过审 | 与「连上扫雷网」分开 |

一次性成就是 `kind=once`、`thresholds` 长度为 1 的特例。进度值是 0 或 1。

多阶段里，**分难度局数**是三个 `kind=count`（阶段 1、10、50、100、500、1000），只数过审且非进行中赛事的标准三级录像。**金羊杯参赛**和**打卡赛参赛**不在新手单独计数，见 6.3，图鉴指向那两个 `code`。缺陷数、合并 PR 数没有现成表，不能从仓库或玩家自报推断；在有运营写入的计数之前，这两个 `code` 不自动增长。

**单调。** 只增的是「又多了一条合格事实」。实名可以撤销；录像可以冻结。所以进度不是绝对单调。

**永久。** 证据还在、并且仍满足当前规则，就保留授予。模式名单变了就按新名单重算，不够就撤销。

**改档。** 例如局数阶梯从 100 改成 200：用 `MedalContribution` 的行数重算，按 §4.6 改写这一枚的阶段。不保留一枚「100 局」再加一枚「200 局」。

**撤销。** 删掉贡献行，重算次数或「是否仍存在」。局数阶梯按 §4.6 降档或撤销这一枚。全模式少了一个模式，就撤销「全模式」这一条一次性授予；各模式本身若没有单独勋章，不必再拆。某个平台改为未验证或绑定被删，只撤销该平台这一枚。

### 6.3 历练勋章

探索、收藏、耕耘、征途不要共用一条进度，尤其不要和 PB 共用。

**探索（`bv_set`）。** 每个难度三档：常见、少见、稀有。档是嵌套的，后一档的冻结 BV 名单包含前一档。名单是规则数据（点估计达到概率阈值的 BV），冻结后不因重新抽样改名单。抽样空洞不算缺失。名单未冻结的难度不发这一档。

进度的 `extra` 是该难度已出现过的 BV 集合，来自过审录像的 `bv`。当冻结名单是这个集合的子集时，按 §4.6 把该难度这一枚改写到对应的最稀档。同一 BV 多条录像不增加进度。另有一个 `kind=count` 的「BV 种数」，只数不同 `bv` 的个数，不要求是哪些值。种数和全收集是两行。种数在有阶段之前不发勋章。

**收藏。** 单局存在性用 `kind=once`，证据一条录像：

- 中级 `bv < 30`、高级 `bv < 100`：过审即可。这是收藏，不是能力勋章的 BV 门槛。
- 初级 `cell7 > 0`、初级 / 中级 / 高级 `cell8 > 0`。
- 中级 time sub bvs：同一条录像上 `(timems/1000)^2 < bv`。定义只建一条，放在收藏。挑战图鉴若要出现，引用这个 `code`，不建第二行进度。

高级数字覆盖是一条 `kind=cell_mask`：该玩家全部高级过审录像的 `cell0`–`cell8` 做并集。`extra` 是位图。盖满 0–7 是第一档，盖满 0–8 时按 §4.6 改写到第二档。这不是 PB，也不是「某一条录像同时有 0 到 8」。

收藏不强制 STD。方案只说有效完成、不看榜单门槛。模式集合放进 `scope`，初版为全部 `Mode`。若以后要收成仅 STD，改 `scope` 后重算。

**耕耘。** 时间、3BV/s、thrp **不新建进度**，图鉴条目指向 6.1 的 `code`。BV 种数和概率全收集指向本节已有的两行。

战力、典型时、asb、PB 奖牌数和奖牌分：站点没有可执行的公式（`pluck` 不是战力）。确认之前不建定义、不设档。PB 格上的名次颜色是 `speedranking.pb` 的展示，不是本系统的勋章，也不能回写成解锁条件。

累计完成 3BV、有效时长可以做 `kind=count`，对过审录像的 `bv`、`timems` 求和，每条 `video_id` 一条贡献。不估计站外对局。

**参赛次数。** 金羊杯和打卡赛各一个 `kind=count`，不要合成一条。一条贡献是一场已颁奖赛事，按 `tournament_id` 去重。报名未结算不算。不按录像张数加，也不按 `upload_time` 把赛后补传算进某一场。

金羊杯大约半年一届，门槛是 1、2、5，牌子是铜、银、金。必须完赛：`bt20th`、`it12th`、`et5th` 都不是占位。未完赛不写贡献。次数超过 5 时，阶段停在金，`current_value` 继续增加；展示在金牌外缘加环，环上写这个次数。不另设 6、10、100 档。

打卡赛一周一场，门槛是 1、5、10、25、50，牌子是锡、赤铜、铜、银、金。只计已颁奖且 `classic_score < 780000`。超过 50 时同样停在金并加环，环上写 `current_value`。

新手里不再另建参赛计数。详情就是该 `code` 的贡献行，不另存届次名单。金羊杯的名次牌、打卡赛的名次勋章和冠军累计，仍是别的 `code`，不和参赛次数混在一条阶梯里。

打卡赛冠军不计入正式赛、社区赛或邀请赛的冠军累计。那些级别现在没有正在运行的比赛，对应 `code` 先不启用。

**单调与回滚。** 贡献只在新的合格录像或新的已颁奖赛事出现时增加。录像作废或赛事取消则删贡献并重算；次数可以下降。下降后按 §4.6 把这一枚降档，一档都不够才撤销。规则改档同样按新阈值重算，不够则撤销。

### 6.4 赛事勋章

**输入。** 只复制赛事在 `AWARDED` 之后已经写下的名次和金羊杯列。不读录像的 `upload_time`，不把赛后补传自行算进某一届，也不为没有官方名次行的历史比赛补排名。

**打卡赛单届名次（`event_place`）。** 一届已颁奖的打卡赛一条授予，`scope_key` 为 `tournament_id`。有效人数 N 只数 `classic_score < 780000` 的选手。勋章名次在这些人里按 `classic_score` 从低到高排，不使用把占位分也排进去的 `rank`。

发档看 N，保证这一档的人仍是少数：

| N | 发放 |
| --- | --- |
| 1–2 | 不发名次勋章 |
| 3–5 | 第 1 名：冠军 |
| 6–9 | 第 1 名冠军，第 2 名亚军 |
| 10–15 | 再加上第 3 名季军 |
| 16 及以上 | 再加上第 4–8 名里、名次满足 `名次 × 2 < N` 的八强 |

当前最多 6 人，所以一届最多冠军和亚军。季军、八强、前 10% 在人数不够时不出现。前 10% 要等 N ≥ 20，并且只发给名次在第 4 名到 `floor(N/10)` 之间的人；这个区间空着就不发。人数以后变多，同一套表自动放开后面的档，不用改称号。

**打卡赛冠军累计（`count`）。** 只数上面发出了「冠军」的那些周。阶段是 1、5、10、25，同一枚改写。不叫三冠王、十冠王，也不并进正式赛冠军。不设打卡赛的累计前三和跨难度冠军。

**金羊杯用时（`gsc_stat`）。** 九个列各是一个定义（或每个难度一个定义、三个指标为三个 `metric`）。只读已颁奖届次上、且不等于默认占位的毫秒值。档位整数未定，`thresholds` 先空，不发档。`scope_key` 为届数 `order`，每一届保留自己的授予。比较方向为越小越好。

**金羊杯名次牌（`gsc_place`）。** 只覆盖完赛选手中的 `rank` 1–20。1 金、2 银、3 铜、4–10 赤铜、11–20 锡。赤铜是哑光暗红，锡是哑光青灰，都不带金色，亮度也不超过金、银、铜。21 名及以后没有这套牌子。未完赛不发该届任何牌子，包括以后才填上的用时档。

三组合计在完赛选手之间按 `t37` 从小到大排，不用混有未完赛选手的 `TournamentParticipant.rank`。每一届一条，`scope_key` 只含届数 `order`。

单局和有效最佳是另外的名次，不替代三组合计，同样只统计完赛选手。每个级别、每个指标各比一次，指标是时间、3BV/s、STNB。单局取该玩家这一条最好的合格录像。有效最佳初级取 20 局、中级 12 局、高级 5 局，三个指标各自选自己最好的这 N 局再相加：时间和越小越好，3BV/s 与 STNB 和越大越好。完赛之后这三个级别都已填满，时间总和里不再加占位。合格条件与 `refresh_gsc_scores` 相同：过审、标准模式、BV 不低于 `B_BV_MIN` / `I_BV_MIN` / `E_BV_MIN`（10 / 30 / 100）。时间还要快于对应占位。STNB 用 `iqg * K`（36 / 162 / 435）。

时间单局对应已有的 `bt1st` / `it1st` / `et1st`，有效时间对应 `bt20sum` / `it12sum` / `et5sum`。3BV/s 和 STNB 现在没有列，也没有名次。这两项要等金羊杯刷新在颁奖时把数值和 1 起的名次写下来，勋章才复制。不在勋章 app 里扫录像现算，也不手改迁移去加列。每一项的 `scope_key` 含届数、级别、指标，以及「单局」或「有效最佳」。主页默认展示时，三组合计优先于有效最佳，有效最佳优先于单局。

**单调。** 单届授予不随玩家后来打得更好而升级；下一届是新的 `scope_key`。累计冠军次数随新的冠军赛事增加。金羊杯用时档相对「该届成绩」固定，不跟生涯 PB 走。

**永久。** 届次结果保持有效就保留。

**改档。** 打卡赛的人数门槛写在规则里。以后若把「N ≥ 6 才发亚军」改成别的人数，按已保存的当届 N 和名次重算，并按 §4.6 改写或撤销该周这一枚。金羊杯用时整数档刚被填上时，同样只改写该届这一枚。

**撤销。** `rank` 在颁奖后被官方重刷，或赛事离开 `AWARDED`：按新名次重写该 `scope_key` 的授予。名次变差导致不再落在任一档里，则撤销。赛后补传没有进入官方名次行时，不改、不撤。不根据录像是否仍在个人 PB 里推断赛事勋章。

### 6.5 特殊勋章

**挑战。** 只收「还没有对应能力档」的复合或极端目标。三阶 thrp 是 `kind=composite`。不建三阶全能。中级 time sub bvs 引用收藏里的那一条。NF 高水平若已经是效率定义中的一档，就不再复制。

复合成就没有自己的录像计数。`current_stage` 由三个子进度决定：三个难度都达到某一共同阈值，这一条复合勋章就改写到该档。证据是三枚录像 id，写在 `evidence` 里。一条录像只有一个难度，天然不会占两个坑。子进度之一被撤销后，重算复合档；按 §4.6 降到仍同时满足的最高档，一档都不满足则撤销这一条。子定义自己的授予按 6.1 处理，不连坐。

三阶的档写在这一条复合定义的 `thresholds` 里，不是每个整数档再做一个 `code`，也不是「单级有的档自动都有三阶」：

- 全能不设三阶。初级、中级、高级各有自己的授予，三个难度同时达标也不再合成一枚。
- 三阶 NF thrp：0.9、0.95、1。其中 1 是三个难度都有合格 NF 且 thrp 达到 1。
- 三阶 FL thrp：只有 1、1.2、1.5。0.5–0.8 以及高于 1.5 的档只存在于单级定义。

**隐藏（`kind=once`，`hidden=true`）。** 任一过审录像满足 `timems` 区间，或初级 `bv = 1`。不限模式。不计分，`score_by_stage` 为 0，总分跳过它们。

未解锁时：图鉴接口不返回该定义，不返回条件，也不返回「有一条隐藏成就」。已解锁后：返回注解（为什么这是成就），并允许佩戴。佩戴上限 6，**包含**已解锁的隐藏勋章。

改匹配规则后重算是否仍满足，不满足就撤销。证据录像作废则重新搜索其他录像；找不到就撤销，于是它再次从该玩家的图鉴中消失。

### 6.6 纪念勋章

**输入。** 运营或以后接入的、已经核对过的事实。不是录像聚合。

活动、早期建设、赛事组织：`kind=manual`。授予必须有理由、日期、操作者（`UserProfile`）。没有录像 id 也可以。撤销同样记录操作者和原因。

缺陷被修复、PR 被合并若要做新手阶段，计数只能由运营写入 `MedalContribution`（或以后单独的事实表），状态必须是已修复或已合并。玩家只提交未接受的不计。纪念图鉴可以挂同一个 `code`，但不能再自动发一枚「每个 PR 一枚」的纪念勋章。一次性的贡献荣誉仍用 `manual`，与计数阶段分开。

**单调。** 人工授予不随成绩波动。次数类是否下降，只随运营更正事实。

**永久。** 直到被运营撤销或对应事实被核销。

**改档。** 缺陷 / PR 的 1、5、20 若调整，按已记录的次数重算阶段，不够则撤销。纯人工勋章没有阈值，不因规则重算而消失。

**撤销。** 只走人工撤销或事实核销，不因为玩家后来的 PB 变化而回滚。

### 6.7 原始股东

**输入。** 该玩家名下仍在库里的全部 `VideoModel`，取 `id` 最小的一条。不看出审状态、模式和难度。删除或改归属之后，这条最小值可以变大。

**阶段。** `kind=min_video_id`，`code=shareholder.origin`，方向 `desc`。阈值从易到难存成 `100000`、`10000`、`1000`，录像 id 必须严格小于阈值。id 为 100000 或更大时一档都不够。对外称号是系列名加阶段：原始股东·100000、原始股东·10000、原始股东·1000。

**证据。** `current_value` 和 `best_video` 始终记录玩家的最小录像 id。授予证据在满足该档 `id < threshold` 的录像中按 `upload_time, id` 选择最早一条，日期与该证据同步；它可以与最小 id 的进度录像不同。补传、改时或证据失效后重选，`granted_at` 取仍有有效证据的已记录档位中最早的达成时间。第一次计算只记下当前档，不回放中间档。

**触发。** `medal.signals.enqueue_medal_refresh_on_video` 在录像保存或删除后、事务提交时入队。保存时若录像上已有旧的 `player_id`，旧玩家也入队。信号里不查录像。定义行由 `ensure_shareholder_definition` 在读图鉴或重算时补上；已经存在的阈值和开关不会被写回。

## 7. NF / FL 与三阶在数据上的形状

效率相关的定义键是 `(metric, level, style)`，不是一条「效率」进度。

| 录像 | 更新的 PB |
| --- | --- |
| `right_ce = 0`，且 `ce >= bv` | 破限、神速、全能（style `any`）；NF 破限、NF 神速、NF 全能；NF thrp。不更新 FL thrp |
| `right_ce > 0` | 破限、神速、全能；FL thrp。不更新任何 NF 定义 |
| `right_ce` 为空，或 NF 但 `ce < bv` | 不更新 thrp。时间 / 3BV/s / STNB 是否更新，仍看它是否满足那些定义自己的资格 |

这和现有榜不同：`speedranking` 把 NF 录像同时放进普通榜和 NF 榜。勋章的 thrp **不能**沿用那个双重进入。

三阶不增加第四个计数器。例如「三阶 NF thrp 1」依赖 `ability.thrp.nf.b`、`.i`、`.e` 三行进度都已达到阈值 1。授予上的 `evidence.video_ids` 是三个难度首次达到目标档位的录像，完成时间取三者上传时间的最大值；不采用后来刷新最佳的录像时间。日志节点也保存整个证据集，因此非最后完成的分项改时后同样可以触发校正。凑不齐三枚就撤销这一条复合授予。

同一 `video_id` 在 `MedalContribution` 里对同一个 `code` 唯一，避免历练重复累计。它作为多个 PB 定义的证据是允许的，因为那些定义不是在做加法。

## 8. 授予流水线

触发只来自已经落库的事实。勋章评估放进后台任务，页面请求读取已有结果并按需入队。「请求 2 秒、事实提交后 5 秒更新勋章」是性能目标，尚未通过生产环境压测验证，不能作为时延保证。`on_commit()` 只推迟回调到提交后，入队及其去重查询仍在当前进程同步执行。

工人使用现有 `db_worker_robust`。玩家刷新优先级为 1，新任务 3 秒后才可执行；历史补发为 0，创建后即可执行。合并不推迟原有较早时间；异常过晚的刷新任务提前到当前 3 秒延迟上限，历史补发提前到当前时间。READY 任务在合并查询期间被 worker 领取时，另排一条 READY 任务承接本次变更。任务能否及时执行还取决于工人是否运行、队列积压和正在执行的任务。优先级不能中断已经运行的长任务。

### 一次刷新打几次库

同一玩家同类 `READY` 任务合并；去重在数据库按玩家参数过滤，并通过玩家行锁串行化查询和入队。刷新任务读取该玩家当前数据，复用进度和授予映射，比较字段后集中 `bulk_create` / `bulk_update` 有变化的进度。`MedalScan.scanned_at` 保留首次完成时间，重复刷新不更新该时间。评估期间也持有玩家行锁，同一玩家的并发入队可能等待该事务完成。

工人不读取 Redis。没有 `MedalScan` 或显式全量触发时完整评估该玩家；普通增量复用数据库状态。定义一次读取供各评估器共用，股东和新手集合不再维护 Redis 计算副本。缺键批量读摘要回填；Redis 故障不阻断业务计算，发布失败尝试删旧值并由有限 TTL 与后续读取恢复。

普通已扫描用户、各勋章均无变化且无需补齐历史时，含提交回调的刷新为 6 次 SELECT：用户及摘要/佩戴/扫描、当前录像、有效定义、进度、授予、覆盖各一次，无勋章业务写入或 Redis 访问。补传、升档、改时和证据失效仍按需增加历史查询。佩戴中的补传会发布名字缓存，`test_incremental_queries.py` 中的固定 fixture 断言 11 次，包含发布前最新摘要读取；同一补传若未佩戴则不发布。此计数不包含录像保存、任务入队和任务框架状态写入，不作为其他场景的固定查询次数或生产耗时承诺。

尚未实现的优化包括按录像变更游标进行增量归约，以及贡献、授予的统一批量写入。是否增加录像索引应结合查询计划和实际数据量验证，迁移仍由 Django 生成。

补发按指定玩家入队，优先级低于普通刷新。授予的唯一约束是 `(user, definition_code, scope_key)`，重复任务不会把一条阶梯插成两枚。

### 标识绑定与解绑

`identifier.services.bind_identifier` / `unbind_identifier` 保留批量修改录像 `state` 的路径；现有排行、最新队列等更新仍在这些业务函数中完成。仓库没有 `identifier.tasks.task_sync_identifier_videos`，不能把排行同步描述为已实现的后台任务。

勋章刷新在批量操作的事务提交后，按受影响玩家去重入队，不为每条录像单独评估。任务执行时读取数据库里的最新资格，绑定后可发放、解绑后可撤销。比赛录像公开同样在批量清除 `ongoing_tournament` 后入队相关玩家。

### 谁触发

当前实现了录像保存/删除、实名变更、扫雷网绑定、标识绑定/解绑、比赛录像公开和首次访问的刷新入口。下表中的赛事颁奖、贡献累计和其他扩展事件是后续接入目标，不能视为已经实现的自动发放路径。

| 事件 | 来源 | 重算范围 |
| --- | --- | --- |
| 录像创建或保存 | `VideoModel` 信号。关心 `upload_time`、`state`、`ongoing_tournament`、`player_id`、`level`、`mode`、`bv`、`timems`、`right_ce`、`ce` 相关列、`cell0`–`cell8` | 旧玩家与新玩家身上，这条录像可能碰到的 `code`。不是全站 |
| 录像删除 | `post_delete` | 原玩家的相关 `code` |
| 实名变更 | `UserProfile._realname` 保存信号 | 入队玩家刷新，重算实名一次性成就等已接入规则 |
| 标识绑定、解绑 | `identifier.services` 批量更新后提交回调 | 按受影响玩家去重入队 |
| 比赛录像公开 | `reveal_videos_for_tournament` 批量更新后提交回调 | 重算相关玩家的生涯 PB |
| 平台绑定变为已验证、改为未验证或删除 | `AccountLinkQueue` | 该平台这一枚。不重算其他平台 |
| 扫雷网导入指向了过审录像 | `VideoSaolei.import_video` | 导入成就，以及这条录像本身触发的能力 / 历练 |
| 赛事成绩与名次刷新，且状态为已颁奖 | 现有结算任务末尾，不另排一轮 | 该届的赛事勋章、金羊杯档、对应参赛次数里这场的贡献 |
| 赛事取消或名次被官方改写 | 同上 | 该届授予的核验。只跟官方新行，不按补传录像的上传时间回放 |
| 运营授予或核销 | 管理接口 | 指定的 `manual` 或计数 |
| 规则变更 | 管理任务 | 改定义上的阈值或名单，按当前规则重算，改写或撤销这一枚 |
| 打开摘要，且该玩家还没有 `MedalScan` | `GET /players/{user_id}` | 入队这一名玩家的历史扫描。请求里不聚合。工人跑 `evaluate_player`，看库里已有的合格录像、实名和绑定 |

未颁奖的赛事只刷新了 `rank` 时不发勋章。进行中的赛事录像（`ongoing_tournament=True`）不进入生涯 PB；批量清除标记时必须显式入队，不能依赖模型保存信号。

只有缺少 `MedalScan` 或完整刷新触发才走完整评估。展示键缺失、过期或 Redis 故障不会改变数据库增量路径。

已经有状态行时，首次达标或升档直接更新自然档位，不额外聚合最佳成绩。同档内更好的普通后续录像不更新能力勋章。发布摘要前由 `_refresh_video_history` 校正录像派生的日期、证据和日志：新建或升降档、任一历史证据被修改、以及更早的达标候选都会触发查询；更晚的同档录像跳过历史查询。全量 `evaluate_player` 核验所有已接入的录像派生勋章，并可修复旧版本留下的日期。

每次校正只处理已经记录过的档位和当前档，不补造中间档。每档按当前合格录像重选最早证据，同档只保留一个节点，按时间排序，同一时间按档位从低到高排序。规则中已经删除的档位或不再有有效证据的节点移除。`granted_at` 取这些节点的最早时间，当前授予证据对应当前档；上传时间改早、改晚都能校正。集合类的新手勋章按每个级别或模式的最早录像计算最后完成时间，证据和节点保存完整 `video_ids`。人工覆盖的日期、证据和日志不受自动校正影响，人工操作审计仍保存在 `MedalOverrideLog`。

## 9. 查询、补发与重算

**读路径**读取`PlayerMedalSummary`，再结合共享图鉴生成响应；缺少摘要时才从勋章原始表补齐，不在个人主页请求里对`VideoModel`做聚合。服务层返回当前摘要及`scan_pending`；没有`MedalScan`时由API入队`task_backfill_player_medals`。侧栏与勋章页复用同一玩家的摘要和进行中的请求；扫描尚未完成时有限重试，完成后自动更新，达到重试上限则提示稍后重试。`scan_pending`只表示首次扫描是否完成，不代表每次后续刷新任务的状态。

**补发**是一个可重复执行的指定玩家任务，与普通刷新调用同一个 `evaluate_player()`，覆盖目前接入的股东、新手、PB 和复合勋章。赛事勋章等尚未接入的评估器不在当前扫描范围内。对每个已接入的 `code`：

- 算出进度和当前阶段；
- 还没有这一枚，且阶段大于 0：插入一枚，`granted_at` 取第一次达到该阶段的证据时间，`stage_log` 只记这一档；
- 已有未撤销的一枚：把 `stage` 改写到当前阶段，核验已记录各档的最早有效证据，校正 `granted_at`、当前证据和 `stage_log`，同步重建摘要与状态缓存。

因此补发跑两次不会把首次时间改成第二次任务的时间，也不会把一条阶梯刷成多枚。撤销行还在，唯一键会挡住再插入；证据再次成立时清掉 `revoked_at` 并改写阶段。

升级后已经扫描过的玩家可通过 `POST /api/medal/refresh`，或管理员 `POST /api/medal/staff/rebuild`（指定 `user_id`）入队全量重算，修复旧日期；后台工人完成后生效。`enqueue_medal_backfill` 命令只面向尚无 `MedalScan` 的玩家，不用于修复全站已有授予。

**规则变更**不是另一套发放。改定义上的阈值或名单之后，需要调用玩家自己的刷新接口（入队，限流）或管理员针对该玩家的补发接口。评估会按当前规则改写阶段，一档不够就撤销；保存定义仅清图鉴缓存，不会自动扫描全站玩家。

**证据重算**从证据录像或赛事行出发，走同一条升降和撤销。不要为改档单独做「只改阶段、不撤销」。

个人主页和图鉴解释未撤销授予的当前 `stage`。时间轴的节点是 `stage_log`，不是进度行的更新时间。一次性勋章没有阶段变迁时，时间轴用 `granted_at`。

索引放在勋章表上：`(user, definition_code)`、`(video)`、`(participant)`、`(user, revoked_at)`。若补发时按玩家扫描录像过慢，再给 `VideoModel` 增加 `(player, state, level, mode)` 索引，仍由 Django 生成迁移，不手写。

## 10. API

Ninja，挂在 `/api/medal/`。除管理员接口外全部限流。装饰器用 `decorate_view` 包 `django_ratelimit`，并在 docstring 开头用无序列表写明。管理员接口用现有的 `staff_required`，不限流。

不提供任何「提交成绩 / 提交 BV / 提交数字格」的写接口。

| 方法与路径 | 谁 | 限流建议 | 行为 |
| --- | --- | --- | --- |
| `GET /catalog` | 匿名 | `ip`，与现有榜单同量级，例如 `5/s` | 已启用的定义。隐藏且调用者未解锁的不出现。不含条件文案 |
| `GET /players/state?ids=1,2,3` | 匿名 | `ip`，`5/s` | 批量返回佩戴中的短记录，最多 100 个 id，顺序与佩戴列表一致。只含 `stage > 0` 且未锁定的条目。没佩戴时 `grants` 为空。命中 Redis 时不查 MySQL。缺键批量读数据库摘要并回填；未扫描玩家返回空列表，不扫描录像 |
| `GET /players/{user_id}` | 匿名 | 同上 | 该玩家的详情：各系列当前阶段、下一档、总分（不含隐藏）、佩戴、`video_id`。隐藏仅当已解锁。没有 `MedalScan` 时入队历史扫描，不在这次请求里计算。玩家主页继续用这一次详情，名字悬停不调用它 |
| `GET /players/{user_id}/grants` | 匿名 | 同上 | 未撤销授予的分页。默认每页不大，避免单次响应过大 |
| `PUT /pins` | 登录本人 | `user`，例如 `30/m`，`block=True` | 提交至多 6 个授予 id，顺序即左侧顺序。已解锁隐藏可以入选。不接受座次、星号或绰号 |
| `POST /refresh` | 登录本人 | 同上，更严，例如 `1/m` | 只入队该玩家的重算，不入队全表扫描 |
| `POST /staff/grants` | 管理员 | 无 | 人工授予并锁定指定档位。体：`code`、`user_id`、理由、日期、档位及可选范围；纯人工类型可省略档位 |
| `POST /staff/grants/{id}/revoke` | 管理员 | 无 | 人工撤销并持续禁发，必填原因 |
| `POST /staff/rebuild` | 管理员 | 无 | 入队补发或证据重算，参数指明范围 |
| `GET /staff/catalog` | 管理员 | 无 | 完整目录，含隐藏和停用定义 |
| `GET /staff/players/{user_id}` | 管理员 | 无 | 当前授予、人工覆盖及最近 50 条操作历史 |
| `POST /staff/overrides` | 管理员 | 无 | 强制发放、持续禁发或恢复自动；恢复自动在事务提交后入队 |

输出结构放 `schema.py`。直接对应单表的用 `create_schema`。摘要是手写 Schema，因为一条响应要拼进度、授予和座次。

错误沿用项目已有的响应习惯：未登录、不是本人、佩戴超过 6 枚、授予不属于本人、对未解锁隐藏的探测。不要为了「有没有隐藏成就」返回不同的 404 以外的提示；未解锁的隐藏在目录里就是不存在。

## 11. 前端只需要的 DTO

文件放在哪一节见 §3.4。这里只规定接口返回给页面的字段。

客户端不要用 `VideoAbstract` 的 `bvs`、`stnb`、`thrp` 自行判断解锁。那些 getter 会用到本地 STNB 系数。

### 状态

`GET /players/state` 给名字悬停。每个玩家：

- `user_id`
- `grants`：`code`、`stage`、`timestamp`（Unix 秒）、`scope`、`tournament`、`rank`

展示键只含佩戴中的已授予短记录，顺序与 `pin_ids` 一致，不保存 value、levels、modes、locked 或录像证据。没佩戴时缓存 `{"grants":[]}`。缺键批量读取数据库摘要；未扫描玩家返回空列表，详情接口仍负责首次补发。

### 详情

`GET /players/{user_id}` 只给玩家主页。摘要里每个已展示的勋章：

- `code`、`series`、`subseries`、`stage`、`stage_count`
- `direction`（`asc` 或 `desc`）
- `current_value`、`next_threshold`（使用第 5 节的整数刻度；能力勋章的 `current_value` 固定为空，没有下一档时 `next_threshold` 为空）
- `granted_at`、`video_id`（可空）、`tournament_id`（可空）、`rank`（可空）
- `hidden`、`annotation`（仅已解锁的隐藏成就）
- `score`（隐藏为 0）

佩戴：长度 ≤ 6 的授予 id 列表。
总分：非隐藏、未撤销授予按当前分值表相加，每枚只计当前 `stage` 一次。分值表未定之前为 0。

图鉴按 `series`、`subseries` 分组。未解锁的非隐藏项带条件说明（条件文案由 `code` 对应 i18n，数值用 `thresholds`）。未解锁的隐藏项不在列表中。

## 12. 明确不做

- 不实现 IOE 勋章，也不做 Corr 勋章。两列仍只是录像统计。
- 不恢复 NT20.5，不做动态定阶小数表，不把锚点前 20 的均值写成勋章档。
- 不做梁山分，不做现任、历史最高或任何全站历史名次。不从录像回放某一届结束时的排名。
- 不把「进入某指标 TOP5」或 `speedranking.top` 的排名当作任何勋章的条件。
- 不把同一条阶梯的每一档都做成一枚勋章。进阶按 §4.6 改写阶段。
- 不从客户端另收 BV、数字格、thrp、完成度、局数。
- 不用 `UserMS` 的录像计数器，不用前端不完整的 `MS_Mode`，不用 `ranking` app 的草稿表。
- 不在规则未定时实现 asb、战力、典型时、PB 奖牌分的档位。
- 不手写迁移脚本。本文也不包含迁移文件。
- 佩戴接口不接受超过 6 个，也不接受未解锁或已撤销的 id。

## 13. 方案里仍待验证的点

下列各项以方案第十二节为准。未核实的不建定义，或定义保持 `active=false`，不发奖。核实之后直接改这一行的 `thresholds` 或 `scope`，再按 §4.6 重算。改档和证据失效都会降档或撤销。不复制定义行，不记录发出时的规则版本。

| 待验证 | 架构上怎么留口 |
| --- | --- |
| STNB 的完成度、资格是否就是现公式 | 现在固定用 `iqg * K`（36 / 162 / 435），不用前端本地系数。完成度若以后要进入公式，改比较后重算阶段。进度仍保存 `iqg` 与录像 id |
| 破限 / 神速 / 全能的整数档来自全体录像还是每人一条 PB；Sub90、Sub40 是区间估计 | 档位只活在 `thresholds`。改列表后重算。不再满足的档撤销 |
| 效率只按 thrp；1 以下各档可能按 OpenMS 的 thrp PB 再平移；FL 顶尖档来自站外榜 | NF 与 FL 已是不同 `code`。平移只改对应 `code` 的 `thresholds` 再重算。NF 上限 1 写在资格里（`ce >= bv`），不做成可以调到 1 以上的阈值 |
| 时间、3BV/s、NF、thrp 是否都有可靠的达标证据 | 不读排行榜 Redis，不保存另一套生涯最佳。全量扫描聚合过审录像判定档位，普通增量只比较自然档位。某指标生成列大量为空时，该 `code` 不启用，不先发 |
| BV 全收集的具体整数名单（初级 5% / 1% / 0.1%，中高级 1% / 0.1% / 0.01%；尾部样本不够） | 名单写在 `scope`。未冻结则该档不启用。换名单后重算，盖不住新名单就降档或撤销 |
| asb、战力、典型时、奖牌数、奖牌分 | 没有定义行，避免空档被刷出来 |
| 42.42 与 `*8.99` 是否按百分秒截断、样本是否足够少 | 匹配规则写在隐藏成就的 `scope`（第 5 节的毫秒区间）。改区间后重算，不满足就撤销。未解锁者不看到这条 |
| 打卡赛以外的非金羊杯赛事、以及历史周赛要不要补发 | 现在只认已颁奖的打卡赛和金羊杯。新的赛制是新的 `code`。打卡赛人数门槛在 §6.4，人多了自动放开季军和八强 |
| 主页展示个数、图标、通知、时间轴的界面 | 个数已定为 6，含已解锁隐藏。图标和通知不在本架构里定。时间轴只约定数据是授予的 `granted_at` |

改档只做这一件事：改这一行的 `thresholds` 或 `scope`，入队重算。不复制定义，不记录发出时用的是哪一档规则。
