# Path 效率榜

## 规则与缓存

- 小榜为 `{b/i/e/sum}_{path/cpath/epath}`，共十二项，均越小越好，默认按 `sum_epath` 排序。
- 准入：三级别 STD、OFFICIAL、非隐藏比赛录像，包含 NF，无 BV 门槛。
- 三个指标独立选择最佳录像；有限非负数有效，0 有效，NULL 独立排除，不为历史缺失补零。
- 个人同分保留原录像；重建按 `id ASC` 稳定选优；用户同分按 Redis member 顺序，不编码用时或上传时间。
- 每个指标的 sum 必须三级别齐备，不补缺省值；三个级别的最佳录像可以不同。

`effranking:path:records` hash 以用户 id 为 field，保存九项 `{b/i/e}_{path/cpath/epath}`，各为 `null` 或 `{value, video_id}`。`value` 保留按每格 16px 归一化的原始距离，录像 id 指 `VideoModel.id`。三个 sum 从单项计算，不重复保存。十二个 `effranking:path:{stat}` zset 使用用户 id 作 member、原始未舍入数值作 score，升序读取；展示和个人比较不从 score 恢复数据。

接口位于 `/api/effranking/path`，复用效率榜的查询、管理员修复和事务约定。排行返回完整九项；个人另返回十二项名次。管理员修复单项回源并重算同指标 sum；修复 sum 仅使用 hash。API 参数与响应见 Ninja 文档。

## 更新路径

- `videomanager` 的旧值捕获包含 `path/cpath/epath`；Path 仅监控这三个指标及分类、准入字段，不依赖 BV、用时或 NF。
- 新增和改善直接比较缓存；仅持有纪录变差、失效或删除时按需查库补位。玩家、级别迁移同时处理旧分类和新分类。
- 批量加入按玩家分段，每指标一条窗口查询，在 `(player_id, level)` 内按指标、id 选优。
- 批量移除先用固定录像 id 的 queryset 与缓存持有 id 求交集，再按指标合并真正受影响的玩家/级别，最多三条补位查询，不逐用户查库。
- 仅提交改变的 hash 与 score；单项变化只影响其自身及同指标 sum。仅录像 id 变化时不必重写 zset。

保存、删除与批量操作均复用效率榜提交后总入口，共用 Redis 读写 pipeline，不新增锁或重试。事务、异常日志、临时榜发布机制及部署暂停范围见[效率榜 README](../README.md)和[管理命令文档](../../../../vitepress_doc/zh/guide/development/management-commands.md#rebuild-eff-ranks)。首次部署执行 `rebuild_eff_ranks --ranking-name path`，仅替换 Path 的十三个 key；本地快照初始化也会重建本榜。

排行按初级、中级、高级、合计四组显示 Path/CPath/EPath；个人页在效率表中与 Thrp、TPE 合并，以指标为行、四个级别分组为列。前端将原值除以 16，以格为单位显示三位小数，title 保留换算后的完整精度，无色阶；单项各自链接最佳录像，sum 不生成链接。管理修复结果及新闻也按格显示，不改 API 或 Redis 的原始值。新闻覆盖十二项首次取得及原始值严格降低，sum 的 `video_id=null`，`count/timems=null`。移除、管理员修复及全量重建不发新闻。前端路由与组件职责见[排行榜 README](../../../../front_end/src/views/RankingView/README.md)和[个人主页 README](../../../../front_end/src/views/UserView/README.md#效率纪录)。

## 索引决策

首版不新增字段或索引，沿用玩家外键及 `(state, player, level)`。正常新增/改善不查询候选，公开读榜只用 Redis；重点测量的是纪录失效补位和批量窗口选优。

2026-11-25 完成三组对照，I1/I2 仅用于测量，未作为模型迁移：

| 方案 | 索引 |
| --- | --- |
| I0 | 现有索引 |
| I1 | 共享过滤索引 `(state, player_id, level, mode, ongoing_tournament)`，仍需排序 |
| I2 | 三指标各一条 `(state, player_id, level, mode, ongoing_tournament, metric)` |

保留现有索引将 `state` 放首列的约束，避免改变玩家外键校验使用的索引及状态更新的锁等待。后续若小批量补位成为瓶颈，再为实测受益的指标生成 I2 迁移，不固定 `FORCE INDEX`，不为缓存 sum 建数据库索引。

### 测量数据与环境

数据来自 `https://openms.top` 的公开快照 `back_end/saolei/tmp/public-data-path-20261125`，247 用户、408,322 录像、2,286 标识，已通过 `validate_snapshot`。旧快照的 `cpath/epath` 缺失；本次通过 `query_by_id` 取得三字段和 Pluck，不把历史 NULL 补成 0。合格录像 406,851 条（初级 223,697、中级 110,035、高级 73,119），涉及 164 用户、483 个用户/级别组合。`path` 全部有效；`cpath/epath` 各有 327 条历史缺失（0.0804%），三项各有 1 个有效零值。

单个 `(用户, 级别, 指标)` 候选数中位 314、p95 3,274、最大 11,122；最大样本分别为用户 60 初级、172 中级、26 高级。六条真实录像（id 1、850、5000、20000、100000、250000）的 parser 输出与生产详情三字段逐一相等；另五条 2022 年录像的生产快照与详情均为 NULL，不是 0。

本地 MySQL 8.4.11、Django 6.1.3；独立库 `saolei_path_bench` 按现有模型 DDL 载入全部录像，I1/I2 只在连接局部临时表加索引，未改生产库或共享本地业务库。下表为 20 次热查询中位数（ms）：

| 场景 | I0 | I1 | I2 |
| --- | ---: | ---: | ---: |
| 单用户补位，中位候选样本 | 1.1–2.6 | 1.4–2.5 | 0.43–0.75 |
| 单用户补位，p95 候选样本 | 4.3–7.9 | 4.3–6.9 | 0.55–0.90 |
| 单用户补位，最大候选样本 | 11.5–37.1 | 10.2–28.0 | 0.46–0.82 |
| 同一录像三项补位合计 | 41.8 | 30.5 | 1.6 |
| 1 用户窗口（三项） | 353–398 | 333–348 | 54–58 |
| 10 用户窗口（三项） | 2,589–3,068 | 1,982–2,036 | 399–406 |
| 100 用户窗口（三项） | 3,789–3,843 | 3,284–3,304 | 2,791–2,846 |

首次与热查询差异不大：单用户首次中位 10.9/9.4/2.5 ms（I0/I1/I2），热查询中位 7.5/6.3/0.65 ms；100 用户首次基本等同于热查询。`EXPLAIN ANALYZE` 显示 I0 用 `video_state_player_level_idx` 扫描最多 3,745 行后排序，I1 仍需排序，I2 用覆盖索引只读 2 行且无排序；但 100 用户时三个方案都退回约 397,592 行全量扫描与窗口排序，I2 不再有数量级收益。

导入全部录像及三字段约 72.5 秒。I1/I2 创建分别约 1.6/3.3 秒，增加约 13.5/52.7 MiB；1,000 行状态更新由 54.8 ms 增至 99.4 ms，三字段更新由 26.4 ms 增至 51.4 ms。现有索引下单录像补位最坏约 37 ms，三指标全量重建约 11 秒，均可接受；I1 收益不足，I2 小批量收益暂不足以抵消写入与空间成本。

这些是本地热缓存查询耗时，不代表生产 API 延迟保证；公开元数据快照也不是生产库物理克隆。原始 SQL、参数、执行计划和扫描/排序记录保留在 `.tmp/checks/path-index-20261125/`（`results.json`、`summary.md` 等），不提交原始快照。
