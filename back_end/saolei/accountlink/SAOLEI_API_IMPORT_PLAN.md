# 扫雷网官方 API 接入方案

状态：首批后端已实现，待站长部署并运行首次同步；Web API 和前端接入留待下次更新。本轮不对现有业务库执行迁移或真实导入。

核对日期：2026-10-29。

## 接入范围

采用 [saolei-api](https://github.com/putianyi889/saolei-api) 访问扫雷网官方 API 和录像文件，分两次更新接入账号资料刷新、本人录像目录同步和录像导入。保留现有账号关联申请、人工审核、已导入本站的录像及卡片布局；旧扫雷网来源目录彻底删除，按已验证的绑定账号重建新目录。

替换数据取得方式，继续复用现有录像解析、原文件哈希查重、标识校验、来源上传时间、排行、比赛和勋章处理。账号绑定成功独立于外站资料同步：第三方请求、解析或入队失败均不撤销已提交的绑定，也不把成功的绑定响应改成失败。

旧网页爬虫不恢复；旧 URL 和三个旧任务路径继续保持停用。首批管理命令串行执行，不新增 Django Tasks；下次更新如增加任务，使用独立路径，避免升级前入队的旧参数被当作新 API 请求执行。

## 发布阶段

1. 首次更新只部署依赖、数据结构、内部同步及导入服务和管理命令。扫雷网资料刷新、目录同步及录像导入接口保持关闭，旧录像列表和统计接口也关闭；仅由服务器管理命令发起并完成首次同步。不开发或改接新 API，不注册新的 Ninja 路由（包括目录和摘要查询），前端代码保持不动。API 相关改动仅限关闭旧查询所需的路由移除和引用清理。同步进度和结果通过管理命令及服务端日志查看，同步完成后也不自动开放接口。接口关闭情况由站长人工鉴定，不新增自动化测试。
2. 下次更新再实现并开放下文所列的新 Ninja API，接入前端查询、同步和导入操作。复用首次更新的服务、任务和新来源库，不再清空数据或重新迁移旧来源库。

账号关联申请、审核和已有绑定继续保留；首次更新仍不在扫雷网关联审核成功后自动拉取资料，避免从管理命令以外发起同步。删除旧来源模型时一并关闭依赖该模型的旧列表、统计接口，清理其路由、视图及直接导入，避免残留引用阻止后端启动；这部分最小清理为允许的 API 改动，不借此兼容新数据结构，也不修改前端查询代码。

## 迁移方式：删除旧来源库，按绑定账号全量重建

新旧扫雷网用户 ID 保持一致，直接沿用 `AccountSaolei.id` 和现有已验证的绑定，不要求用户重新关联。录像 ID 可能变化，因此不建立新旧录像 ID 对照表，也不按相同数字继承旧来源记录或导入关联。

这里的“新库”指现有数据库内独立的新来源模型和数据表 `SaoleiApiVideo`；不另行部署数据库实例。

| 对象 | 迁移处理 |
| --- | --- |
| 旧 `VideoSaolei` 模型、表和全部来源记录 | 彻底删除；不清空后继续复用，也不复制数据到新表 |
| 新 `SaoleiApiVideo` | 新建空表，从新 API 全量取得目录 |
| `AccountSaolei` 和已验证的 `AccountLinkQueue(platform=c)` | 保留，以实际账号关联作为全站重建的种子 |
| 已导入的 `VideoModel`、`ExpandVideoModel` 和录像文件 | 保留；删除旧来源记录不执行本站录像删除流程 |
| 旧来源的 `import_video` 关联 | 随旧表删除；新来源通过原文件哈希重新查重、建立关联 |
| 账号上的旧 `video_import_task`、成绩、人气和三级录像数量字段 | 随结构迁移删除；新 `video_sync_cursor` 初始为 0，不继承旧任务进度 |

原 `VideoSaolei.import_video` 是从来源记录指向本站录像的外键，删除方向不会反过来级联删除 `VideoModel`。迁移不调用 `VideoModel.delete()` 或站长录像删除 API，不因此清理本站文件、排行、比赛关联或结算成绩；离线迁移测试覆盖旧表删除后本站录像、扩展记录和文件仍保留。

新表使用独立的本地主键 `id`，以唯一的 `remote_id` 保存新 API 录像 ID，并关联现有 `AccountSaolei`。`status` 直接保存 API 的审核状态整数，仅用于展示；已屏蔽、待审、已通过和未知状态均不影响是否尝试导入。新来源模型不设置 `hash` 字段，也不依赖上游 `hash`。`import_video` 使用可空的 `OneToOneField` 指向 `VideoModel`：扫雷网不会有不同来源 ID 对应同一原文件，同一条本站录像最多关联一条扫雷网来源记录。

新来源模型必须包含 `software` 字段，原样保存 API 返回的软件名称字符串；首次目录同步和后续详情更新均写入该字段，不限制为本站的软件枚举。[只读抽样](SAOLEI_SOFTWARE_SURVEY.md)已观察到 `Clone`、`Arbiter`、`Vienna`、`元扫雷3.3.4` 和 `Saolei.wang`，其中名称可能包含版本号；这些样本不构成上游字段取值的封闭枚举。

导入采用软件白名单，仅接受 `Clone`、`Vienna`、`Arbiter`、`元扫雷3.3.4`。集中定义白名单并按 `software` 原字符串精确匹配，区分大小写，不使用前缀匹配或自动兼容其他版本；`Saolei.wang`、未知名称、空字符串等所有白名单外取值均跳过。

来源目录照常保存所有软件的记录，首批命令仅为白名单内的软件串行执行导入；白名单外不下载文件或创建本站录像，详情刷新后也须在下载前按最新值重新检查。白名单外计入跳过数量，不计为网络失败，不自动重试。下次开放页面时展示来源记录及跳过原因。此限制独立于 `status`。

首次更新的全量同步仅由服务器管理命令 `sync_saolei_api --all-linked --full` 发起，不经网站接口；去掉 `--full` 即按保存的游标增量同步及续跑，`--account-id` 可重复指定扫雷网账号 ID，供小范围联调：

1. 按已验证的扫雷网绑定枚举账号，并核对其与 `AccountSaolei.parent` 的关系。未验证申请不纳入；绑定与账号记录不一致时单独报告，不猜测映射或修改绑定。
2. 为所有符合条件的账号安排资料刷新和录像目录全量同步，新来源的账号游标 `video_sync_cursor` 初始化为 0，使用各自绑定的扫雷网账号 ID 请求 API。中断续跑使用已成功提交的游标，不要求每位用户手动点击，也不扫描所有外站玩家。
3. 全量目录包含上游返回的全部审核状态和软件名称，导入前统一应用软件白名单，白名单外跳过；白名单内的录像不按 `status` 预先过滤。详情或文件不可取得时记录具体失败，继续处理其他录像。按页保存进度，失败账号可以恢复，已完成账号不因其他账号失败而回滚。
4. 新目录取得文件后，计算原文件哈希；同主且同哈希时复用已有本站录像、保留既有 ID，并建立新的来源关联。不同所有者的哈希冲突明确报告，不能据此改归属。
5. 新表只在首次结构迁移时创建为空。重跑管理命令或之后执行“同步全部”时，更新新表、保留成功关联和进度，不再清空新表或删除本站录像。

本站查重当前只查询 `original_hash` 索引。全量重建前应确认存量没有缺失哈希；必要时复用已有 `backfill_video_hashes` 命令补齐，不增加按旧来源 ID、时长或 3BV 猜测对应录像的兜底。命令及哈希规则见[录像管理说明](../videomanager/README.md)。

结构变更由 Django 自动生成，核对结果应为删除旧模型、创建新模型及移除账号过时字段，而非重命名旧表或搬运旧记录。旧任务指针随字段删除，不新增 Web 清理接口，也不手写数据迁移脚本。迁移前停止仍运行旧代码的相关 worker；新代码中的旧任务路径继续明确失败，历史任务记录中的旧录像 ID 不得传给新任务。旧表删除后，其专用查询、统计、序列化和测试切换或移除，不保留一个空的旧来源系统。

## 已核对的上游能力

初版方案以 v0.3.0 和[官方 API 文档](https://saolei.wang/page/api)为核对基线；首批实现固定使用 [v0.4.0](https://github.com/putianyi889/saolei-api/releases/tag/v0.4.0) 的官方 wheel，已核对 Release SHA256。2026-10-29 的 [`software` 只读抽样](SAOLEI_SOFTWARE_SURVEY.md)验证过目录和代表录像详情；本次实现使用离线响应及文件 fixture 验证，不执行真实账号同步或录像下载导入。

| 客户端能力 | 网站用途 | 需要遵守的契约 |
| --- | --- | --- |
| `user_info(ids)` | 已绑定账号的 ID、姓名和外站封禁状态 | 一次最多 50 个 ID；按返回的 `id` 匹配，不按数组位置匹配；不使用账号成绩和外站标识列表 |
| `video_list(player_id=..., cursor=..., size=...)` | 获取指定玩家的录像目录 | ID 升序；`size` 上限 1000；保存 `next_cursor`，保留玩家筛选条件 |
| `video_info(ids)` | 导入前确认归属、更新展示状态并取得文件后缀 | 一次最多 50 个 ID；缺项不等于已删除，不因目录中的 `status` 预先跳过请求 |
| `download_videos([suffix])` | 取得单条录像的二进制内容 | 后缀格式为 `YYYY/MM/DD/filename`；仅从官方文件域下载；返回内容不自动落盘 |
| `stats()` | 为本次目录同步确定 ID 上界 | 不通过遍历 ID 探测数据；不要把全站录像数量当成单个玩家的数量 |

客户端返回全部审核状态：`0` 已屏蔽、`10` 待审、`20` 已通过；未知状态整数也会保留。列表没有文件地址，需要通过详情接口取得。

网站不使用 `status` 作为导入资格判断。若上游不返回某条详情或文件地址，则记录为“详情或文件不可取得”，保留来源记录和重试机会；不把这种情况伪装成本站按审核状态禁止导入，也不猜测文件地址或恢复网页爬取。

官方按合作方限制数据请求为 60 次/分钟，建议全量同步低于 30 次/分钟；录像文件全站限速 3 次/秒。客户端默认的数据间隔 2 秒、下载间隔 0.4 秒只在单个实例内有效，多进程并不共享额度。

当前官方页面还提供帖子接口，本次导入不使用；不为这些接口扩展网站或客户端。

## 依赖、密钥与模块边界

- 按现有 WOM、MSGames 的方式，将固定版本的 Release wheel 和发布的 SHA256 加入 `requirements-wheels.txt`，在 `requirements.txt` 固定包版本。实现前通过依赖解析检查 HTTPX、Pydantic 和 Python 版本兼容性，不复制客户端源码。
- 服务端沿用 `utils.secrets_json.read_secret`，在创建客户端时惰性读取 `saolei_api_key`。不在 settings 加载时读取，不增加自动写入密钥的业务入口。真实 key 不进入源码、前端、文档、fixtures、任务参数或日志。
- `accountlink/saolei/` 沿用现有 `msgames/`、`wom/` 的组织方式；这是 `accountlink` 内部模块，不是新的 Django app。
- `client.py` 惰性读取密钥并创建客户端；`utils.py` 放白名单和纯字段转换；`services.py` 编排资料、目录落库和文件导入；管理命令负责串行调用及失败汇总。下次更新再按需增加 `tasks.py`、`api.py`，模型仍由 `accountlink.models` 管理。
- 登录、本人操作、关联是否已审核、目标资源访问权限统一在 API 层校验。service 不校验操作者角色。异步任务执行时重新核实账号、来源录像和绑定关系是否仍与入队时的目标一致，失效任务停止写入，防止解绑、重绑后的旧任务写错账号。

## 资料与录像字段适配

### 账号资料

本次只使用账号的 `id`、`name` 和 `banned`。所有账号成绩数据（`scores`、`scores_nf`）及 `signatures` 均不进入网站的资料适配、持久化或接口输出，也不作为绑定、资料刷新或录像导入的前提。录像自身的成绩、NF 属性和文件内标识仍按既有导入业务处理。

| 新 API 数据 | 当前模型 | 处理建议 |
| --- | --- | --- |
| `UserInfo.id` | `AccountSaolei.id` | 新旧用户 ID 一致，直接沿用现有绑定；按返回 ID 校验响应归属，不重新映射账号 |
| `name` | `name`，现有长度 10 | 校验新站长度契约，必要时扩容；不静默截断 |
| `banned` | 与本站 `UserProfile.is_banned` 无直接对应 | 仅用于外站账号状态，不自动封禁本站账号；封禁响应不依赖成绩字段存在 |
| 不再同步的旧字段 | `total_views`、`beg_count/int_count/exp_count`、`b/i/e/s_t_ms`、`b/i/e/s_b_cent` | 删除字段及旧值，不再保留历史账号统计；其他平台的同名字段不受影响 |
| 已停止使用的旧任务指针 | `video_import_task` | 删除字段；首批直接串行执行，不保留无用途的任务关联 |

`accountlink.saolei.services.update_saolei_account_info()` 已替换旧资料写入函数，只更新姓名、外站封禁状态和资料更新时间。`AccountSaolei` 仅保留 `id`、`parent`、`name`、`banned`、`update_time`、`video_sync_cursor` 和 `video_update_time`；不进行账号成绩精度升级、字段换算或相关数据回填。

账号还需保存本地同步进度，不属于上游账号资料：

| `AccountSaolei` 新字段 | 类型 | 含义 |
| --- | --- | --- |
| `video_sync_cursor` | `PositiveBigIntegerField(default=0)` | 上次已成功提交的录像目录页对应的 `next_cursor`，用于下次增量请求的 `cursor`；初始为 0，从目录起点扫描 |

每页来源记录与 `video_sync_cursor` 在同一数据库事务中提交；请求、响应校验或写入失败均不推进。游标以目录成功落库为准，不以录像文件是否导入成功为准；白名单外录像也照常保存目录并计入游标进度，下载或导入失败另按来源记录重试。字段持久化在账号表，不依赖缓存、更新时间或已导入录像的最大 ID 推算。结构迁移由 Django 自动生成。

### 录像目录

| 新 API 数据 | 本地字段或行为 |
| --- | --- |
| `id`、`user_id` | API 录像 ID 写入新表 `remote_id`，另设本地主键；逐条核实与绑定账号的归属，不读取旧来源表 |
| `level=beg/int/exp` | 映射为本地 `b/i/e` |
| `real_time`、`board_3bv`、`nf` | 对应 `timems`、`bv`、`nf` |
| `software` | 新来源表保存 API 原始软件名称字符串，供目录接口返回和前端展示；不转换为本站软件枚举 |
| `upload_time` | Unix 秒转为带 UTC 时区的时间，沿用来源上传时间保存逻辑 |
| `status=0/10/20` | 新表保存原整数，分别展示为已屏蔽、待审、已通过；未知整数也保留，仅用于展示，不影响是否导入 |
| `file_url` | 详情取得后将客户端规范化的 `YYYY/MM/DD/filename` 后缀保存到新来源表可空的 `file_url` 字段；导入从该字段下载，使用实际文件名构造 Django `ContentFile` |

旧来源状态枚举不作为新库的数据契约；仅供旧模型使用的枚举、DTO 和查询代码在实施时清理，不建立原始响应影子表。

新来源模型不再提供录像网页链接的 `url` getter。`file_url` 由详情刷新维护：目录列表不包含文件地址，目录更新保留已保存的后缀；详情缺项保留已有信息，详情明确返回无文件则将 `file_url` 置空，不用旧后缀继续下载。文件下载失败保留已落库的后缀和来源记录，后续重试仍先刷新详情。

上游 `hash` 不采集、不持久化，也不用于来源匹配或导入判定。文件下载后仍交给既有录像导入服务，沿用本站 `VideoModel.original_hash` 的统一查重规则；新来源表不另存一份文件哈希。

目录写入业务改接新模型，按新 API 的 `remote_id` 更新或创建，保留新库已经建立的 `import_video` 关联。后续同步也必须更新待审转通过、屏蔽及元数据修正，不能沿用旧函数只插入未知 ID 的实现；新表已有记录的账号归属冲突时停止并报告。

扫雷网账号 ID 在新旧站之间保持一致；它与本站 UserProfile ID、UserMS ID 仍是不同概念。来源录像 ID 和本站录像 ID 也各自独立，所有关联按实际外键处理。

## 同步和导入流程

### 串行执行与节流

首批由管理命令在同一进程串行处理账号、目录页和录像文件，整个命令共用一个客户端。数据请求间隔为 2.1 秒，文件下载间隔为 0.4 秒；不增加主任务、子任务、专用队列或缓存进度。站长不要同时启动多个使用同一 key 的同步进程。下次更新开放 API 时再按需要编排后台任务，继续复用内部服务并统一节流。

首次更新由管理命令调用内部服务完成同步，不提供 Web 触发入口。网络请求在数据库事务和排行锁之外；本地落库锁定来源账号和来源行，文件导入阶段沿用 `ranking_access`。下次开放的 Web API 只验证权限和创建任务，返回任务标识，不在 HTTP 请求中循环下载整批录像。

客户端的 30 秒 timeout 是网络操作超时，不作为整个任务或整批下载的总耗时承诺。下载每次传一个后缀，避免一次把整批文件放入内存；通用下载边界若需补强，应在客户端完善，不在网站重新实现 HTTP 客户端。

### 首次同步与后续增量

1. 首次同步仅由迁移管理命令在服务器串行处理已验证且绑定一致的账号，新账号 `video_sync_cursor=0`，旧来源表和旧同步断点不参与计算。增量更新和中断续跑从该账号已保存的 `video_sync_cursor` 请求；显式重新全量扫描才从 0 开始。下次更新开放网站 API 后，由 API 验证账号已关联且操作者为本人，再调用同一套内部服务。
2. 使用 `stats().max_video_id` 固定本次处理上界，分页请求始终携带 `player_id`。此上界用于让任务收敛，不代表上游提供了一致性快照。
3. 一页元数据验证后，将该页来源记录与响应的 `next_cursor` 对应进度在同一事务中提交，再读取下一页。跨过本轮 ID 上界的页面仅保存上界内记录，提交的游标最多为上界加 1，避免跳过尚未处理的尾部。`video_sync_cursor` 只前进、不回退；重新全量扫描使用本次扫描的分页游标，不用较小的页游标覆盖账号已保存的进度。失败时整页回滚、不推进游标，也不把未完成同步标为成功。
4. `video_sync_cursor` 持久化每个账号上次成功同步到的位置，完整目录更新时间仅在本轮目录扫描完成后更新；两者与已有资料更新时间分开，刷新姓名不重置录像游标。具体字段通过 Django 自动生成结构迁移。
5. 增量游标只能找到新增 ID。保留“同步全部”的目录对账操作，更新已有录像的元数据和展示状态；另行重试未导入、详情暂不可得或文件取得失败的记录，不按审核状态排除重试，但重试仍须通过同一软件白名单。`since` 是上传时间筛选，不能当作审核变更时间筛选。
6. 单次详情响应缺少某个 ID 时保留本地资料并记录不可取得，不据此删除录像、清空关联或标为已删除。屏蔽状态由列表的明确状态确认。

### 单条录像导入

`status` 不影响是否导入。先检查来源 `software` 是否在白名单内，白名单外直接跳过；白名单内的录像，无论审核状态均可请求详情、下载文件并进入同一导入链。详情刷新后若最新 `software` 不在白名单内，同样在下载前跳过；实际无法取得详情或文件、文件解析失败或触发本站既有业务校验时，按具体原因处理。

1. 单条导入任务先用新表本地主键读取来源，再调用 `video_info(source.remote_id)` 重新取得详情，核对外站录像 ID、玩家 ID 和文件后缀，并更新展示状态；未取得详情或没有文件时记录不可取得。本地主键不作为上游录像 ID 使用。
2. 下载原文件并构造 `ContentFile`，将文件交给改接新来源模型的 `saolei_video_import_one()`，复用其本地导入业务，不保留对旧 `VideoSaolei` 的兼容调用。
3. 本站录像属性和本地审核状态由文件解析及现有业务规则决定，上游 `status` 不参与本地状态判定；继续基于文件内标识执行 `Identifier.verify`，不读取账号资料中的 `signatures`。
4. 文件、扩展记录、统计、排行、比赛及勋章沿用既有创建链。发现用户没有 UserMS 时，按现有 MSGames 业务的方式创建并持久化实际关联。
5. 查重后不改变已有录像归属；异主文件冲突不调早其上传时间。同主录像沿用 `set_import_upload_time` 的更早时间规则，同一来源重试或迁移后重新关联已存在的本站文件时，不重复创建录像或增加本站录像计数；来源与本站录像保持一对一关系。
6. 文件下载、解析或写入失败时保留可重试的来源记录；重试先检查既有导入关联，避免重复创建录像。

后续来源审核状态变化时只更新展示数据，不停止导入，也不自动更改已导入本站录像的状态、删除录像或触发比赛重新结算。作废和重算继续走独立业务流程。

首批命令在目录同步后扫描本地新来源表中白名单内、尚未关联本站录像的记录，包含以前已落库但未完成的录像。即使目录游标已推进，进程中断或文件导入失败也不会导致续跑漏导。单个账号资料或目录失败仍尝试处理其他独立阶段及账号；单条文件失败保留来源记录并继续，最后返回非零退出码。上游鉴权失败或限流则立即停止，不自动重试，已提交的目录和导入结果保留。

## 下次更新：网站 API 和前端

以下接口全部留待下次更新，首次更新不注册或开放。新 API 使用 Ninja，建议统一挂在 `/api/accountlink/saolei` 下：

| 操作 | 建议接口 | 行为 |
| --- | --- | --- |
| 刷新资料 | `POST /{account_id}/refresh` | 本人且已验证；入队后返回任务标识 |
| 同步目录及批量导入 | `POST /{account_id}/sync` | 本人且已验证；显式区分全部对账和新增同步 |
| 导入单条来源录像 | `POST /videos/{source_id}/import` | 使用新表的本地主键，验证来源账号归属；通过软件白名单后创建或复用导入任务，否则返回跳过结果 |
| 查看本地目录 | `GET /{account_id}/videos` | 分页读取本地记录，包含来源 `software`，限制返回条数，不访问外站 |
| 查看同步摘要 | `GET /{account_id}/summary` | 读取本地游标、更新时间及任务汇总，不访问外站 |

这些路径是方案，不是已部署契约。所有权限在 API 层解决，普通用户写操作按用户限流，同时避免同一账号重复启动同类活动任务。

首次更新不修改 `CardSaolei.vue` 或其他前端代码，现有禁用状态保持不变。下次更新保留卡片、轮播、同步区域和管理入口布局，开放新 Ninja 接口时再启用对应按钮。非本人页面不出现可用的同步或导入入口，不能只依赖前端判断保护接口。

下次开放前端后，来源状态、任务状态和本站录像审核状态分开展示，并区分新表本地主键、外站 `remote_id` 和本站 `import_video_id`。全量对账期间显示同步进度，不能将目录暂为空误报为本站录像丢失。失败统计应查询失败的来源任务，不能沿用当前“先过滤已导入录像，再统计失败”的口径；整批状态必须与实际子任务结果一致。仅活动任务期间轮询本地摘要，完成、失败或卸载后停止。

录像管理列表展示来源记录的 `software`，白名单外记录显示“暂不支持该软件，跳过导入”。本站 `VideoModel.software` 仍由 `MSVideoParser` 解析实际文件确定，不用 API 的软件名称字符串覆盖；未知来源软件名称也可以入库展示。

下次更新的资料卡片保留布局，不接入账号成绩和外站标识列表，不再展示已删除的成绩、人气或旧计数；首次更新前端仍不改动。录像网页链接按官方文档改为 `https://saolei.wang/video/{id}`；玩家主页链接实施时核对新站路由后统一修改，旧 ASP 地址不继续用于新数据。

旧来源模型在首次更新删除时，仅为关闭旧查询移除其历史列表、统计 URL 和相关引用，前端不动；下次更新再修改前端，切到新 Ninja API。不把旧来源 ID 自动解释为新 API 的 ID，也不将旧 URL 重定向到数字恰好相同的新记录。下次更新中资料刷新等旧 Django view 如需修改，按项目规范迁移到 Ninja。

## 错误和重试

| 情况 | 处理 |
| --- | --- |
| 本站未登录、不是本人或关联未验证 | API 层拒绝，不发外站请求 |
| 服务端未配置 key | 明确标为本地配置问题，不伪装成外站用户不存在 |
| 上游 `AuthenticationError` | 上游鉴权失败；不能直接转换成本站登录失效的 401 |
| 上游 `RateLimitError` | 保留 `retry_after`，任务按调度规则稍后重试；不循环立即重试 |
| 上游 HTTP、网络或响应格式失败 | 分类记录上游错误；保留已完成绑定、已落库页和已导入录像 |
| 本地数据库、文件或业务异常 | 与上游错误分开，不用捕获所有异常的方式统一包装成“网络错误” |

资料刷新失败不覆盖已有数据；只有成功提交的页推进目录游标。业务已导入与任务执行成功分开判断，错误响应和日志包含目标账号、来源录像及任务标识，不包含认证头或 key。

## 实施顺序与验收

1. 沿用保持一致的用户 ID 和现有绑定，验证封禁账号的基础资料响应；账号资料不依赖成绩或外站标识列表。所有录像审核状态统一处理，不核对或迁移旧来源录像 ID。如客户端无法表达官方响应，先在客户端修正契约。
2. 固定依赖，完成字段转换及离线样本测试；定义新来源模型、账号基础资料字段和新游标，由 Django 自动生成删除旧模型、创建新模型及必要账号字段变更的结构迁移。
3. 完成改接新模型的资料、目录、单条导入服务和全站已绑定账号重建管理命令，整个命令串行复用同一客户端，并补导本地未完成录像；首批不新增后台任务或队列。
4. 首次更新清理旧来源引用，仅为关闭旧列表和统计接口移除相关路由、视图及直接导入，前端不动；验证原文件哈希回填与删除范围后，停止旧执行路径，删除旧来源库、创建新库、删除旧任务指针和统计字段并初始化新游标。所有同步、刷新和导入接口继续关闭，不开发或改接新 API，不挂载新 Ninja 路由。
5. 由站长通过管理命令先联调一个已绑定账号，再运行全站全量重建。分别核对资料、目录、已有文件复用和新文件导入；失败可续跑，不再次清空新表。通过命令结果和日志验收，首次更新至此结束，不开放接口。
6. 下次更新完成 Ninja API 和前端接入，通过权限、任务状态和页面验收后再开放查询、资料刷新、同步及导入入口；沿用首次同步的新来源数据和进度。

首次更新的离线 CI 使用 `httpx.MockTransport`、模拟配置和小型录像 fixture，不需要真实 key，不访问扫雷网。重点覆盖后端服务和管理命令中的单位和时间转换、审核变化、分页失败不推进游标、同步失败不影响已有绑定、重复任务、同主查重、异主冲突以及既有排行和比赛信号。API 权限及前端测试留待下次更新，不为接口关闭新增路由、HTTP 状态或前端开关测试。

迁移验收另需证明：删除旧来源表保留本站录像、扩展记录及文件；只为已验证且一致的绑定账号从 0 全量同步；同一个数字在新旧来源中代表不同录像时不会继承旧关联；同一文件在新站换 ID 后仍复用原本站录像，并建立唯一的新来源关联；中断后恢复和重新全量均不重复导入。

首次更新的接口关闭情况由站长人工鉴定，包括旧刷新、同步、导入、录像列表和统计接口，以及未开放新 Ninja 路由。不为此新增自动化测试，不为验收修改 API 或前端；允许的 API 改动仅限上述关闭旧查询及清理引用。首次同步仅由管理命令发起，同步完成也不自动启用网站接口。

导入验收需覆盖 `status=0/10/20` 及未知整数：在同样可取得文件且通过本站业务校验时，均完成相同的导入流程。改变上游 `hash` 不改变导入结果；详情或文件不可取得按实际失败原因记录。用户 ID 直接沿用现有绑定，不重新申请或验证。

首次更新的字段验收覆盖 `software` 的首次写入和后续更新；目录接口输出及前端展示留待下次更新验收。未知软件名称原样保留，本站录像的软件类型仍以文件解析结果为准。

账号资料验收需证明网站只适配所需基础资料，不读写或输出 `scores`、`scores_nf`、`signatures`；旧成绩、人气、计数和任务指针字段随结构迁移移除，不新增成绩精度迁移。刷新基本资料保留目录游标及完成时间，录像文件的成绩解析和标识归属校验继续有效。

游标验收覆盖初始值 0、各账号独立保存、增量及中断续跑读取成功游标、页记录与游标同事务提交、失败回滚，以及重新全量扫描不回退账号进度。白名单外记录和文件导入失败不阻塞已落库目录页的游标推进，资料刷新也不重置游标。

首次更新的软件筛选验收覆盖后端服务和管理命令的单条、批量、全站重建和重试流程：白名单中的 4 个精确取值继续走既有导入校验；`Saolei.wang`、未知名称、空字符串、大小写变体和其他版本名称在任何 `status` 下均保留目录记录并跳过导入，不下载文件、不创建本站录像。列表在白名单内、详情更新为白名单外时也跳过；跳过数量与失败数量分别汇总。API 入口验收留待下次更新。

下次更新接入前端时，Cypress 由用户运行，覆盖卡片布局、本人限制、任务结束后停止轮询和来源状态展示。首次更新不修改前端或相关测试。真实 API 联调与离线测试分别记录结果，不把 mock 测试通过写成外站验证通过。

已确定账号资料不使用任何成绩数据或 `signatures`，不调整账号成绩精度；旧来源库删除、新来源库按已绑定账号全量重建、录像包含 `software` 字段且导入按上述软件白名单筛选、`status` 不限制导入、不采集上游 `hash`、用户 ID 保持一致。封禁账号的基础资料响应和新主页地址仍需技术核实。
