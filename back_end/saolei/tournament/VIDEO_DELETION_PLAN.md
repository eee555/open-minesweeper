# 比赛录像删除与成绩一致性

状态：业务约定已确认，2026-10-24。本文记录普通删除与按比赛类型重算的边界；已有 GSC、经典打卡赛重算服务继续使用。站长单个删除 API 已返回受影响比赛 ID 并记录日志警告，隐藏中文页面已提供警告确认和串行处理；其他删除入口的警告、主办方私信及重算事务与并发控制的完善尚未实现。

## 已确认的业务约定

- `VideoModel` 删除时仍一起删除对应 `ExpandVideoModel`，沿用现有删除信号。
- **普通删除已颁奖比赛的录像，不自动重新结算；在显式重算前暂时保留已经结算的成绩、名次、排名积分和个人历史最好成绩。** 录像文件和比赛录像关联被删除，原录像不再能预览或下载。
- **显式重算时，被删除录像如何影响成绩由比赛类型、赛制及成绩来源决定。** 打卡赛和 GSC 录像来源成绩不再计入已删除录像；GSC 手工来源保留主办方录入的成绩。
- 每个比赛类型负责自己的删除处理及重算规则。公共删除信号不自动重算，也不代替赛种判断成绩来源；新增赛种必须同时提供这些业务规则及测试。
- **普通删除必须有比赛相关警告。将来增加私信功能后，普通删除比赛录像须私信通知受影响比赛的主办方。** 通知本身不作废录像成绩，不自动扣分。
- 最新录像队列继续保留既有快照逻辑，见 [录像事件说明](../videomanager/README.md#删除录像)。

上述“暂时保留”描述删除操作当下的行为，不保证后续重算仍保留被删录像的贡献。未结算比赛尚无正式结果，首次结算同样按各赛种的成绩来源处理。

## 各比赛类型的重算规则

| 比赛类型及成绩来源 | 重算依据 | 被删除录像的处理 |
| --- | --- | --- |
| 打卡赛（Weekly，当前经典赛制） | 网站内仍存在且符合计分条件的比赛录像，沿用 2高5中及默认补位规则 | 该录像的成绩贡献作废，从剩余合格录像补位；不足数量按本赛制默认值计算 |
| GSC，`GSCParticipant.manual_scores=False` | 网站内仍存在且符合计分条件的比赛录像，沿用 20/12/5 规则 | 该录像的成绩贡献作废，从剩余合格录像补位；不足数量按 GSC 默认值计算 |
| GSC，`GSCParticipant.manual_scores=True` | 主办方手工录入的九项成绩 | 不从录像重算这九项成绩，录像删除不改变手工输入值；仍参与全场排名及积分重算 |
| 未来新增赛种或赛制 | 由该类型明确自己的成绩来源和计算服务 | 明确定义删除后的处理及重算行为，完成接入后才允许调用对应重算入口 |

`manual_scores` 是 **GSC 参赛者级别** 的选项，同一场 GSC 可以混合手工来源与录像来源成绩。没有启用该选项的参赛者继续按录像重算，不能因为本场某位选手使用手工成绩，就保留其他选手已经删除的录像贡献；也不能按“当前无录像”自动启用手工成绩。

手工来源保留的是录入成绩，不是固定名次或积分。其他选手重算后的成绩改变时，其名次、`rank_score` 和关联用户的积分汇总仍可能变化。

## 当前实现及风险

| 位置 | 当前行为 | 后续需要处理的边界 |
| --- | --- | --- |
| `Tournament.videos` / `VideoModel.delete()` | 一个录像可以关联多场比赛；删除录像清除这些多对多关联，不删除 participant | 不增加自动重算信号；警告和通知必须覆盖所有关联比赛，不能依赖 `ongoing_tournament` 判断 |
| `GSCParticipant` / `WeeklyParticipant` | 保存汇总成绩、名次及 `rank_score`，录像删除不会更新这些字段 | 保留删除当下的结果；后续显式重算按赛种及成绩来源更新 |
| `WeeklyParticipant.classic_et` / `classic_it` | JSON 内保存 `[video_id, timems]`，不是外键 | 删除后保留成绩，但不能把旧 ID 继续作为可用录像链接；当前周赛表格仅检查 ID 非零，仍会展示失效预览入口 |
| `management/commands/refresh_tournament_scores.py` | 按类型分派 GSC / 经典打卡赛重算服务，在数据库事务中刷新成绩、全场排名、积分及历史 best；GSC 跳过手工成绩重算 | 已删除录像不再贡献录像来源成绩，符合业务规则；仍需完善事务内写 Redis 和并发积分覆盖问题 |
| `gsc/tasks.py` / `weekly/tasks.py` 的 finish | 删除无录像参赛者、重算成绩及排名、切换状态、公开录像，再分别排队发积分和刷新 best | 与维护重算命令的副作用不同，入口应明确用途；无录像参赛者处理继续由赛种决定，GSC 手工来源不因无录像被删除 |
| `services.delete_participants_without_videos` / `api.delete_participant` | 前者按现有录像判断参赛者是否保留，并排除 GSC 手工来源；后者允许主办方或管理员删除符合条件的无录像参赛者，删除会撤回该人的积分 | 区分删除录像、删除参赛记录及显式重算，不能把三者视为同一操作；未来赛种需定义自己的参赛资格保留规则 |
| GSC `manual_scores=True` | 手工成绩不随 `refresh_gsc_scores` 重算，也不因无录像被 finish 清除 | 保留该来源语义，不把普通删除后的录像来源成绩自动转为手工成绩 |
| `services.get_participants_for_rank` / `get_ranked_participants_for_award` | 目前 GSC 以外分支直接查询 Weekly 参赛者 | 新增赛种时须扩展明确的类型处理，不能让未知类型沿用这个分支；管理命令当前已明确拒绝不支持的类型 |

当前录像筛选及 GSC 手工成绩来源处理已经基本符合上述规则。后续重点是明确入口职责、补齐失效预览、通知以及数据库与缓存的一致性，不把显式重算时移除已删录像的贡献当成需要修复的错误。

## 普通删除的警告与未来私信

当前 `POST /api/video/admin/delete` 接收 `{"id": 123}`，仅允许 superuser 会话调用并校验 CSRF。接口通过 `delete_video_by_id` 事务删除并沿用已有信号，返回 `id`、`deleted`、`affected_tournament_ids`；涉及比赛时记录警告日志，不自动重算或通知主办方。同路径 GET 仅验证权限并初始化 CSRF，不修改录像。

隐藏中文页面 `/#/superuser/delete-videos` 没有导航入口；后台确认权限后才显示删除表单。页面提供比赛相关警告及永久删除确认，先校验、去重全部 ID，再逐个请求，显示已确认结果和受影响比赛。遇到失败、超时或权限失效立即停止后续请求，不自动重试；操作者核对结果后可以重新确认并继续剩余 ID。每次删除独立提交，后续失败不回滚此前成功项。手动停止或离开页面只停止后续请求，不能撤销已发送的删除。Admin 等其他入口的警告及未来私信仍待实现。

### 删除前的警告

站长隐藏页面现已提供通用比赛警告和确认，但尚未在删除前逐场预览关联比赛。后续有交互的删除入口，包括 Django Admin 的单条及批量删除确认页，应先列出受影响比赛及录像数量。用户级联删除也需要提示比赛录像的影响。后台脚本和定时任务无法交互确认，应记录相同语义的警告及删除来源。

已颁奖比赛的提示应明确表达：

> 这些录像关联比赛。删除后将无法再预览或下载，本次删除不会自动修改已结算的成绩和积分。之后重算打卡赛或 GSC 录像来源成绩时，被删除录像将不再计分；GSC 手工录入成绩仍保留，但名次和积分可能随全场重排变化。

实际提示按关联比赛的类型、状态及参赛者成绩来源展示。未结算比赛说明首次结算采用相同的赛种规则。一个录像关联多场比赛时分别说明，不能统一承诺“所有比赛成绩不受影响”或“所有类型重算都会作废”。

当前私信功能尚未实现，警告不能宣称“已通知主办方”。接入私信后，才增加“删除后会私信通知相关比赛主办方”的说明。

### 私信功能接入后的通知规则

- 普通删除比赛录像后，向受影响比赛的主办方发送私信；覆盖实例删除、QuerySet 批量删除、Admin、后台任务、用户及扩展记录引发的级联删除。
- 通知包含比赛、原录像 ID、原录像所属参赛者、删除时间和删除来源；能可靠取得操作者时再记录操作者，不能把录像所属用户直接认定为删除操作者。
- 已颁奖比赛的私信明确“录像已删除，本次删除未自动重算；后续重算按本赛种及成绩来源处理”，并附上对应类型的规则。打卡赛和 GSC 录像来源说明重算时不再计入该录像；GSC 手工来源说明保留录入成绩。未结算比赛说明首次结算采用相同的规则。
- 批量删除按同次操作、比赛及收件主办方合并，避免每条录像各发一封；同一录像属于多场比赛时通知各场主办方。没有主办方或账号已经不存在时，记录未投递原因，不猜测收件人。
- 通知只能在删除事务成功提交后投递；回滚不发信，失败可以重试，同一删除事件对同一收件人不重复创建私信。
- 删除前保存通知所需的比赛与收件人信息，不能等 `post_delete` 之后再通过已经清除的多对多关联查找主办方。低层删除捕获可复用 Django 的 `pre_delete`；批量上下文和操作者信息由删除业务入口提供，直接 ORM 删除允许记录为来源未知。
- 通知意图须与删除在同一数据库事务中持久化，再复用项目现有 Django Tasks / `django-tasks-db` 执行投递，不新增消息队列。只注册一个提交后发送回调不足以保证进程退出后仍可补发；未来私信记录或投递记录须提供持久化及去重依据。

这部分等待私信功能设计后实现，本轮不增加临时私信模型或发送任务。

## 按比赛类型组织删除与重算

### 各层职责

| 层次 | 职责 |
| --- | --- |
| 公共录像删除路径 | 删除录像及扩展记录，维护普通录像相关计数、排行和引用，捕获受影响比赛并支持警告、审计和未来私信；不自动执行比赛重算 |
| 赛种或赛制自己的业务服务 | 决定成绩依据、已删除录像的处理、剩余录像补位、无录像参赛资格、手工来源保留方式及赛种 best 计算 |
| 公共比赛入口及可复用服务 | 校验并分派具体类型；为适用的赛种复用事务、全场排名、积分差额和缓存同步能力；计分字段与参赛者查询由对应类型明确提供 |

继续沿用 `gsc/services.py` 与 `weekly/services.py` 等现有服务，公共入口按比赛类型及赛制明确分派。共同的事务和积分维护可以复用，各赛种的成绩来源及删除规则分别实现。

当前赛种沿用现存录像和 GSC 手工录入成绩作为重算依据。删除事件保存的追溯信息用于审计与通知，不用于恢复已删除录像的计分贡献。未来赛种若需要独立保存成绩依据，由该类型自行定义其数据模型和重算规则。

### 新增比赛类型或赛制的接入要求

每个新类型须同时定义并接入：

1. 成绩来自网站录像、主办方输入还是其他数据源，以及来源选项作用于整场比赛还是单个参赛者。
2. 普通删除后的处理、显式重算是否作废已删除录像、无录像时的补位或参赛资格规则。
3. 该类型的成绩重算、全场排名、积分及历史 best 更新方法，以及与首次结算的业务区别。
4. 删除警告和未来主办方私信中的类型说明，多场关联时分别使用各自规则。
5. 删除、重算、混合成绩来源、重复执行和失败回滚的测试与文档。

尚未提供重算实现的类型应由重算入口明确拒绝，不能默认按 GSC 或打卡赛计算；公共辅助函数也须同步检查类型覆盖。

### 复用现有计算并统一事务入口

1. 显式重算以比赛为单位，记录操作者和影响范围；一个录像关联多场比赛时，各场分别执行自己的规则，重算某场不隐式重算其他场。
2. 分派到对应赛种及赛制的计算服务，复用 GSC 20/12/5 与经典打卡赛 2高5中的既有筛选、默认补位和汇总逻辑；GSC 按每位参赛者的 `manual_scores` 区分来源。
3. 重算全场排名，复用 `award_tournament_rank_scores` 的新旧 `rank_score` 差额思路及 `TournamentUser.add_score` 的原比赛结束时间衰减规则。不能仅扣被作废录像所属用户的积分，其他选手名次和积分也可能变化。
4. 复用 `refresh_gsc_best_scores(..., rebuild=True)` / `refresh_weekly_best_scores(..., rebuild=True)` 允许历史 best 回退；如果参赛者退出计分，其原用户仍须纳入积分撤回与 best 修正范围，不能只遍历重算后剩余参赛者。
5. 成绩、全场排名、积分差额及 best 在同一数据库事务内写入。首次结算、重复结算、历史补录、更正和积分任务必须共用并发控制，按固定顺序锁比赛、参赛记录及受影响的 `TournamentUser`；仅锁本场比赛无法防止同一用户跨场积分并发覆盖。
6. Redis 在提交后从已提交数据库状态更新，并保留可重试的同步意图，防止回滚发布脏数据或较旧任务覆盖新结果。私信使用同样的提交后投递边界；普通删除的通知不触发此重算链路。

现有 finish、发积分及 best 任务分开执行，现有 `refresh_tournament_scores` 虽有数据库事务，但积分与 best 服务会在事务内直接写 Redis，也没有统一的数据库锁协议。这些是后续一致性改进项，不改变各赛种已经明确的重算数据来源。

### 仍需在实现前确定的规则

- 现有 finish 会删除无录像的非手工站内参赛者，而维护重算命令保留参赛者并计算默认补位成绩。后续按赛种明确这两个入口是否需要统一，不增加跨赛种的通用删除规则。
- 并列成绩的名次规则。当前 `refresh_tournament_ranks` 只按成绩排序再顺序编号，更正流程不能擅自改成另一种并列规则。
- 普通录像“冻结”与比赛“作废”的关系，以及跨场作废的权限和确认方式。
- 历史成绩来源的更正与切换由对应赛种管理；GSC 已有手工来源不能按录像是否齐全自动切换。

## 后续实施顺序与验收

1. 增加按赛种及成绩来源展示的删除警告；修正周赛中已删除录像的预览状态，在显式重算前保留原毫秒成绩。
2. 沿用并补齐各赛种的删除与重算服务，明确 finish 与维护命令的职责，以及新增类型的接入要求。
3. 完善重算事务、并发控制及操作记录，覆盖全场积分、历史 best 和缓存一致性。
4. 私信功能完成后接入普通删除主办方通知，并复用其投递、重试和去重能力。

测试重点：普通删除与批量/级联删除不立即重算；打卡赛和 GSC 录像来源重算时排除已删除录像并正确补位；同场 GSC 手工来源保留输入值但参与全场排名和积分更新；手工及匿名成绩不被误清除；多场比赛各按自身规则处理；重复重算不重复扣分；历史 best 回退；结算并发、失败回滚与缓存重试；不支持的赛种被明确拒绝；通知回滚不发送、重试不重复及缺少主办方。前端警告和失效预览入口由组件测试覆盖，Cypress 留给用户运行。
