# 录像分享链接预览计划

更新：2026-11-24。

状态：首版后端及本地验证已完成；尚未部署，分享 UI 不开放。QQ 卡片、Nginx 文件转发及服务器容量由用户在秘密上线后验收。

## 1. 目标与范围

让录像链接在 QQ 聊天等场景中生成卡片预览：

- **图片**：固定显示录像完成后的棋盘画面——所有非雷格翻开设邻雷数，雷格显示雷。由 `VideoModel.board` 位图与 `level` 推导，不重放录像，也不保留过程中的插旗/鼠标状态。
- **文本**：卡片标题与说明包含本局元数据（玩家、难度、模式、3BV、用时等）。
- **分享入口**：QQ 实测通过后，在录像页提供复制分享链接的按钮。首版秘密上线后端能力，不向用户暴露相关 UI，由维护者手动构造链接验收。

不在本次范围：

- GIF/动画预览；QQ 之外的平台逐一适配；把站内路由从 hash 模式改为 history 模式。
- 修改现有录像链接 `#/video/<id>` 的行为。
- 还原录像结束瞬间的插旗/误标状态，或任意时刻的中间局面。

## 2. 现状与约束

| 项目 | 现状 | 影响 |
| --- | --- | --- |
| 路由 | `createWebHashHistory`，链接为 `/#/video/<id>`（`front_end/src/router/index.ts:2`） | 爬虫请求只到 `/`，拿不到录像 ID，必须新增服务端可解析的路径 |
| 页面模板 | `front_end/index.html` 是静态首页，无 OG 标签；后端 catch-all 用 `TemplateView` 返回它（`back_end/saolei/saolei/urls.py:45`） | 需要新增带动态 OG 标签的响应，且新路径必须放在 catch-all 之前 |
| 棋盘数据 | `VideoModel.board` 是雷分布位图（`models.py:169`、`utils/parser.py:66-79`）；`level` 给出尺寸（`VIDEO_BOARD_PLAN.md:33`） | 两者足以推导完成画面，无需重新解析录像；历史录像 `board` 可能为 `null` |
| 可见性 | `a` 未审核、`b` 冻结、`c` 通过、`d` 标识不匹配、`e` 外部审核；`ongoing_tournament=True` 表示比赛录像尚未公开（`videomanager/api.py` 的 `_visible_video_info`、`_can_request_video`） | 两个分享端点都要求 `state` 为 `c`/`d` 且 `ongoing_tournament=False`，审核通过不等于比赛已揭晓 |
| 尺寸上限 | 当前支持的最大棋盘为 24×30（`config/text_choices.py` 的 Level） | 分享绘图上限与当前支持配置同步；将来支持更大尺寸时，须同步更新限制、测试及资源估算 |
| 图像依赖 | 后端无 Pillow 等图像库（`requirements.txt`） | 需新增依赖，见第 4 节开销分析 |
| 分享组件 | 无录像分享组件；有通用 `CopyToClipboard.ts`、`IconCopy.vue` 可复用 | 前端改动集中在录像页一个按钮 |
| 图片转发 | `videomanager/api.py` 已有 `X-Accel-Redirect` 先例，Nginx 提供 `/internal-media/` 内部文件路径 | 所有图片仅通过 `X-Accel-Redirect` 交给 Nginx，Django 不直接返回 PNG；接受偶发文件竞态失败 |

## 3. 技术方案

### 3.1 分享链接与 OG 页面

新增服务端路径，例如 `GET /video/<int:id>`：

1. 按 ID 读取 `VideoModel`，在 API/视图层校验 `state` 属于公开集合（`c`、`d`）且 `ongoing_tournament=False`；不满足条件时统一返回 404，不输出玩家、成绩、棋盘或其他录像元数据。即使访问者是本人或管理员，分享端点也不放宽匿名公开条件。
2. 返回一段最小 HTML，包含：

   - `og:type=website`、`og:url=<绝对 URL>`、`og:title`、`og:description`
   - `og:image=<图片 API 的绝对 URL>`、`og:image:width`/`height`（服务端按 `level` 推导的行列数与 24px/格动态填写，例如 16×30 棋盘为 720×384；与绘图共用尺寸计算，缺少 board 时填写共用占位图的实际 192×192 尺寸）
   - `twitter:card=summary_large_image`
3. 用 `<meta http-equiv="refresh" content="0;url=/#/video/<id>">` 跳转回站内页面；页面同时放一个普通链接作为兜底。

注意点：

- 新路径注册在 `saolei/urls.py` 的 catch-all 之前，使用不带尾斜杠的 `path('video/<int:id>', ...)`。
- `og:image` 必须是绝对 URL 且爬虫可匿名访问。规范地址统一使用 `videomanager/config.py` 中的 `SHARE_PREVIEW_SITE_URL`（当前 `https://openms.top`），不从请求的 Host 或代理协议推断，避免错误域名及 HTTP 地址；替换公开站点域名时同步修改该配置。
- `og:image` 指向包含绘图版本的图片 API 路径（如 `/api/video/share/v1/<id>.png`），由后端检查缓存或按需生成文件，再通过 `X-Accel-Redirect` 交给 Nginx，无需提前预热录像缩略图；爬虫拿到的是不带 `#` 的普通 URL。绘图版本必须同时进入对外 URL 与内部缓存文件名，不能只修改内部文件名。
- HTML 使用 Django 模板自动转义玩家名、标识等文本；秘密上线时核对 QQ 是否读取 OG 标签，以及零秒 `meta refresh` 是否影响抓取。实测通过前不开放分享 UI。

### 3.2 图片 API

新增 Ninja 端点，例如 `GET /api/video/share/v1/<int:id>.png`；只接受明确支持的版本，未知或已停用的版本返回 404：

```text
请求 → 查录像 + state、ongoing_tournament、尺寸校验 → 按内容摘要定位缓存
     → 缓存存在：准备内部转发路径
     → 缓存缺失：从 board 解出雷分布 → 生成 PNG → 唯一临时文件 + 原子替换
                 → 生成或写入失败：记录日志并返回错误
     → 尽力更新 mtime、Redis 参考计数及清理任务入队标记
     → Django 返回 X-Accel-Redirect 和空响应体 → Nginx 读取文件并发送图片
       （转发后文件消失或不可访问时允许失败，不增加回退路径）
```

- **数据来源**：只读 `VideoModel.board`（bytes）和 `level` 字段，不读录像文件、不启动 `ms_toollib` 解析子进程。完成画面由雷分布唯一确定，无需重放。
- **位图解码**：按 `VIDEO_BOARD_PLAN.md:29-39` 的编码反向解包——行主序、LSB-first，位索引 `r * columns + c`，1 表示雷。`board` 为 `null` 时返回占位图；与 `level` 尺寸不符时返回 404。
- **尺寸推导**：`b` 8×8、`i` 16×16、`e` 16×30；`c{rows}_{columns}_{mines}` 直接解析 `rows`/`columns`。与 `board` 字节数 `(rows * columns + 7) // 8` 校验一致。
- **位图有效性**：校验末字节高位补零，实际雷数与等级雷数一致；不一致返回 404。
- **尺寸限制**：在位图展开、命中图片缓存或创建画布前校验 `1 <= rows <= 24`、`1 <= columns <= 30`，最多 720 格；自定义等级还需校验雷数范围。按 24px/格绘制时，画布最多 720×576 像素，不因库中存在更大的历史棋盘而自动放宽。限制与项目当前支持的最大棋盘同步维护，将来支持更大尺寸时须同步更新本限制、边界测试、内存/CPU 与容量估算；超限返回 404。
- **画面生成**：遍历格子，非雷格统计周围 8 邻域雷数得 0–8，雷格标记为雷。直接复用 `putianyi889/minesweeper-board` 0.7.0 的 `cellup`/`celldown`/`num*`/`mine` SVG，由 resvg 一次性栅格化为随代码发布的小图集 `share_preview_assets/cells.png`，保留 MIT 授权。运行时用 Pillow 拼接，不加载 SVG 转换器或字体绘制数字。不使用 `flag`（完成画面不保留插旗）。
- **绘制**：图片先以 RGB 绘制，再 `convert('P', palette=ADAPTIVE, colors=16)` 并 `optimize=True` 输出调色板 PNG（实测 16×30 棋盘约 8.8 KB，见 4.4）。
- **响应方式**：任何情况下均不由 Django 直接返回 PNG 字节，包括缓存命中、现场生成、占位图、文件系统错误及 `DEBUG` 本地调试。正常结果统一返回 `X-Accel-Redirect`；生成或写入失败返回错误，允许文件在转发后被清理导致的偶发失败，不增加 Nginx `error_page` 回跳或其他补偿端点。
- **限流**：这是匿名公开端点，用 Django ratelimit 做 IP 限流；所有 API 都需要限流的规则同样适用。
- **失败处理**：满足公开条件且尺寸有效、`board` 为 `null` 时，通过 `X-Accel-Redirect` 返回共用占位图，不按录像 ID 持久化占位图；`board` 与 `level` 尺寸不符、尺寸超限、非公开 state、比赛尚未公开、录像不存在返回 404。Django 阶段发现生成、缓存访问或落盘失败时记录日志，返回不含内部细节的错误（例如 503）；Nginx 阶段文件消失或不可访问时允许直接返回其错误。命中旧缓存也不能跳过可见性及尺寸校验。

### 3.3 文本元数据

OG 标题与说明从 `VideoModel` 生成，不从棋盘或录像文件读取：

| 字段 | 来源 | 示例 |
| --- | --- | --- |
| 玩家 | `player.realname` / identifier | 玩家名 |
| 难度 | `level`（`config/text_choices.py` 的 Level） | 高级 / Expert |
| 模式 | `mode` | 标准 |
| 3BV | `bv` | 255 |
| 用时 | `timems` | 68.320s |
| 上传时间 | `upload_time` | 2026-11-24 |

说明文本不写入图片，只放在 OG 标签里。这样既满足“预览文本包含本局元数据”，又避免引入中文字体与跨平台文字排版，图片保持纯棋盘。

### 3.4 缓存：静态文件 + Redis 参考计数 + 后台清理

图片字节缓存在本地文件，Redis 只保存参考计数与清理任务入队标记，两个固定键不随录像数量增长，没有容量问题。图片 API 检查或生成文件后，始终通过 `X-Accel-Redirect` 交给 Nginx 发送图片，Django 响应体为空。接受转发与文件清理之间的偶发竞态失败，不实现图片字节直返、Nginx 错误回跳或其他补偿。目录扫描、排序与批量删除全部交给现有唯一的 `db_worker_robust` 执行，请求不扫描目录，也不等待清理完成。本功能只影响分享端点，故障不阻塞网站正常服务，可接受线上测试。

- **存放路径与内容身份**：`MEDIA_ROOT/thumbnail/`，与现有 `videos/`、`avatar/` 并列。文件名为 `<video_id>-v1-<content_digest>.png`，摘要由 `board` 与 `level` 生成，绘图版本单独保留。这样旧请求晚于重新解析完成写入时，只会留下旧摘要的冷缓存，不会覆盖新棋盘的缓存。生产目录为 `/root/saolei/media/thumbnail/`；本地开发为 `BASE_DIR/assets/thumbnail/`（`DEBUG` 下 `MEDIA_ROOT = BASE_DIR/'assets'`，见 `settings.py:203`）。无需新增环境变量。
- **无锁并发**：本功能不使用文件锁、分段锁或 Redis 执行锁。接受同一图片重复生成、缓存被并发删除、mtime 或参考计数偶发失真。每个请求以本次校验通过的录像数据定位或生成对应图片；不为消除转发后的文件竞态增加互斥或回退。
- **写入方式**：先编码完整 PNG，写入同目录下由标准库生成的唯一临时文件，最后 `os.replace` 原子替换，避免并发请求共用临时文件或读到半截 PNG。文件权限设为 0644，父目录允许 Nginx worker 遍历。目录创建、编码、写入或替换失败时记录日志并返回错误，即使内存中已有 PNG 也不直接返回图片；临时文件使用不同扩展名，在 `finally` 中尽力清理。
- **读取方式**：`og:image` 始终打图片 API。Django 检查文件是否存在，缺失则生成并落盘；成功后仅返回 `X-Accel-Redirect: /internal-media/thumbnail/<video_id>-v1-<content_digest>.png`，复用现有 `internal` location，由 Nginx 读取、发送文件。Django 不全量读取缓存 PNG，也不为 Nginx 之后的文件打开失败补偿。本地调试同样需要通过配置了该内部路径的 Nginx 入口验证，直连 Django 不提供 PNG 响应体。
- **占位图**：首版部署时运行 `python manage.py prepare_share_preview`，在 `MEDIA_ROOT/thumbnail/placeholder-v1.png` 准备一个 192×192 的共用 PNG，经同一 `X-Accel-Redirect` 路径发送。该文件不进入录像缓存计数或清理名单；缺失或不可访问时允许失败，不在请求中直接返回占位 PNG 字节。
- **失效**：录像删除后，在事务提交后尽力删除已知路径的缓存并扣减参考计数，不在请求内枚举目录；删除失败或并发生成留下的文件交由后台冷数据清理。`board`/`level` 重新解析变更后按新摘要定位或生成，旧摘要缓存由后台回收。绘图样式变更时同时更新 `og:image` 的对外版本路径与内部文件名。图片响应采用 `Cache-Control: no-cache`，占位图也不设置长期缓存。站外平台已经生成的旧卡片何时重新抓取仍由平台决定，不承诺即时刷新。
- **访问时间**：每次命中或生成后，尽力用 `os.utime` 把文件 mtime 更新为当前时间；失败记录日志，继续按正常方式转发，不为修复访问时间读取或返回图片字节。mtime 只作为冷数据排序参考，允许在并发删除、替换或访问中失真。不用 atime，因为部分文件系统用 `relatime`/`noatime`，不可靠。
- **Redis 参考计数**：在 `videomanager/cache.py` 中维护固定键 `video:share-preview:count`。成功写入且写入前观察为新增 PNG 时递增，成功删除后尽力递减，未落盘不递增；接受并发重复生成导致多计或覆盖导致少计。计数包括所有绘图版本与内容摘要的 PNG，不包括共用占位图和临时文件。计数仅用于廉价触发任务，不增加严格同步或事务协议；更新失败不影响图片响应。
- **冷数据清理（优先删除最久未访问的缓存）**：
  - 触发：参考计数达到 2 万张时，只入队后台任务；计数键缺失、为负等明显异常时，也入队一次后台校准。用固定 Redis 键 `video:share-preview:cleanup-pending` 的 `SET NX` 加有限 TTL 合并入队，入队失败记录日志并允许后续重试；TTL 避免任务异常退出后永久无法再次触发。Redis 不可用不影响当前图片响应，恢复后的缺失计数由后续访问触发校准，也可手动运行管理命令。
  - 任务：由现有单 worker 串行执行（`start.sh:22-25` 只启动一个 `db_worker_robust`，`run_background.sh:24-25` 执行该进程），所以重复入队也依次扫描，不会同时扫描。Redis 入队标记用于减少重复排队，不承担执行互斥。实际扫描缓存目录内匹配图片命名规则的 `*.png` 普通文件，不跟随符号链接，以文件系统实际数量判断是否需要清理，不凭 Redis 数值决定删除数量。
  - 删除：实际数量达到上限时，按本次扫描所得的 mtime 升序尝试删除最旧的一批，目标为上限的 80%（1.6 万张）。文件已经消失则忽略，不可访问则记录日志并继续处理其他文件；允许期间发生访问、生成或替换，不加锁或等待。文件在转发后、Nginx 打开前被删除时允许请求失败，不增加特殊处理。临时文件、共用占位图及其他目录内容均不删除。
  - 回写：任务结束前重新扫描剩余 PNG 数量，并覆盖 Redis 参考计数；允许扫描或回写期间的并发新增、删除造成偏差，后续触发时再以实际目录校正。并发新增或文件不可删除导致未达到目标时允许暂时超限，后续访问达到阈值后继续触发清理，不在 Web 请求内补扫。
  - 兜底：`python manage.py cleanup_share_previews [--count-only]` 入队同一个后台任务，支持只校准计数模式并输出任务 ID；命令自身不扫描目录，不另起 worker，也不直接调用扫描函数，保持所有清理入口在现有单 worker 中串行执行。不依赖 APScheduler 定时扫描。任务失败记录日志，入队标记不能永久残留。旧绘图版本、旧内容摘要的缓存与当前缓存一并计数、排序和回收。
- **容量**：按需生成，只缓存公开且尺寸合规的录像，不预热历史。2 万张是异步清理阈值，允许竞态下暂时超限，不是严格磁盘配额。图片及 mtime 保存在本地，Redis 只保存两个固定小键。

### 3.5 前端分享入口

- 首版不增加或展示分享按钮、导航、提示等 UI，维护者直接访问 `/video/<id>` 验证；隐藏 UI 不替代服务端可见性检查。
- 秘密上线并完成 QQ 验收后，再在录像分析页加入“复制链接”按钮，生成 `/video/<id>` 绝对 URL，复用 `CopyToClipboard.ts`。仅为满足公开条件的站内录像提供入口。
- 按钮位置与文案按现有 UI 风格处理，不影响录像播放与导出。

## 4. Pillow 的内存与 CPU 开销分析

4.2–4.4 保留最初的资源与格式估算；当前实现的本地基准见 4.5，不能据此认定 Linux 生产环境具有相同性能。生成路径只读模型字段，无录像解析、无子进程。

### 4.1 依赖本身

- Pillow 提供预编译 wheel，安装无需本地编译；运行时是 C 扩展，不常驻额外进程。
- 不引入 ImageMagick 等外部二进制，部署面较小。

### 4.2 单次生成的内存

| 阶段 | 估算 | 说明 |
| --- | --- | --- |
| `board` bytes | 最大 24×30 为 90 B | `(rows * columns + 7) // 8`；绘图前强制尺寸上限 |
| 雷分布矩阵 | 约 10 ~ 30 KB | 最大 24×30 的 Python 整数数组 |
| Pillow RGB 画布 | 宽×高×3 字节 | 16×30 棋盘按 24px/格约 720×384 ≈ 830 KB；24×30 约 1.2 MB |
| 调色板转换与编码缓冲 | 约画布的 2 ~ 3 倍 | 峰值约 2 ~ 4 MB |
| PNG 输出 | 约 8.8 KB | 实测 16×30 混合数字/雷/明暗格，见 4.4 |

单次请求主进程峰值内存主要在绘图阶段，约数 MB；不再启动解析子进程，没有额外的解释器基线内存。现场生成时短暂持有编码后的 PNG 字节用于落盘，缓存命中时 Django 不读取完整图片，文件内容由 Nginx 发送。

### 4.3 单次生成的 CPU

| 阶段 | 估算 |
| --- | --- |
| 位图解包 + 邻雷统计 | 数百微秒 |
| Pillow 绘制数百至数千色块 | 1 ~ 5 ms |
| 调色板转换 + PNG 编码（zlib，单线程） | 2 ~ 10 ms |
| **合计（未命中缓存）** | **约 5 ~ 20 ms** |
| 命中缓存（本地文件） | API 查询录像并校验可见性、尺寸，按摘要检查文件、尽力更新 mtime，再返回 `X-Accel-Redirect`；不解析录像、不绘图、不读取完整 PNG |

对 Web 请求而言，这个量级可以接受，但仍建议限流；若后续访问量上升，可把生成移到 Django Tasks 后台任务，请求端只读文件。

以上生成耗时不代表完整 HTTP 请求耗时，数据库查询、Redis 参考计数和任务入队需另计；全目录扫描、排序和删除不进入请求路径。基准测试需覆盖 24×30 上限、缓存命中、未命中，以及清理任务运行期间的请求延迟。将来扩展支持尺寸时同步重测。

### 4.4 格式与容量实测

用贴近真实 SVG 素材配色的 16×30 完成棋盘（混合翻开的空白格、数字 1–6、雷）在本地实测：

| 格式 | 体积 |
| --- | --- |
| RGB PNG（默认） | 23,127 B |
| RGB PNG（optimize） | 22,097 B |
| **调色板 16 色 PNG（optimize）** | **8,775 B** |
| WebP 无损 | 9,112 B |
| WebP 有损 q90 / q80 | 43,822 B / 34,118 B |

结论：选调色板 PNG。WebP 无损体积没有优势，有损反而因色块边缘噪声显著变大；SVG 单素材仅 111–567 B，但 `og:image` 对 SVG 兼容性差，不直接用。emoji 文本也无法满足卡片行数与对齐要求。

容量：按 16×30 样本的 8.8 KB/张，1 万条约 88 MB，2 万张约 176 MB；这不是 24×30 棋盘的单图上限或严格磁盘上限，实施时补测最大支持棋盘。图片字节不进入 Redis，参考计数达到 2 万张后由后台扫描实际目录并清理至约 80%，允许竞态及删除失败造成临时超限。恶意遍历 ID 会放大生成次数，需要共同依靠限流、文件缓存、公开性与尺寸校验及后台清理约束成本。

### 4.5 当前实现的本地基准

2026-11-24，Windows、Python 3.12.10、Pillow 13.0.0；每种尺寸生成 100 次，记录第 2–100 次的中位数。高级使用本地库中公开录像 #403332 的真实 board，其他尺寸因没有对应非空 board，使用固定种子 `20261124` 的合成棋盘。

| 棋盘 | PNG 体积 | 生成中位数 |
| --- | ---: | ---: |
| 8×8 / 10 雷 | 1,799 B | 2.6 ms |
| 16×16 / 40 雷 | 4,638 B | 10.1 ms |
| 16×30 / 99 雷（真实录像） | 8,391 B | 17.4 ms |
| 24×30 / 200 雷 | 13,531 B | 27.8 ms |

最大尺寸本轮观测到单次最高约 50.3 ms，100 次生成期间的 RSS 采样增长约 4.8 MiB；采样间隔为 1ms，不是精确的单次请求内存峰值。初始 5–20ms 估算不适用于全部支持尺寸。按本次最大样本估算，2 万张约 271 MB，未计文件系统开销，也不是容量上界。

测量只覆盖绘图与编码，不含数据库、限流、Redis、入队及 Nginx 传输。脚本、完整数据及样图位于 `.tmp/checks/share-preview-implementation-20261124/`。

## 5. 安全与稳定性

- 权限：图片 API 与 OG 页面都在 API/视图层要求 `state` 为 `c`/`d` 且 `ongoing_tournament=False`，缓存命中也执行检查；未揭晓的比赛录像不输出任何元数据或图片。
- 限流：两个端点均加 ratelimit；管理端 API 的 CSRF 规则不涉及这些匿名只读端点。
- 输入校验：`id` 为正整数，不存在时统一处理，不回显原始异常。
- 数据校验：先限制行数不超过 24、列数不超过 30、总格数不超过 720，再校验位图字节数；缺失 board 返回共用占位图，尺寸无效或超限返回 404。将来支持更大棋盘时须同步更新限制及估算。
- 缓存文件名只含录像 ID、明确支持的图片版本与棋盘内容摘要；绘图版本同时进入 `og:image` 对外 URL。所有图片只经 `X-Accel-Redirect` 发送，不新增 Nginx 公开静态入口，外部直接访问 `/internal-media/` 仍须被拒绝。
- 本功能不创建或获取文件锁、分段锁、Redis 执行锁；Redis 入队标记只合并排队请求。清理及只校准操作均由现有单 worker 串行执行。冷数据任务只操作缓存目录内匹配命名规则的 PNG 普通文件，不跟随符号链接，不删除临时文件或其他目录内容。
- 允许偶发文件竞态导致请求失败，不增加直接返回 PNG、Nginx 错误回跳或其他补偿。Django 阶段生成或写入失败时记录日志并返回不含内部细节的错误；mtime 更新、Redis 计数或入队失败不改为返回图片字节。并发写入仍使用唯一临时文件和原子替换，避免留下半张 PNG。
- Redis 计数只是任务触发参考，后台以实际目录为准并在结束时回写；Redis 或任务入队故障不改为在请求内扫描目录。

## 6. 测试与验证

按项目规范分别维护：

- **后端单元测试**：图片 API 的成功、文件缓存命中、公开/非公开 state、比赛未揭晓、录像不存在、`board` 缺失/尺寸不符、限流；覆盖 `state=c/d` 且 `ongoing_tournament=True`，包括已生成缓存、本人及管理员访问。验证生成文件的 PNG 魔数、尺寸与调色板模式、正常命中时 mtime 更新、唯一临时文件和原子写入；成功的 Django 响应包含正确 `X-Accel-Redirect` 且响应体为空，包括占位图及 `DEBUG=True`。并发同一 ID 可重复生成，不创建锁文件。
- **画面正确性测试**：构造已知雷分布的小棋盘，验证邻雷数计算、雷格显示、尺寸与位图解包一致（行主序、LSB-first）。
- **尺寸边界测试**：24×30 可生成，25×30、24×31 及更大历史棋盘返回 404，即使位图长度正确或已有缓存也不能绕过；测试非法自定义尺寸与雷数，确保在创建画布前拒绝。
- **缓存故障与竞态测试**：Django 检查时文件缺失则生成并落盘；目录无法创建、编码或写入/替换失败时返回错误，即使已生成 PNG 也不直返；mtime 更新、Redis 计数或入队失败时不切换为图片字节响应。覆盖两个请求并发原子替换及清理期间重复生成，不要求只生成一次或计数完全准确；不要求转发后文件被清理时仍能成功返回图片，也不为该窗口增加补偿测试。
- **缓存清理测试**：请求及管理命令只入队，不扫描目录；阈值触发与任务去重、标记 TTL/失败恢复、计数缺失与高估/低估的校准、Redis 故障。后台按真实 PNG 数量决定是否删除，验证最旧优先、80% 目标、任务结束回写实际数量，以及跳过临时文件、非 PNG、符号链接和不可删除文件；覆盖文件在扫描、读取元数据和删除间消失的处理，允许计数偏差，不要求强一致。
- **失效测试**：事务提交后尽力删除已知缓存；重新解析后内容摘要变化，旧请求的迟到写入不会覆盖新棋盘缓存；共用占位图不按录像 ID 留存；绘图版本改变时 `og:image` 的对外 URL 和内部文件名同时变化；未知/停用版本返回 404。
- **OG 页面测试**：标签齐全、绝对 URL、跳转目标、玩家与标识文本转义；非公开录像不暴露图片、标题或成绩。
- **Nginx 验证**：通过 Nginx 入口确认冷生成、缓存命中及共用占位图均通过 `X-Accel-Redirect` 返回完整 `image/png`，权限拒绝有效，`Cache-Control` 符合约定，外部无法直接访问内部文件路径。不配置缩略图读取失败后的 `error_page` 回跳；允许转发后的偶发文件竞态失败。Django 测试客户端不能替代这项验证。
- **前端组件测试**：第二阶段开放 UI 时，验证按钮仅出现在可分享的站内录像上，复制链接正确；Cypress 命令交用户执行。
- **基准测试**：用真实 `board` 数据及 24×30 上限测生成耗时、峰值内存和清理期间请求延迟，核对第 4 节估算。
- **秘密上线验收**：第一阶段只部署后端能力，不展示相关 UI；由用户手动构造分享链接，在目标 QQ 客户端中验证卡片、图片裁切、文字、点击后的跳转、`meta refresh` 对抓取的影响、缓存更新及容量变化。通过后再实施并开放 UI。
