# 录像准入放宽与玩家认证计划

状态：业务规则已按 2026-11-13 的 Q1–Q12、R1–R5 答复及后续补充确认，代码已按本计划实施，生产与 E2E 验收仍待执行。第 8、9 节保留决策记录，目前无待确认的业务规则；文中标为“建议”的技术方案已在实施时细化，细化结果见文末「实施状态」。

## 1. 已确认需求

所有原本要求实名的操作，改为满足以下任意一项即可：

1. 已实名。
2. 已通过玩家认证。

MSGames 绑定不作为独立准入条件。绑定本身已需管理员审核，管理员可以参考已有绑定情况主动提交玩家认证任务；绑定、解绑或重新验证均不自动授予或取消玩家认证。

新增 `UserProfile.verified` 字段。玩家认证通过以下途径获得：

- 站长（`is_superuser`）或管理员（`is_staff`）主动为用户认证，包括为自己认证；不要求管理操作者先有玩家认证。
- 用户向任意另一名用户发送请求，对方在七天内批准后建立认证关系；收件人可以尚未认证或已经失去认证。申请人的当前认证状态取决于认证人的认证状态，批准本身不保证申请人立即为已认证。
- 站长或管理员每次认证用户，都将目标作为一棵树的根节点：解除其原有上游边，认证目标及整个子树；不会将目标挂在管理操作者下面。管理员认证自己也沿用此规则。

取消站长/管理员自动认证：账号创建、角色升降、登录和读取资料均不因管理身份自动设置 `verified`，也不回填现有管理账号。

站长可以取消任何用户的认证；取消某节点时，同时切断该节点的入边，即解除其被上游认证的当前关系，使其成为未认证根，自身和整个子树都取消认证。后代内部的认证关系保留，不保存旧入边或操作历史。用户也可主动解除自己的被认证关系，产生相同的断开上游和级联取消结果，但只能对本人操作，不获得取消任意他人认证的管理权限。普通管理员和原认证人不能使用管理接口取消他人的认证。

即使用户因上游被取消而已经处于未认证状态，也能解除仍然保留的上游关系，再通过管理员主动认证或玩家请求补救；不设置禁止重认状态。待处理申请仍不可撤回或换人，解除已形成的认证关系是独立操作。

被取消者仍可由其他人重新认证。若有人坚持认证站长认为应取消认证的用户，站长可沿新认证关系继续向上追溯并处理；这是人际与管理判断，不增加禁止重认、独立撤销标记、特殊审批或自动追责逻辑。

申请同一时间只能发给一人，不可撤回、不可换人；收件人可以拒绝，冷却从申请时起算，拒绝不提前结束原七天窗口。没有发送与批准额度。七天按连续 168 小时计算，截止时间由 `created_at + 168 小时` 推导，恰到期即失效。申请链路内检查当前节点：未到期且未获批准则拒绝新申请，已到期且未获批准则删除后再创建；不设置定时清理任务，已批准的当前节点不因七天到期而删除。

个人设置页不设收件箱，不展示收到的申请列表。双方通过其他方式提前联系：申请人输入约定的认证方 ID 发出申请，认证方直接输入被认证方（申请人）的本站 ID 并提交认证；后端确认该用户有发给当前认证方的有效未批准申请，才受理后台任务。输入 ID 不是管理员直接认证，不能跳过已有申请或指定收件人检查。

被封禁、停用或纪念账号也可以参与认证，仍须满足对应操作的登录、角色或指定收件人权限；不为其新增认证专属禁令，也不绕过停用账号无法登录等原有机制。认证不解除封禁或停用。

公开展示当前认证状态，不展示认证来源或认证人。认证功能入口位于个人设置页。不保留认证历史：只保存当前申请和当前认证树，拒绝或到期的未批准记录在下次申请时替换；管理员直接认证、站长取消及本人解除均直接更新当前节点。站长取消和本人解除仅移除目标入边，保留后代内部的有效边。

级联消耗波动较大，所有认证与取消认证都通过 Django Tasks + `django-tasks-db` 后台执行，包括玩家批准、管理员认证（含自我认证）、站长取消及本人解除关系；即使当前没有后代也不走同步特例。API 只提交任务并返回受理结果，不等待级联，不再采用延长 HTTP 超时的方案。申请创建/过期替换与拒绝不授予或取消已生效认证，可继续使用短事务；具体任务与结果查询要求见第 4.5 节。

“准入资格”“批准认证关系”和“当前玩家认证状态”分别处理：仅实名不自动将 `verified` 设为 True；未认证的用户也可以处理发给自己的申请，但其批准不会凭空授予已认证状态。玩家认证不等于真实姓名核验，不要求填写或公开姓名。

## 3. 统一准入口径与模块边界

建议定义 API 层可复用的准入判断，逻辑为：

```text
满足身份准入 = has_realname() OR UserProfile.verified
实际操作权限 = 原有登录、角色、资源等检查 AND 满足身份准入
```

管理身份不直接满足玩家认证或身份准入。管理员可调用主动认证接口认证自己，再通过 UserProfile.verified 满足准入；读取时不计算 `is_staff OR is_superuser OR verified`。

准入判断不查询 AccountLinkQueue 或 AccountMinesweeperGames，也不根据绑定资料推导玩家认证。管理员参考 MSGames 绑定后仍使用统一的后台认证接口：任务完成后目标成为已认证根，按原规则恢复有效子树；不新增绑定事件自动认证逻辑。

- 在 `userprofile` 的 API 辅助模块统一定义实名或玩家认证的判断，供上传和比赛 API 复用；不引入账号关联查询或反向模型依赖。
- `UserVerifyTree` 同时承载当前申请和认证树，模型与写入服务放在 `userprofile`，不另建申请表或历史表；路由可拆为 `userprofile/verification/api.py`，共享输出放 `schema.py`，按现有方式注册 Ninja Router。
- 登录状态、管理员/站长角色、批准者是否为指定收件人等权限，只在 API 层检查；认证写接口在短事务内读取当前数据、校验权限并持久化任务，不把收件人 `verified` 作为批准权限。任务携带服务端确定的操作类型、操作者、目标和预期记录版本，不能由客户端指定任意任务路径或覆盖授权上下文。task/service 执行已授权命令，负责当前记录、树结构、状态传播、幂等及事务一致性，不重复操作者角色授权。
- 新增本人能力字段（暂名 `can_submit_replays`，含义为满足身份准入，仍需原有操作校验），由后端计算，上传与比赛页面共同读取，统一实名或玩家认证口径。
- 后端每次受保护操作重新判断，不信任前端缓存。该能力不代表 `verified`，也不是批准认证请求的前提。

## 4. 数据模型与认证流程

### 4.1 用户状态与认证树

新增 `verified = BooleanField(default=False)`，只记录当前状态。现有实名用户通过实名条件准入，不批量转成已认证玩家。仅绑定 MSGames 而未实名、未认证的用户不直接准入，管理员可参考绑定情况主动认证；不自动回填。站长和管理员也默认 False，可主动认证自己。角色变化不自动修改认证。

新增模型 `UserVerifyTree`，按用户指定的四个字段保存当前节点和申请，不另加 `status`、`expires_at`、`handled_at` 或历史表：

| 字段 | 类型与含义 |
| --- | --- |
| `user` | `OneToOneField`，主键，关联 UserProfile，表示当前节点；数据库主键列为 `user_id`，不再增加 id 字段 |
| `parent` | 可空 `ForeignKey`，表示当前父节点对应的用户；建议关联 UserProfile，使尚无树记录的用户也能接收申请。未批准时表示指定收件人；为空表示根节点 |
| `created_at` | 本轮申请发送时间，或管理员直接认证时间；管理员认证已有节点时显式更新，不使用仅在插入时赋值的逻辑代替 |
| `verified` | Boolean，表示根节点已获管理员认证，或当前父节点已批准入边；不表示用户当前的有效认证状态 |

两个 `verified` 的语义必须区分：`UserVerifyTree.verified` 是本节点/本条入边是否批准，`UserProfile.verified` 是有效认证结果。建议公式如下，后台任务在同一事务内修改节点并向后代传播维护后者，读接口无需递归整棵树；提交任务时不提前改变任何认证状态：

```text
无节点：UserProfile.verified = False
根节点：UserProfile.verified = UserVerifyTree.verified
非根节点：UserProfile.verified = UserVerifyTree.verified AND parent.UserProfile.verified
```

只有 `UserVerifyTree.verified=True` 的非根节点才形成有效入边；待处理申请虽有 `parent`，不应被当作已生效的认证边。遍历有效后代时须过滤该字段。父节点状态失效时，后代 UserProfile.verified 改为 False，但后代已经批准的 UserVerifyTree.verified 保持 True，才能在上游恢复后自动恢复。OneToOne 主键保证每人最多一条当前记录；拒绝或解除后无需区分历史原因。

已确认的级联行为：

- 站长取消节点 X：将 X 的 `parent=None`、树字段 `verified=False`，使其成为未认证根；X 及其全部有效后代的 UserProfile.verified=False。保留后代树记录的 parent 和 verified；X 原本就是根时同样适用。
- 用户解除自己的被认证关系：对本人的节点执行同样的切断和级联逻辑。已因上游失效而未认证，但树记录仍为已批准且有父节点的用户也可执行，不要求 UserProfile.verified=True；未批准的申请不能通过此入口撤回。
- 站长或管理员每次主动认证节点 X：由后台任务无条件覆盖 X 的当前记录为 `parent=None`、树字段 `verified=True`、`created_at=任务实际认证时间`，不受旧申请或入边阻止。X 及其全部有效后代 UserProfile.verified=True；待批准的后代不能因本次级联自动获批。排队期间不改写节点时间。
- 普通玩家批准时将申请人树记录的 verified=True，保留 parent 和 created_at；申请人及有效后代的 UserProfile.verified 按认证人状态同步。未认证的认证人也可批准，此时树字段为 True，用户字段仍为 False。
- 例：A → B → C，取消 A 后三者均为 False；管理员认证 B 后切断 A → B，B、C 为 True，A 仍为 False。以后再取消 A 不影响已独立的 B → C。
- 内部节点例：A → B → C 原本均已认证，站长取消 B 时切断 A → B，A 仍为 True，B、C 为 False，保留 B → C。A 后续状态变化不再影响 B、C；若 D 通过新的申请认证 B，则 B、C 按 D 的状态传播，不因此前撤销被业务逻辑阻止。
- 补救例：A → B → C 因取消 A 全部未认证后，B 主动解除 A → B，保留 B → C，再向 D 申请。D 即使未认证也可批准形成 D → B；此时 B、C 随 D 保持未认证，D 后续被认证则一并生效。

主动认证、请求批准、站长取消及本人解除关系必须走明确的写入入口，不把 `verified` 或树边暴露给普通资料编辑，也不放入管理员通用可写字段列表，避免绕过管理取消权限、本人操作限制或树结构校验。检查 Django Admin、清空资料及批量编辑路径。

禁止自环、祖先挂到后代及其他环，节点不能出现多个当前父节点。允许向未认证者申请后，必须在批准时校验成环，不能只检查创建申请时的树。建议已有上游关系的玩家先主动解除再重新申请，避免待办批准直接覆盖既有关系；批准前也需核对申请人期间是否被管理员认证或已建立其他关系，冲突不得静默覆盖新状态。

站长取消与本人解除可复用“切断目标入边、级联置为未认证”的业务服务，由不同 API 分别校验管理权限和本人操作权限。对已形成的新认证关系，站长可再次取消，也可向上追溯处理；服务不因历史撤销禁止重新认证，不自动处罚认证人。

### 4.2 申请、拒绝与过期替换

四个字段足以表达当前业务，不保留独立拒绝历史。状态由字段组合推导：

| parent | 树 verified | 含义 |
| --- | --- | --- |
| 非空 | False | 未批准申请，创建满七天后过期 |
| 非空 | True | 已建立的入边，不按七天过期；当前有效认证状态继续看 UserProfile.verified |
| 空 | True | 管理员直接认证的根 |
| 空 | False | 未认证根，或被拒绝后保留冷却的当前节点，不区分来源 |

收件人拒绝未批准且没有认证写任务占用的申请时，用短事务将 `parent=None`、树 verified=False，并保留 created_at。原收件人因此不能再次批准，申请人仍须等到 `created_at + 168 小时` 才能新建申请；无需增加 rejected 字段。拒绝后重新进入设置页只展示“未认证”和剩余冷却，不提供单独的拒绝历史状态。

申请链路先检查目标是否有尚未结束的认证写任务，有则返回处理中；没有时在同一短事务内锁申请人并查询当前 UserVerifyTree：树 verified=False 且未满七天时拒绝新申请；已满七天则删除旧节点，再创建 `parent=新收件人`、`verified=False`、`created_at=当前时间` 的记录。无节点时直接创建。树 verified=True 的根或已批准入边不按时间删除，先按既有规则通过后台任务解除已建立关系。判断使用树字段，不能用 UserProfile.verified，否则会误删上游尚未认证的已批准入边。

删除与创建一起提交，不先删除再在另一事务创建；仅删除当前节点记录，不删除用户或其有效后代。parent 的外键目标及删除策略须保证这一行为，不能用对子节点的级联删除实现过期替换。待处理申请不允许撤回或换人，不新增定时清理任务。历史 parent、旧时间、旧批准和拒绝结果均不另外保存。

### 4.3 请求处理与七天边界

- 只有当前树记录 parent 指定的另一名用户才能在七天内提交批准任务，不要求其已认证。API 以服务器受理时间判断 `accepted_at < created_at + 168 小时`，恰到期拒绝受理。按时受理的批准任务不因排队跨过截止时间失效；worker 核对原申请版本和该受理时间，不把实际运行时间当成批准提交时间。
- 申请不可撤回、不可换人，可被拒绝；同一时间只能向一人申请。冷却从申请创建时算，拒绝不重置期限、不提前解锁；例如 11 月 13 日申请、15 日被拒，20 日同一时刻才能再申请。不新增发送或批准额度，也不追加发送/批准速率额度。
- 收件人未认证或失去认证均不影响其处理请求；批准时读取其状态用于计算申请人及后代的认证结果，不把 True 作为通过权限。被封禁、停用或纪念账号不增加认证专属资格排除；实际无法登录的账号不会因此获得会话。
- 建议已认证申请人不再创建新申请。本人当前申请读取按期限及任务受理状态返回结果，不在 GET 中写库，不提供收到申请的列表。认证方输入申请人 ID 后，API 直接查该 UserVerifyTree，检查 parent 等于当前用户、树 verified=False 且受理时未到期，再捕获当前 created_at/parent 作为任务预期版本。客户端不必先拉申请列表或取得申请时间；任务执行时仍检查版本和成环风险，失效判定不依赖旧记录已删除。
- API 受理批准只返回“任务已提交”。后台任务执行时在同一事务设置树 verified=True，按认证人届时的有效状态更新申请人及有效后代 UserProfile.verified；完成后才展示“对方已批准”，并区分“目前已认证”。任务失败不部分生效，不保存批准事件历史。
- 重复批准已成功请求只返回既有结果，不重新挂接树或写回 True，尤其不能让旧成功请求在站长取消或本人解除后复活。管理员明确发起的新认证操作则切断目标上游边，建立新的已认证根并恢复其子树。
- 收件人失去认证时不取消待办、不删除请求，也不要求其恢复认证后才能批准；待办仍遵守原七天期限。申请人期间被管理员认证等关系变更须在批准事务内检查，不能用旧请求覆盖新根状态；具体冲突响应在实施时沿用统一状态冲突机制。

### 4.4 并发、级联与复用

复用 `accountlink/services.py::save_verified_account_link` 的事务和用户行锁做法，以及 `ClassicBindRequest` 的期限和幂等处理经验。当前申请和树统一使用 UserVerifyTree，不混用外站关联队列，不额外引入通用审批工作流或历史存储。

单用户行锁不足以防止遍历子树时并发插入或换父节点。建议所有修改认证状态或树边的事务先获取同一个数据库协调锁（例如锁定专用协调行），再按用户 ID 顺序锁定涉及的用户和请求，重新判定权限、树结构、期限及冷却后执行。创建树边、管理员将目标设为新根、级联取消和本人解除关系必须遵守同一协议，避免漏掉新后代或发生环；收件人未认证不会自然阻止环，尤其需要验证双方互相申请及并发批准。

级联操作在后台任务的一个事务内完成，分批查询子节点和批量写入不能分批提交。所有受影响节点更新 `date_updated`，批量更新不会自动执行实例 save 或逐用户信号，须显式处理缓存失效与事件。任务结果只返回操作结果、目标和影响数量，不返回整棵树或认证关系；排队与运行期间保留上一次完整提交的认证状态，取消任务尚未完成时也不提前报告认证已取消。

OneToOne 主键保证每人一条当前节点；创建申请仍锁 UserProfile 行，在尚无树记录时也能串行检查冷却和插入，不依赖锁不存在的节点。认证方按 ID 提交后，由 API 锁定并捕获当前 `user_id + created_at + parent` 标识本轮申请，后台任务再次核对，旧任务不得误处理重新创建后的记录。拒绝也按输入 ID 在短事务中检查当前申请的接收者和未批准状态。行锁并发验证按 [Django select_for_update 文档](https://docs.djangoproject.com/en/6.0/ref/models/querysets/#select-for-update)使用真实 MySQL 的 `TransactionTestCase`。

过期未批准申请的删除与新申请创建只在申请链路内执行，和收件人批准遵守同一锁协议；并发时只能出现旧请求及时批准，或旧请求已过期被替换这两类一致结果，不增加清理任务或额外过期调度机制。

### 4.5 全后台认证与取消认证

复用现有 Django Tasks + `django-tasks-db`，任务定义放在 `userprofile/tasks.py`，可按操作类型统一调度或拆分任务。项目已有 `medal/tasks.py` 的数据库入队、READY/RUNNING 查询与防重复做法，以及 `common/management/commands/db_worker_robust.py` 的 worker 生命周期处理，不另引入任务队列或认证历史表。

- **受理**：认证、取消认证接口只作登录/角色/本人/指定收件人、申请期限及参数等短检查，可靠持久化任务后返回 HTTP 202 与 task_id。复用数据库任务后端，使提交控制与任务入队在短事务中一致落库；入队失败不返回已受理。不得先同步改 parent/树 verified，再把用户状态传播留给任务。
- **执行**：worker 获取认证写入协调锁后检查当前节点及预期版本、是否仍可执行、是否成环，在一个事务中修改树和全部有效后代状态。申请创建、过期替换和拒绝也遵守同一写入协议，遇到正在执行的长事务应快速返回“处理中”，不能让短 API 等待整次级联。
- **顺序**：管理员认证、取消、本人解除和玩家批准均按认证写任务的受理顺序串行执行，防止较早的认证在较晚的取消之后落地。多 worker 下使用队列协调机制保证顺序，不能仅假定相同优先级天然 FIFO；不按相反操作合并任务。协调锁也防止长遍历期间并发加边或换根。
- **单节点待办**：同一目标已有 READY/RUNNING 认证写任务时，重复操作返回已有 task_id；不同操作先返回处理中，待当前操作结束后可再提交。申请创建/拒绝/过期替换不得改写正被该任务引用的记录，避免按时提交的批准在排队期间被删掉。此为事务冲突处理，不是发送或批准额度。
- **七天边界**：批准是否及时以 API 受理时间为准，任务参数保存 accepted_at 和原申请 created_at/parent；队列等待不使按时受理的批准过期。任务执行时使用认证人当前状态传播，不把受理时的有效认证快照用于赋值。新申请和管理员直接认证各自的 created_at 含义继续按第 4.1 节处理。
- **幂等与失败**：使用任务标识、当前记录版本及执行协调保证同一已受理任务至多产生一次业务变更。重试原任务不应在已有新关系时重新切边或重新认证；失败先回滚整次树变更，重试仍校验原上下文。业务提交成功而任务完成标记未保存的中断窗口也须能识别，不能只依赖任务状态判断可重放；利用现有任务记录与事务配合实现，不为此扩展四字段树模型。
- **结果查询**：提供仅提交者可访问的任务状态接口，使用 DBTaskResult 的 READY/RUNNING/SUCCESSFUL/FAILED 及业务结果；对已失效的申请等状态冲突给出明确结果，不显示伪成功。前端在本次操作页面显示排队/处理中，按需查询至完成后重取资料，也可离开页面后回到设置页查看本人任务。任务不是认证历史，按既有任务清理机制短期保留结果，不清理 READY/RUNNING，不永久保存操作流水。
- **运行维护**：普通 HTTP 请求与状态查询继续使用原超时，不配置认证接口长时例外，不提高全局 Web 超时。worker 的执行时长、数据库锁等待与进程管理由后台任务运行环境管理；监控耗时、节点数、失败及积压，优化批量查询与写入，不以固定 HTTP 时长猜测子树规模。复用 `db_worker_robust` 时注意其会在启动恢复流程将遗留 RUNNING 标为 FAILED，需结合业务幂等核对是否已提交，再安全重试。
- **交互**：202 只表示入队，认证及取消均在任务完整提交后生效。页面可查询自己刚提交的任务进度和结果，此为主动操作反馈，不增加认证申请的邮件、未读催办或其他主动提示。入队请求发生网络超时时先查询/去重，不自动提交第二份写任务。

## 5. API 与前端计划

### 5.1 API 草案

路径仅为讨论用，最终以 Ninja Schema 和自动文档为准。

| 操作 | 建议入口 | 权限与行为 |
| --- | --- | --- |
| 查看本人认证与准入 | 复用登录响应、自动登录、`GET /api/userprofile/info/0` | 返回 `verified` 和本人准入能力，统一各登录途径 |
| 发起请求 | `POST /api/userprofile/verification/requests` | 登录用户，只能以自己为申请人；固定任意另一名用户为收件人，在链路内拒绝未到期旧申请，或删除过期未批准申请并新建 |
| 查看本人当前申请 | `GET /api/userprofile/verification/request` | 仅返回本人当前申请/冷却与任务受理状态；没有收到申请的分页列表或收件箱接口 |
| 按 ID 认证 | `POST /api/userprofile/verification/requests/{user_id}/approve` | 认证方直接输入申请人 ID；服务端读取当前记录，校验存在、parent 为当前用户、未批准和七天受理期限，捕获申请版本，返回 202 + task_id |
| 按 ID 拒绝 | `POST /api/userprofile/verification/requests/{user_id}/reject` | 同样直接输入申请人 ID，服务端校验该申请发给当前用户；无认证任务占用时短事务拒绝，不执行级联 |
| 本人解除关系 | `POST /api/userprofile/verification/detach` | 仅本人；校验当前关系后返回 202 + task_id，后台切边并级联取消，已经未认证但仍有关系时也可提交 |
| 主动认证 | `POST /api/userprofile/admin/verification/grant` | `is_staff OR is_superuser`，可认证自己；返回 202 + task_id，后台强制目标设根并认证有效子树 |
| 取消认证 | `POST /api/userprofile/admin/verification/revoke` | 仅 `is_superuser`；返回 202 + task_id，后台切断目标入边并级联取消；不得排除管理员/站长目标 |
| 查询任务结果 | `GET /api/userprofile/verification/tasks/{task_id}` | 仅任务提交者；校验任务路径属于认证模块，返回处理状态及必要结果，不泄露任务参数或认证关系，不创建认证历史表 |

不提供撤回或更换收件人接口。普通接口复用登录装饰器；按用户此次明确决定，发送和批准不添加业务额度或速率限额，此项优先于仓库普通接口一般限流约定。其他只读接口按既有规范配置 `django-ratelimit`。认证专用管理接口无需限流，须有 CSRF；站长取消使用 `django_auth_superuser`。现有 `staff_required` 只判断 `is_staff`，新授权接口须确保单独 `is_superuser=True` 也可使用，且不要求管理操作者 `verified=True`；复用并完善适当的公共权限机制，避免意外扩大其他接口权限。遵守 [管理员 API 的 CSRF 规范](../ADMIN_API_CSRF.md)，普通用户接口不新增 CSRF。

本人解除关系的 API 不接收可任意指定的目标用户 ID，不要求本人仍已认证；既有普通接口限流约定适用于该独立操作。此接口是本人放弃关系，不能复用站长取消接口并放宽它的权限。普通用户按普通接口约定，管理身份调用该写接口时复用 `admin_csrf_required`；不改变普通申请接口的原有 CSRF 约定。

错误区分准入不满足、没有可由本人处理的申请、请求过期、冷却未结束及状态冲突；直接输入 ID 但没有申请、申请发给其他人或已经被拒绝时均不得提交认证任务。准入失败不再提示“必须实名”。新错误直接替换原准入错误，网站同步更新，不兼容第三方客户端；姓名隐私接口原有 `realname_required` 语义保留。

普通上传迁入 `common` 的 Ninja Router，候选为 `POST /api/common/uploadvideo`；复用 `new_video_by_file` 及文件上传 Schema，保留大小限制、配额、封禁、原上传限流、响应中的录像 ID/状态和 `ranking_access` 维护锁行为。同步调整现有 `videoUploadService` 和测试，移除旧 Django 上传 view/路由，不保留第三方兼容层。

### 5.2 用户界面与缓存

- 个人设置页增加紧凑的玩家认证区域：当前状态、输入认证方本站 ID 发出申请、本人当前申请及到期/冷却时间；认证方使用独立的“认证玩家”输入框填写申请人 ID，直接提交认证，也可按同一 ID 拒绝。输入框明确区分“向谁申请”和“认证谁”，不设收件箱、不展示收到申请列表，也不显示撤回/换人按钮。认证方可以未认证，不能按认证标识筛选可申请对象。
- 不提供主动提示、邮件、站内未读提醒或认证人推荐。申请人须提前通过其他途径认识收件人并约定好，再提交申请；设置页用简短中英文说明该前提，不增加查找陌生认证人的搜索流程。双方自行进入设置页查看和处理。
- 树 verified=True 且 parent 非空时提供独立“解除认证关系”操作，已因上游失效而未认证时也可见；确认说明会移除自己的上游关系并取消自己和有效后代的认证。与不可撤回的未批准申请明确区分；解除后允许重新走申请流程，仍检查节点时间和现有冷却，不擅自豁免冷却。
- 上传与报名未满足准入时，用简短中英文文案说明“实名或玩家认证”并提供相应入口，不再推荐绑定 MSGames 作为准入途径；手动文件选择与比赛自动上传必须同步放开。
- 管理员用户页提供主动认证按钮，可参考用户已有 MSGames 绑定情况提交任务；个人设置中的管理员也可认证自己，站长可见取消按钮。操作提示明确会切断目标入边并取消目标及全部后代认证，前端按钮隐藏不能代替后端授权。取消时说明已实名用户仍可通过实名条件准入。
- 管理员主动认证的确认说明同时提示“任务完成后，目标将成为独立根节点，不再受原上游影响”。所有认证/取消操作提交后先显示“已提交/处理中”，不提前修改前端认证状态；任务完成后再显示成功并分别展示关系已批准和当前认证状态，避免把 202 或未认证者批准显示成“已获得准入”。
- 本人资料 Schema、`user_metadata`、注册/登录/自动登录返回、TypeScript 用户模型及 store 一起更新。公开单用户与批量资料返回 `verified` 并显示当前认证标识，不展示来源、认证人、认证历史或树结构。申请人可读取自己的当前申请，认证方仅按已知 ID 提交处理，不提供收到申请的查询列表。
- 用户持久缓存采用 `services/userService.ts` 的现有机制调整字段与版本，避免旧记录漏字段；保留旧数据的安全默认值。
- 认证变化时显式更新目标和全部受影响后代的 `date_updated`，实名变化也刷新本人准入能力。MSGames 绑定、解绑/撤销关联不影响该能力，无需为准入增加关联事件刷新。角色变化仅影响管理操作权限，不自动授予玩家认证。
- 本页同步操作成功或认证任务完成后重新获取本人状态和是否仍有上游关系，进入设置页读取当前数据。只查询用户自行提交的任务进度，不为收到认证申请建立主动通知或后台催办轮询；任务查询与进度反馈不属于主动催办。既有用户缓存正常更新，后台以最后完整提交的状态判断权限。本人关系存在与否仅返回布尔操作能力，不展示父节点身份；任务结果确认见第 4.5 节。
- 复用 BaseButton、BaseTable 与现有操作结果反馈组件；需要弹窗时按需创建，不建设消息系统或新的通知任务。

## 6. 迁移、发布与文档

1. 按 UserProfile.verified 与四字段 UserVerifyTree 实施模型和状态机，通过 `manage.py makemigrations userprofile` 自动生成迁移，不手改迁移脚本；不另建申请表、审批事件表或认证历史表。
2. 所有账号默认 `verified=False`，不回填管理账号，不因角色或关联自动授予认证。上线后站长/管理员可主动认证自己，再按实际需要认证其他节点；不需要自动认证回填命令。
3. 后端先发布新字段、请求 API 和统一准入能力；三处原实名门槛同步切换，并覆盖所有受影响的登录响应、实名及认证变更路径。
4. 前端同步读取能力、在个人设置页开放认证入口并切换新上传 API；不保留旧上传地址兼容期。安排前后端发布避免网站仍请求已删除地址。
5. 初次上线不因 UserProfile.verified=False 收回已有实名用户的准入；仅绑定 MSGames 不直接准入，由管理员根据绑定情况按需提交认证任务。若回退到旧代码，无实名的新认证玩家会失去准入，须明确通知并保留字段与当前认证树。
6. 更新 `userprofile/README.md` 及实际涉及的录像上传、周赛和 GSC 用户指南（中英文），写明实名或玩家认证准入，不把账号关联列为第三条途径。数据库/索引、管理命令及新增信号分别同步到 `vitepress_doc/zh/guide/development/` 对应文档；仅在实际新增这些机制时更新。API 以自动文档为准。

后续已确认：站长取消任意节点认证时，同时取消其被认证关系，即切断入边；目标成为未认证根，并向有效子树级联取消用户认证状态，后代内部已批准关系保留。内部节点不再继承原上游状态，无需独立撤销字段。

如果他人坚持重新认证该用户，站长可以沿新的关系继续向上追溯处理；这是人际与管理判断，业务逻辑不增加禁止重认、自动追责或特殊审批。这项规则已消除原一致性问题，目前无待确认的业务规则。

最新模型决策：UserVerifyTree 仍仅有 user、parent、created_at、verified 四个字段，不保留认证历史。所有认证与取消由 Django Tasks 后台更新当前记录及 UserProfile.verified；排队、运行、结果与幂等复用既有任务记录，不向树表添加任务字段，也不新增认证流水。申请创建/过期替换和拒绝仍用短事务，惰性清理不改为定时任务。

## 11. 实施状态（代码交付）

模型与数据：`makemigrations` 生成 `userprofile/migrations/0010_*.py`，新增 `UserProfile.verified`、四字段 `UserVerifyTree`（`user`、`parent`、`created_at`、`verified`）以及单行协调表 `UserVerifyCoordinator`。`parent` 关联 `UserProfile` 而不是树节点，删除当前申请记录不会级联删除后代；`(parent, verified)` 联合索引供有效后代遍历。仓库 `.gitignore` 忽略 `**/migrations/*`，新迁移需要用 `git add -f` 显式纳入版本管理。
