# 玩家认证有向图改造计划

状态：2026-11-13，D1–D10 已确认，目前无待定业务规则；阶段 1–3 已实施。第 4、5、6、8、10 节中「后台任务、202 受理、`expected_revision` / `submission_id` 版本比对」的描述已被 D5–D10 取代，以第 11 节为准。旧树功能已完成的检查不能作为新图方案的验证结果。

## 1. 结论：重做认证核心，复用外围能力

**建议重做认证关系模型及其业务模块，不在现有树状态机上继续补丁；保留已经接入网站的准入与展示能力。**

这里的“重做”范围是 `userprofile/verification/`、认证任务入口、关系模型和认证界面，不是重写 UserProfile、录像上传、比赛、登录或全站任务系统。可以在原模块路径内替换实现，不需要另起一套长期并行的系统。

| 判断维度 | 在现有实现上直接改动 | 重做认证核心 |
| --- | --- | --- |
| 关系模型 | UserVerifyTree 以 user 为唯一主键，一个节点只能有一个 parent；改字段不足以支持多条入边 | 新建按有向边存储的模型，多入边、多出边自然成立 |
| 普通流程 | create_request、reject_request、submit_approval、detach 等大部分分支都要删除或改变含义 | 直接表达“已认证用户认证其他人”，无需保留申请状态机 |
| 状态传播 | _effective_subtree、单父节点继承及逐子树统一赋值不适用于多路径和环 | 普通新增认证与站长显式批量修改分开设计 |
| 管理撤销 | 原逻辑切断一条入边并自动取消整棵子树，可能误撤销仍有其他认证来源的人 | 站长自行确定边与节点的完整变更，后端原子执行 |
| 任务参数 | 原任务依赖 parent、created_at、expected_verified、申请期限和操作类型 | 使用认证边命令与站长批次命令，独立于旧申请版本 |
| 界面和测试 | 申请、七天冷却、拒绝、解除、根节点说明需要大幅删改 | 按主动认证、管理员设置属性与站长图维护重写，保留登录/准入/公开标识的回归 |
| 风险与成本 | 表面改动较少，但会保留无效概念，且树算法改名后仍可能误用 | 核心代码替换较集中，迁移边界清楚，长期逻辑更少 |

现有代码中真正可复用的是通用能力，不是树语义：

- `UserProfile.verified`、`has_identity_access` 和“实名或玩家认证”准入。
- 登录、自动登录、本人资料中的 `can_submit_replays`，公开认证标识和用户资料缓存。
- Ninja API、现有权限/CSRF 机制、Django Tasks + django-tasks-db、任务结果查询。
- 全局协调、事务与幂等的设计思路；现有具体实现需重新审查，不能直接保留“等待 120 秒后放行”等行为。
- 上传接口迁移及周赛/GSC 的准入接入，无需再次重写。

## 2. 已确认的新业务规则

1. 认证关系从树变为普通有向图。边的方向为“认证人 → 被认证人”，用户可以有多个认证来源，也可以认证多个人。
2. 不再需要申请。已被认证的用户输入其他人的本站 ID，即可主动认证对方，不要求对方预先提交、确认或批准。
3. 普通用户不能删除已建立的认证边，不能撤回给他人的认证，也不能主动解除自己收到的认证。
4. `UserProfile.verified` 继续表达用户当前有效认证状态，认证可以通过用户间的认证行为传递。
5. 站长负责认证图维护与批次撤销，一次提交所有需要调整的边和节点。后续 D2 明确管理员也可设置 UserProfile.verified，包括 True/False；这更新了先前“只有站长能将属性设为 False”的限制，但不赋予普通管理员删边或提交图维护批次的权限。
6. 站长撤销是极低频场景。后端不计算“应该撤销谁”、替代认证路径、可达性或强连通分量，不自动级联推导撤销结果。
7. 继续沿用已确认的外围规则：准入为“实名或玩家认证”；MSGames 绑定只供管理员参考，不直接准入或自动认证；认证入口在个人设置页，无收件箱和主动提示，不保留关系历史。
8. 沿用上轮后台执行约定：普通认证、管理员设置 verified 和站长批量修改由 Django Tasks 执行。受理与完成分别展示，不能把 202 当成已经生效。
9. 普通认证只新增当前用户到目标用户的边，并将目标 verified 设为 True；已存在出边、下游节点状态、恢复和账号删除引起的一致性问题均由站长负责，后端不增加正向或反向图遍历。
10. 旧树方案尚未部署到生产，不需要编写生产树数据转换或双系统兼容方案。

新机制废止以下旧规则：申请与七天冷却、按申请人 ID 批准/拒绝、未认证者批准申请、本人 detach、单父节点、管理员认证时强制断入边设根、自动撤销子树。普通有向图不要求无环，不能沿用树模型的防成环检查。

## 3. 新数据模型建议

保留 `UserProfile.verified`，作为网站准入和展示读取的当前结果。图的节点使用已有 UserProfile，不增加“根节点/非根节点”身份，也不因管理角色自动认证。

建议新增 `UserVerifyEdge`（暂名），只记录当前存在的有向边：

| 字段 | 建议含义 |
| --- | --- |
| id | 独立主键，一名用户可以对应多条边 |
| from_user | ForeignKey(UserProfile)，认证人 |
| to_user | ForeignKey(UserProfile)，被认证人 |
| created_at | 当前边建立时间，可保留用于维护；不是历史表 |

- 用 `UniqueConstraint(from_user, to_user)` 防止同向重复边，反向边是独立关系。
- 不再使用 user 的 OneToOne 主键或 parent 字段；不再需要边级 verified，因为没有待批准状态，存在的边就是已经建立的关系。
- 普通操作对象是“其他人”，建议禁止自认证边；A → B → A 这样的环允许存在，不增加 DAG 约束。
- 分别支持按认证人查询出边、按被认证人查询入边；复用数据库外键、唯一约束与项目现有关系表做法，不引入图数据库或通用图算法依赖。
- 不保留旧边与操作历史；任务结果仅按现有机制短期保留。
- UserVerifyCoordinator 是否继续使用原表名可在实施时决定，职责收窄为图修改版本/写入协调与任务幂等，不继续承载申请顺序或节点版本语义。

## 4. 普通主动认证：建议只做局部、单调的写入

建议的正常流程：

1. API 校验登录状态、操作者当前 `verified=True`、目标用户存在，受理“当前用户 → 目标用户”的认证任务。
2. 任务在与站长批次共用的协调机制下执行。执行前读取操作者当前认证状态，确认认证传递前提仍成立；不能用排队前的 True 在站长已经撤销操作者后继续授予。
3. 在同一事务内幂等创建该边，将目标 `UserProfile.verified=True`，仅实际变化的资料更新 date_updated。
4. 重复认证同一人不创建重复边，不重置旧边时间；目标已有其他入边或已认证时，可以新增当前操作者的认证边，不覆盖别人。
5. 返回任务完成结果，刷新目标及本人必要的缓存；不新增申请、同意、拒绝或撤销入口。

A 已认证并认证 B，B 随后可以认证 C，即完成正常的多级认证传递，不需要在每次读资料时沿图递归。

**传播边界已确认由站长负责**：若站长把 B、C 都设为未认证但保留 B → C，随后 A 重新认证 B，普通操作只认证 B，不自动恢复 C。相关出边应保留、删除还是同时调整 C，由站长在维护批次中决定；后端不自动遍历，也不要求某种固定的出边清理策略。

权限代码继续放在 API 层；任务执行中的当前认证状态检查用于防止过期授权所依据的业务状态被沿用，不在 service 中重新实现登录、管理员或站长角色鉴权。

## 5. 站长维护：一次提交完整批次，后台原子生效

建议提供一个站长专用批量修改入口，使用 `auth=django_auth_superuser` 与现有管理 CSRF。一次请求携带：

- 要新增的边 `add_edges`。
- 要删除的边 `remove_edges`。
- 要修改认证状态的节点 `set_verified`，每个用户显式给出最终 True/False。
- 图的预期版本 `expected_revision` 和本次提交标识，用于并发冲突及重试控制。

这些是命令输入，后端不据此创建历史表。节点修改指更新 UserProfile.verified，删除账号或清理其他账号数据不属于该入口。

例如当前有 A → B、B → C、X → C。站长决定撤销 B，同时保留 C 的认证，可提交删除 A → B、B → C，并将 B 设为 False；X → C 保持。此处 C 应否保留由站长判断，后端不寻找 X 或计算其他路径。

批次执行要求：

- API 负责站长权限与 CSRF；基础检查包括用户存在、类型合法、同一节点没有互相冲突的赋值、同一边不同时新增和删除、重复输入可识别。
- 后端只校验基础数据及并发版本，不校验“节点最终状态是否等于从某些起点可达”，不替站长补齐受影响节点，也不自动扩展删边范围。
- 任务在同一数据库事务中完成全部边与节点变更、资料更新时间和幂等完成标识；任一写入失败则整体回滚。SQL 可以批量执行，但不能拆成多个提交。
- 普通认证与站长修改使用同一写入协调和图版本。站长基于旧快照提交，而此前普通认证已改变图时，整批返回冲突，由站长重新核对；不在后台静默合并或重新推导。
- 若任务排队期间图版本变化，执行时再次检测，不能只在 HTTP 受理时判断。
- 前端或维护工具可分次读取节点、入边、出边并取得版本，但最终修改必须是一次完整批次；不提供逐节点撤销并自动猜测后续影响的流程。
- 站长可在同一批次显式设置初始用户或其他节点状态；管理员也可通过独立管理入口设置 verified，见下节。管理角色本身不自动认证。
- 若有人持续认证站长认为应撤销的用户，站长通过图关系继续追溯并提交下一批完整修改；业务逻辑不增加禁止重认或自动处罚。

“由站长负责一致性”不取消事务、外键、唯一性和并发校验；它取消的是后端替站长求解认证图的职责。

### 管理员设置 verified

D2 已确认：管理员可显式设置目标 UserProfile.verified 为 True 或 False，包括本人，不要求操作者已经被认证。该操作只修改指定用户属性，不创建或删除边，不自动恢复或撤销其他用户；图的整体一致性仍由站长负责。

建议复用管理权限和 CSRF，提供专用的后台写入口，接收 user_id 和 verified，返回 202 + task_id。任务与普通认证、站长图批次共用写入协调和版本，修改后更新目标 date_updated 及相关缓存。不能因为只有一个字段就绕过后台任务，在通用同步资料编辑中直接写入。

这一入口也可建立初始认证用户，不再要求先由某个已认证用户引导，更不需要补设“根节点”。

## 6. API、任务和界面的重做范围

| 当前实现 | 新方案处理 |
| --- | --- |
| UserVerifyTree / 单父节点版本 | 用有向边模型替换，不保留旧状态机适配层 |
| create_request / reject_request / 七天期限 | 删除，新业务无申请 |
| submit_approval / OPERATION_APPROVE | 替换为已认证用户直接认证目标 |
| OPERATION_DETACH / 普通用户解除 | 删除页面、API 与任务分支 |
| OPERATION_GRANT / 强制设根 | 替换为管理员显式设置 verified=True/False，不要求管理操作者已认证，不自动修改边或其他节点 |
| OPERATION_REVOKE / _effective_subtree / _set_subtree_verification | 替换为站长显式批次，不移植子树撤销算法 |
| expected_parent_id / expected_created_at 等任务参数 | 改为边命令或显式批次及图版本，旧任务不可套用新语义 |
| VerificationStatusOut 中申请状态和冷却字段 | 删除，返回本人当前认证与准入、本人任务状态等必要数据 |
| PlayerVerification.vue / playerVerificationService.ts | 重写为目标 ID + 主动认证 + 本人任务结果，移除申请、拒绝、冷却、解除与根节点文案 |
| StaffView/UserProfile.vue 的旧单用户 grant/revoke | 改为管理员设置当前节点 verified；站长另有完整图批次入口，取消旧单用户自动级联行为 |
| 公开认证标识、上传/比赛入口、can_submit_replays | 保留，只跟随 UserProfile.verified 和实名变化刷新 |
| 旧申请/树/冷却/解除测试 | 移除失效用例，用图关系与批次原子性测试替换；保留不同业务的准入、CSRF 与缓存覆盖 |

普通认证建议为 `POST /api/userprofile/verification/verify`，只接收目标 ID；管理员设置属性建议为 `POST /api/userprofile/admin/verification/set-verified`；站长批次建议为 `POST /api/userprofile/admin/verification/graph-update`，路径为草案。任务提交和结果查询沿用既有返回与权限模式，不另建消息系统。

后台实现复用现有任务基础设施，但重写认证任务内容：

- 取消树的前序任务等待、申请期限和“同一目标只能有一项待办”限制；多个人认证同一目标属于正常多入边。
- 普通重复请求按有向边及任务标识幂等处理；普通认证、管理员设置属性与站长批次协调执行，旧任务不能在撤销后重放授予。
- 长任务不占用 HTTP 等待；任务成功后才更新网站状态，失败回滚、不部分生效。
- 保留任务查询的提交者权限，不将图关系或原始维护参数公开给普通用户。
- 图读取与修改均在 userprofile 边界内，不修改无关的账号关联实现。

## 7. 未上线方案的结构切换与旧任务清理

D3 已确认：旧树方案未部署到生产。本次直接替换尚未上线的认证核心，不建设生产树数据转换命令、双写或长期兼容层；本轮不执行数据库操作。

实施时按以下边界切换：

1. 根据最终模型通过 makemigrations 自动生成结构迁移，移除旧树模型并创建有向边模型，保留 UserProfile.verified 及外围字段。提交迁移及所需依赖，不手写迁移，不擅自重写已在本地应用的迁移文件。
2. 开发和测试环境切换前停止旧认证入口与旧 worker 的写入，检查是否存在 READY/RUNNING 旧任务。若有，明确完成或终止后再切换，不能把旧 approve/grant/revoke/detach 参数解释成图命令。
3. 仅在确有本地遗留队列时处理其清理或明确失败，不为不存在的生产旧任务建设兼容层。是否清理本地认证测试数据按实际环境处理，不重置整个数据库或影响其他业务数据。
4. 新测试数据直接按有向图建立；初始认证由管理员设置 verified 或站长批次完成，不伪造管理员认证边或根节点身份。
5. 删除旧申请、树服务、任务分支、API、界面与失效测试，同步切换新接口、前端和 worker。旧申请接口无需兼容，不静默映射到新主动认证。
6. 上线前确认代码、迁移和任务入口一致。新图产生多入边和环后无法无损回填为单父树，回退需单独评估，不能直接恢复旧代码并继续写入。

不保留关系历史的决定继续有效，不因替换旧模型增加永久历史表。

## 8. 验收与原审核问题的处理

新方案需要验证：

- 只有已认证普通用户能主动认证其他人；无申请也能成功，多入边、双向边和环符合规则。
- 同向重复边幂等；新增边不会覆盖已有来源；普通 API 没有删边、拒绝或解除能力。
- 普通认证只新增当前用户到目标的边并认证目标；既有下游不自动恢复，恢复与边、节点一致性由站长维护。节点已实名与玩家认证两个准入条件继续独立。
- 未认证管理员也能设置本人或他人的 verified=True/False；只修改指定节点，不自动改边或其他节点。普通用户不能调用此管理入口。
- 只有站长能提交图批次；数据变更失败整体回滚，节点与边不会只生效一半。
- 站长提交的版本过旧时明确冲突，不能覆盖并发普通认证；重试不重复施加已经完成的命令。
- 后端不自动删除多余路径、计算撤销闭包、拒绝合法环或修复站长提供的业务结果。
- 账号删除涉及的边与节点一致性由站长负责，后端不自动推导其他节点的认证状态，也不为此新增图修复或专用删除保护流程；基础引用与事务约束仍适用。
- 旧认证任务不会复活旧申请或重新授予，切换期间写入和 worker 状态可核对。
- 本人状态刷新不覆盖后来登录的账号；首次填写实名后刷新后端派生准入字段；进入设置页能够读取当前状态。
- 图版本、普通认证、管理员设置属性与站长批次的任务执行和失败恢复不依赖固定等待秒数。

上轮静态审查中的同步树遍历和任务超时后放行，在重做核心时移除；删除账号后的图一致性按 D4 交由站长维护。迁移未提交和前端会话/准入刷新问题仍然适用，不能因关系重做而遗漏。

实施时按实际范围运行后端检查、Vitest 和必要构建；lintfix/typecheck 遵守跨轮后台工作流。Cypress/E2E 命令随新 spec 定稿后交给用户运行。本轮仅修改计划，不运行代码测试或构建。

## 9. D1–D4 决策记录
