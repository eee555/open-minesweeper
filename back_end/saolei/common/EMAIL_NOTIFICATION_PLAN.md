# 邮件通知系统计划

更新：2026-11-24。

状态：代码已实现。QQ 邮箱已确认不支持 `multipart/multilingual`，改为按用户保存的语言发送单语邮件，默认英文；采用 32 位订阅设置、允许偶发失败、复用登录响应。额度只保存 UTC+8 当前日期的全站计数，不保留历史，订阅默认关闭；新格式的真实邮箱显示待验收。

## 1. 首版范围

- 每个用户用一个 32 位无符号整数字段保存通知订阅状态，普通通知与管理员通知共用；不够时再增加字段。
- 首版只向管理员提供五类通知：作品待审核、录像进入 `FROZEN`、录像进入 `PLAIN`、账号关联申请、新标识自动审核未通过（`safe=False`）。
- 通知提醒管理员处理事项，不是给投稿人、上传人或申请人发送审核结果；后者将来另分配类型。
- 用户设置 `language`（`zh-cn`、`en`、`es`），默认 `en`；每封通知仅包含所选语言的主题、纯文本与 HTML 正文。
- 允许偶发丢信；通知入队、额度读取、模板或发送失败都不能影响业务事务和业务 API 的成功结果。
- 通知邮件由独立后台 worker 发送，请求不等待邮件处理或发送完成；SMTP 延迟、超时及 worker 暂停不阻塞原请求返回。
- 设置放在个人主页已有的「设置」tab，仅本人操作；初始值随登录 API 返回，不新增设置 GET 接口。
- 全站共用每日 2000 封额度，包括注册、找回密码等现有邮件。

首版不增加可靠发件箱、邮件历史、持久摘要批次或自动补发。原草案的每小时摘要暂不实施，先验证五类事件和按语言发信；后续需要合并提醒时单独评估。

## 3. 32 位订阅字段

在 `UserProfile` 增加 `email_notification_mask = PositiveIntegerField(default=0)`。

同时增加 `language = CharField(max_length=5, choices=..., default='en')`，允许 `zh-cn`、`en`、`es`。现有账号通过迁移初始化为英文，新账号同样默认英文；设置独立于网站界面语言，不从浏览器自动改写。

当前 Django MySQL 后端映射为 `INT UNSIGNED`，范围 `0..4294967295`，可使用位索引 `0..31`。已核实本地安装版本的映射及范围；实现时自动生成迁移并验证第 31 位及最大值。

| 位索引 | 稳定类型键 | 数值 | 管理员通知 |
| --- | --- | --- | --- |
| 0 | `staff_media_review` | 1 | 作品待审核 |
| 1 | `staff_video_frozen` | 2 | 录像冻结 |
| 2 | `staff_video_plain` | 4 | 录像需要审核 |
| 3 | `staff_account_link_review` | 8 | 账号关联申请 |
| 4 | `staff_identifier_unsafe` | 16 | 新标识自动审核未通过 |
| 5–31 | 保留 | — | 后续普通通知与管理员通知按需分配 |

- 位为 1 表示订阅，建议所有账号默认 0，由管理员主动开启；新增类型默认关闭。
- 已发布编号不移动、不复用。用完后增加第二个无符号整数字段，既有字段语义不变。
- JSON 直接传整数，例如 `"email_notification_mask": 31`，不再使用十进制字符串或 `BigInt`。
- JavaScript `Number` 能精确表示全部 uint32，但位运算结果可能为有符号数。第 31 位不能用结果大于 0 判断是否启用，也不能将负数保存进登录态；写入由后端按类型合并。
- 偏好只加入本人用户响应，不加入公开资料、玩家名批量缓存或管理员通用编辑字段。
- 当前五类接收者要求 `is_active=True`、`is_staff=True`、`is_memorial=False`，并具有对应订阅位；过滤空邮箱与 `@accounts.invalid`。仅有 `is_superuser=True` 不自动扩大既有后台权限。
- 订阅不授予权限，后台 API 保留原有权限检查。

## 4. 五类触发条件

| 类型 | 触发条件 | 不提醒的情况 |
| --- | --- | --- |
| 作品审核 | 新作品以 `PENDING` 保存；未来重新提交可视为新事件 | 重复投稿失败、普通保存、已处理 |
| 录像冻结 | 创建即为 `FROZEN`，或从其他状态转入 | 重复冻结、只修改原因、相同状态保存 |
| 录像需要审核 | 创建即为 `PLAIN`，或从其他状态转入 | 普通保存、同一操作中的临时默认值 |
| 账号关联申请 | 手工申请进入未验证状态 | OAuth、自动验证成功、同一流程已直接验证、重复申请 |
| 新标识审核没过 | 新建标识自动审核为 `safe=False` 且实际提交 | 重复遇到同一标识、管理员将旧标识改为不安全 |

事件在业务最终状态确定后发布；任务发送前再次确认对象仍处于对应待处理状态，已处理、删除或变更则跳过。

`QuerySet.update` 和批量写入不会触发保存信号，实施时列出相关写入点，必要时显式发布等价事件。批量操作尽量将同类对象 ID 合到一次任务，避免每行注册重复提醒。

## 5. 后台发送、请求边界与事务隔离

`业务写入 → transaction.on_commit(..., robust=True) → Django Tasks 入队 → worker 检查状态与订阅 → 占额 → SMTP`。

- 请求路径只捕获必要事件参数并注册回调；提交后回调只做轻量任务入队，不查询收件人、不构造 MIME、不读取或锁定额度行、不连接 SMTP。
- `on_commit` 回调仍在提交事务的请求线程中执行，并不会自动变成后台任务。因此实际邮件处理必须在独立 worker 中运行，不能直接把发信函数作为提交后回调。
- 请求只承担任务入队的数据库写入开销，不等待、轮询或读取任务完成结果；不在请求内等待发信速率、额度恢复或 SMTP 超时。收件人查询、状态复查、模板渲染、额度检查及发送都由 worker 完成。
- 入队失败直接记录并放弃本次通知，不回退到同步发送，也不在请求中重试。worker 未启动或队列积压时，原请求照常返回；运行配置必须使用现有数据库队列，不能通过即时执行后端或入队信号在请求内执行邮件任务。
- 事务提交前不写通知表、不连接 SMTP、不查询额度，也不把通知任务入队放进业务事务。
- 用 `transaction.on_commit(callback, robust=True)` 注册提交后回调，回调只尽力入队。入队异常记录日志后结束，不传播为 API 失败；回滚时回调自动丢弃。[Django 提交后回调](https://docs.djangoproject.com/en/6.0/topics/db/transactions/#performing-actions-after-commit)。
- 生成参数、注册回调也需隔离异常，尽量只读取现成的类型、对象 ID 等标量，不引入通知数据库查询。不能依赖在原事务内捕获通知数据库异常来保证继续，因为事务可能已失效。
- 无外层事务时，`on_commit` 立即执行回调，因此回调也必须健壮且只入队，不同步发送。
- worker 的占额事务独立于原业务事务。额度、模板及 SMTP 异常只影响通知，不回写或回滚业务数据。
- 不为通知扩大业务事务、增加业务锁或改变上传、导入的接受与拒绝语义。
- 普通上传中已提交的不安全标识应提醒，即使录像随后被拒绝；历史导入中随外层事务回滚的标识不提醒。
- 提交后进程退出、入队失败造成漏信可以接受，不扫描业务库补发。

## 6. 额度表以外的持久记录有什么用

原草案中的两张表用于更强的可靠性与摘要处理：

| 原记录 | 用途 | 首版取舍 |
| --- | --- | --- |
| `EmailNotificationItem` | 保存每个接收者的待发项，支持丢任务后补发、持久去重、处理结果跟踪 | 删除设计，允许偶发丢信，无需可靠发件箱 |
| `EmailNotificationBatch` | 保存摘要成员、领取状态、尝试次数，支持聚合、并发领取、重试 | 删除设计，首版不做持久摘要或自动重试 |

**首版只新增 `EmailSentQuota` 表中的一条当前额度记录，以及用户表上的订阅、语言字段。** 额度记录只用于防止当日超限，不保存历史日期或逐封邮件。Django Tasks 自带的任务记录继续复用，属于现有队列设施，不再为同一封通知增加业务记录。

- 按发送时的当前管理员资格和开关选择收件人，不保存事件发生时的订阅快照，也不回扫历史待办。
- 每个任务对每位收件人最多尝试发送一次；明确失败、超时或 worker 中断均不自动补发，不承诺严格不重不漏。
- 一位管理员发送失败时记录日志并继续其他接收者，不重跑已经部分成功的整个收件人列表。
- 同状态重复保存由触发逻辑避免；不增加跨任务持久去重。重复任务如果再次发送，仍计入额度。
- 额度不足直接跳过本次通知，不积压到次日，后台业务待办照常保留。
- 日志记录类型、对象 ID、任务 ID、接收用户 ID 及失败原因；不记录验证码、密钥或邮件原文。

未来明确需要稳定补发、定时摘要、收信历史或严格去重时，再增加对应持久记录。

## 7. 每日 2000 封额度

全站共用每日 2000 封硬上限，包括通知与验证码。只保留一个总计数，不再单独统计通知用量，也不采用原草案尚未确认的 1800/200 分配。

`userprofile/models.py::EmailSentQuota` 固定一条记录，业务字段只有：

| 字段 | 用途 |
| --- | --- |
| `quota_date` | 当前计数所属的供应商额度日期 |
| `count` | 当日已经占用的发信名额 |

使用固定主键（例如 `id=1`）标识这一条记录，不以日期作主键，也不按日期新增记录。跨日直接覆盖 `quota_date` 并将 `count` 重置为 0，不归档旧值，无需历史清理任务。名称虽为 `Sent`，计数语义是「保守占用的发信尝试数」，不是最终投递成功数。

共用占额与 SMTP 入口放在 `userprofile/mail.py`，只依赖本 APP 模型和 Django 邮件接口，供验证码流程与通知任务调用：

1. 一封邮件一个收件人，不通过群发或 BCC 规避计数；每封仅使用该收件人设置的语言，占一封额度。
2. 每封邮件临发送前，用独立短事务锁定固定额度行。取得锁后按供应商时区重新计算当前日期；跨日则原地重置日期和计数，随后仅当 `count < 2000` 时加 1，否则跳过通知或按验证码失败路径返回。
3. 占额实际提交后再发送，不在 SMTP 期间持锁，不嵌套到可能回滚的业务事务。
4. 失败、超时或占额后进程退出均不退额，避免结果不明时少算；通知不自动重试。
5. 额度数据库不可用则不发信。通知记录日志后跳过，业务仍成功；验证码按原有失败路径及时返回，不排到次日。
6. 共用入口只处理占额和发送；允许通知失败的策略由通知任务负责，不把验证码发送失败伪装成成功。

首次创建也使用相同固定主键，通过唯一性约束处理并发初始化。创建先独立提交，避免竞争插入的共享锁在后续升级为行锁时造成 MySQL 死锁；随后在另一个事务中完成锁行、重置、检查上限与加一。取得锁后再读取当前日期，不能用入队或等待前的旧日期将计数重置回上一天。无需零点定时任务；当天首次占额自然完成重置。

例如任意邮件合计已占 1900，当日最多再占 100。阿里云按收件人计量，平台接受后即使最终投递失败也计费，因此不按收件箱结果退额。[计量说明](https://help.aliyun.com/zh/direct-mail/billing-methods)。

供应商重置时区已确认是 UTC+8，默认配置 `EMAIL_QUOTA_TIME_ZONE=Asia/Shanghai`，按该自然日重置；项目与浏览器时区不参与计数。上线前仍需同步当日已用量或等新窗口启用，并遵守供应商速率限制。部署或重启继续使用当天已有计数，不重新清零。

共用配额的其他脚本或控制台发送需统一入口或扣减本地可用量。大批导入按供应商速率发送；通知因额度不足跳过，不影响导入完成。

## 8. 按用户语言发送单语邮件

管理员试用已确认 QQ 邮箱不支持原先的 `multipart/multilingual`，改用 Django `EmailMultiAlternatives`，详见[邮件格式与运行说明](email_notifications/README.md)。

- worker 读取收件人当前保存的 `language`，入队参数不缓存语言，因此排队期间改设置会在实际发送时生效。
- 根类型为 `multipart/alternative`，包含同一语言的 `text/plain` 和 `text/html`，主题与正文一致；邮件头 `Content-Language` 和 HTML `lang` 标记该语言。
- 三种语言复用同一业务数据与模板，只翻译通知文案；每位管理员收到一封单语邮件。
- 复用 Django 邮件对象、现有 SMTP 后端及统一额度入口，不再重写 `message()` 或嵌套 `message/rfc822`。
- 不依赖浏览器或邮箱客户端自动选择语言，不在邮件内加入脚本、CSS 隐藏或远程图片选语言。
- 仅提供必要类别、数量、对象 ID 与后台链接，不携带验证码、原始响应或不安全标识原文。转义用户输入，链接仍需登录及权限验证。
- 邮件提供本人通知设置链接，不新增 GET 写接口。

仅保留单语格式；QQ 及其他客户端的新格式显示由管理员验收，自动测试不发送真实邮件。

## 9. 随登录返回设置，只新增保存 API

新增 `email_notification_mask: number` 与 `language: 'zh-cn' | 'en' | 'es'`，直接放进已有的本人用户对象：

- `user_metadata(user, user)`：覆盖密码登录、注册、找回密码结果；非本人调用不返回该字段。
- `SelfUserInfoOut`：通过 `create_schema` 的本人字段白名单加入，覆盖 `/api/common/loginauto`、`/api/userprofile/info/0` 及复用该 Schema 的 QQ 本人响应。
- 公开 `UserInfoOut` 和用户目录不加入；匿名自动登录的 `user` 仍为 `null`。
- 前端 `UserProfileData`、`UserProfile` 和登录态保存这两个值，分别默认 0 和 `en`，复用 `applyLoginSession`；不能在某种登录方式漏掉。
- 设置页直接读 `store.user.email_notification_mask` 与 `store.user.language`，不增加专门的 GET。本人资料刷新也沿用这两个字段，避免把已保存值重置。

只扩展响应与相关类型，不为该需求重写旧登录接口。

新增 `PATCH /api/userprofile/email-notifications`，请求例如 `{changes: [{type: "staff_video_plain", enabled: true}], language: "es"}`，两项均可省略，但至少提供一项有效修改。返回 `{email_notification_mask: 4, language: "es"}`。前端显式使用 JSON Content-Type，成功后原地更新登录态对应字段，不重新登录或请求设置。

- 不接受目标用户 ID。API 层检查本人登录状态、类型及布尔值，拒绝未知或重复类型；保存管理员通知偏好不检查管理员身份，仅由前端屏蔽非管理员入口，实际收件资格统一在 worker 发信时检查。
- 锁定用户行后只合并指定类型，保留其他位，避免旧页面覆盖新类型及其他标签页偏好。
- 允许只改语言，不改订阅位；只改订阅位时保留语言。语言与订阅在同一事务保存，未知或空语言拒绝整个更新。
- 按本人维度限流，建议 `30/m`；装饰器列于 docstring 开头，模型输出优先 `create_schema` 字段白名单。
- 这是本人偏好接口，按[管理员 API 的 CSRF 规范](../ADMIN_API_CSRF.md)，不因调用者恰好是管理员就新增后端 CSRF。
- 保存明确传 `update_fields`，按 UserProfile 约定包含 `date_updated`；私有响应不进入共享缓存。

前端在 `UserSettingsView.vue` 嵌入紧凑的 `EmailNotificationSettings.vue`。所有用户可设置通知语言，管理员额外看到五个开关，普通用户显示暂无可订阅类型；复用项目原生 `.base-select`、复选框样式、基础按钮、三语文案与本人访问限制。

保存中禁止重复提交，失败保留选择，成功只更新对应字段；退出或切换账号后清理未保存状态，丢弃旧账号迟到响应。无可用邮箱不能开启，不新增邮箱修改流程。

## 10. 实施与验收

文件归属：`userprofile/models.py` 与 `mail.py` 负责字段、唯一新增额度模型及发信；`services.py`、`schema.py` 扩展登录数据；`api.py` 保存偏好；`common/email_notifications/` 负责跨 APP 事件、任务与 MIME；前端用户类型及设置组件同步更新。

基础模型不反向引入 `common`；跨 APP 接收器由 `common/apps.py::ready()` 注册，不在导入阶段查库。无需新增 `common/models.py`、通知业务迁移或周期补发调度。实现时更新实际涉及的开发文档。

实施顺序：

1. 自动生成订阅、语言字段和 `EmailSentQuota` 迁移，全部发信接入统一占额，通知随 `EMAIL_SKIP` 控制。
2. 补齐本人登录响应、前端登录态与保存接口，默认订阅关闭。
3. 接入五类事件，验证回滚不触发、提交后入队失败不影响业务、请求只入队不等待发送，实现独立 worker 的单次尽力发送。
4. 验证 MIME 结构，少量管理员主动订阅，核对客户端显示、供应商计数及实际额度窗口。

关键验收：

- MySQL 往返保存 `0`、`1 << 31`、`2^32-1`，越界拒绝；JSON 为非负整数，前端第 31 位不误判。
- 密码登录、注册、找回密码、自动登录、QQ 本人响应均携带设置；公开接口不泄露偏好，设置 tab 不增加 GET。
- 本人保存、匿名拒绝、非管理员可保存管理员通知偏好但不收到管理员邮件、按类型合并、登录态原地更新、切换账号迟到响应。
- 五类触发与重复保存边界、不安全标识两个入口、上传拒绝后的已提交记录、导入回滚。
- 用 `captureOnCommitCallbacks` 或事务测试确认回滚不入队；入队、额度、模板或 SMTP 异常不影响业务；一个收件人失败不阻断其他人。
- 请求路径测试断言收件人查询、模板构造、额度占用及 SMTP 均未执行，只登记待处理任务；worker 暂停或模拟 SMTP 持续阻塞时，业务请求仍能返回，且入队异常不会触发同步发信回退。
- 通知与验证码共用 2000 上限；并发初始化仍只有一行，跨日并发只重置一次，旧请求不重置回旧日期；失败不退额、同日重启不清零、上线已用量初始化，跨日后不保留历史行。
- 默认英文、三种语言选择、只改语言保留高位订阅、只改订阅保留语言、非法语言拒绝整个更新；worker 使用发送时偏好。
- 单语 `multipart/alternative` 根类型、本地化主题、语言标签、发件邮箱、HTML/纯文本及输入转义；不配置自动重试和周期补发。
- 自动测试使用隔离数据库、locmem 或捕获 MIME 字节，不消耗生产额度；真实客户端留给管理员试用。
