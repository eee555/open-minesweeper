# 勋章静态规则升级

勋章规则唯一来源为 `medal/definitions.py` 与 `medal/utils.py` 中的静态阈值。玩家进度、授予、佩戴、人工覆盖和审计日志继续存数据库。新增或调整规则应通过代码评审发布。

## 已有数据库升级

1. 暂停后端和勋章任务，备份数据库，并导出 `medal_medaldefinition` 原配置。对比代码规则，确认是否存在需要转入代码的自定义定义或阈值。
2. 在服务器现有迁移历史上执行 `python manage.py makemigrations medal --name static_definitions`。自动生成的操作必须依次为 `RemoveField(playerprogress.definition)`、`DeleteModel(MedalDefinition)`；本目录的 `static_definitions.py` 是本次 Django 自动生成的参考文件，依赖编号对应本地历史，不直接拷贝到不同历史的服务器。
3. 检查迁移计划，再执行生成的勋章迁移。不要通过 ORM 删除定义对象，也不要清空任何玩家状态表；旧外键有级联删除行为，必须先解除外键。
4. 核对迁移前后的玩家进度、授予、佩戴、人工覆盖和审计日志数量、主键及内容。现有授予继续使用原来的 `definition_code`，进度继续使用原来的 `code`。
5. 配置不再使用 Redis 目录缓存。线上“走马观花”仍为旧十模式要求，迁移并启动新版本后台工人后，必须补发已扫描玩家：先执行 `python manage.py enqueue_medal_backfill --all --dry-run`，再通过 `--all --limit 500 --batch-size 100` 分次入队，按输出的 `last_user_id` / `through_id` 续跑。后台工人执行完整评估并更新进度、授予历史和摘要，需观察任务完成情况、失败任务和数据库负载。仅切换存储方式不必抹除现有状态。未定义或停用的 code 保留历史数据，但不在公开目录展示。
6. 恢复新版本服务与后台工人后，按步骤 5 分批入队并验收任务结果。一次性迁移及重算不放入 `start.sh`。

## 新安装与回退

新安装由当前模型生成初始迁移，不再创建定义表。仓库既有数字迁移文件不在 Git 中，本次提供参考模板，避免提交一个依赖不存在历史文件的活动迁移。

数据库删除配置表后，单纯回退代码不会恢复配置。需要回退时，使用升级前的配置导出与数据库备份恢复，并重新核对外键、玩家状态和缓存。
